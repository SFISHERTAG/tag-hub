# Story 3.6 — Escalation view — ascension and risk

**Epic:** 3 — CSM portfolio and impersonation
**Status:** In Review — core loop implemented and verified (types + tests + AC-by-AC audit); AC3/AC5 have documented partial gaps pending live GHL data, see "Known gaps" below

## Story

As a CSM, I want a filtered view of my portfolio showing only clients at key moments (ready to ascend, or at risk of churn), so that I can focus on growth and rescue without scanning the whole list.

## Context

Per `docs/prd.md`, escalation signals identify where action is needed:

**Growth opportunities (Ascension):**
- All health metrics are green AND no expansion upsell attempted yet
- Clients winning deals consistently, ready for closing team or higher tiers

**Churn risk (Rescue):**
- Delivery stalling — deals won but no closing activity
- Show rate collapsed (< 15%)
- CSM hasn't checked in for 30+ days

An escalation view surfaces these without requiring manual scanning.

## Acceptance criteria

1. `/portfolio?view=escalations` shows three sections: Ascension Ready, At Risk, No Action Needed.
2. Ascension Ready: healthy clients with no recent upell attempts.
3. At Risk: critical health OR delivery stalls.
4. No Action Needed: healthy clients, no issues.
5. Each section is sortable by stage or days since last check-in.

- [x] Categorize clients into three buckets — `lib/rules/configs/escalation.config.ts`. Wired today: critical health → At Risk, 30+ days since check-in → At Risk, healthy + no upsell attempted → Ascension Ready, else No Action Needed.
- [x] Layout: three card groups, each sortable — `app/csm-dashboard/views/escalation-view.tsx`, sortable by "days since check-in" (real) or "stage" (see gap below).
- [x] Link to "enter tenant" action (3.3) for follow-up — each card has an "Enter tenant" button wired to `enterImpersonation`.

## Known gaps (why this isn't marked Done)

- **AC3 is partially wired.** "Critical health" and "no check-in 30+ days" both fire for real. "Delivery stalling" and "show rate < 15%" do not — both need a live per-client GHL fetch (fulfillment-pipeline stage, calendar events) that doesn't exist on this read path yet (documented in `escalation.config.ts`). Evaluating with those fields absent is safe (rules engine treats a missing field as "not met"), it just means today's At Risk bucket can under-flag, never over-flag.
- **AC5's "stage" sort is a stand-in.** `ClientData` has no GHL pipeline-stage field yet (3.1's own task list still has "Integrate Fulfillment opportunity stage from GHL" unchecked), so "stage" sort orders by health status (critical → alert → at-risk → healthy → excellent) instead. Real stage sort needs that 3.1 follow-up first.
