# Story 4.6 — Owner's own calendar view

**Epic:** 4 — Client owner dashboard
**Status:** Done

## Story

As a client owner, I want to see my own calendar of scheduled calls, so that I can prepare and remember when my team needs to be ready.

## Context

The closer's workspace (Story 2.2) shows all appointments across the team's calendars — a working surface for the day-to-day. The owner's dashboard shows only their own calendar (assigned to them as an attendee or organizer in GHL), so they can prepare for their calls without seeing the whole team's schedule.

## Acceptance criteria

1. Query appointments assigned to or with the owner as a contact.
2. Display as a calendar month view + upcoming list.
3. Show appointment title, time, status (confirmed/showed/no-show).
4. Link to edit status (mark showed/DQ) if appointment is today or past.
5. "No upcoming" message if nothing scheduled.
6. The grid, the month label and the day an appointment falls on are all computed in a named timezone, not the process timezone. Added after the fact — see "The view was Done and wrong" below.

## Tasks

- [x] Query GHL appointments by owner contact ID or assigned user
- [x] Component: OwnerCalendarView (month grid + upcoming list)
- [x] Add to dashboard (4.2)
- [x] Link to appointment status controls if past/today
- [x] Compute the grid, label and buckets in a named timezone, defaulted the way `lib/ghl/format.ts` and `dayRange` already default it

## Dev notes

**Owner identity resolution (was ambiguous, now decided):** GHL appointments carry `assignedUserId` (the staff member assigned to run the call) and `contactId` (the lead being called) — neither is natively a "primary contact for this tenant" or an "owner tag." Rather than build a new tag-lookup path with no existing precedent in `lib/ghl/contacts.ts`, this filters on `assignedUserId`, matched against a new optional `Tenant.ownerGhlUserId` field (`lib/ghl/tenants.ts`) — set per-location when the client owner also runs their own calls. If unset, the view falls back to showing the location's whole calendar (with a banner) rather than an empty screen, since most tenants won't have this configured yet.

Implementation:
- `lib/ghl/tenants.ts` — added `ownerGhlUserId?: string` to `Tenant`.
- `lib/dashboard/owner-calendar.ts` — `getOwnerCalendar()`: fetches the current month's grid range + a 60-day upcoming horizon via `getAppointments`, filters by `ownerGhlUserId` when set, builds the month grid and upcoming list (capped at 10).
- `lib/dashboard/widget-definitions.ts` — new `owner_calendar` widget, available to `client_owner` and `tag_exec`, registered last so it defaults to the bottom of the grid, below spend/ROAS/funnel/KPI widgets.
- `app/dashboard/widgets/owner-calendar-widget.tsx` — presentational month grid + upcoming list; past/today appointments render the existing `StatusControls` from `app/l/[locationId]/today/status-controls.tsx` unmodified, future ones show a read-only status badge; empty upcoming list shows "No upcoming calls scheduled."
- Wired through `app/dashboard/page.tsx` → `page-client.tsx` → `widget-grid.tsx`, following the same pattern as `day_view`/`pipeline_board`.

This is a secondary view on the dashboard (after spend/ROAS/funnel). Not a full calendar app — just enough to show scheduled calls.

## The view was Done and wrong, which is the case the Status field cannot express

Recorded 2026-08-27, when the timezone defect was found and fixed. **The status was
not lying about the code: every task above was genuinely implemented and the
component genuinely rendered.** It was wrong about the code being *correct*, and
nothing in a Status field distinguishes those.

`getOwnerCalendar` did its date maths in the **process** timezone — `setHours`,
`getFullYear`, `getMonth`, `getDate` — while formatting `monthLabel` in
America/Chicago. Nothing sets `TZ` in Cloud Run, so the process is UTC (see
`lib/time/zone.ts`) and the two disagreed. Three symptoms, one cause:

- `monthLabel` read **one month behind the grid it labels, in 12 of 12 months**,
  and a year behind every January. The anchor was midnight UTC on the 1st, which
  reads as 7pm on the previous month's last day in Central.
- A 7pm Central appointment **bucketed onto the following day's cell**.
- After 6pm Central the grid **drew the wrong cell as today**, and
  `isPastOrToday` flipped early, so the status controls appeared on the wrong
  appointments.

**Why it survived:** `lib/ghl/format.ts` and `dayRange` were fixed for this exact
class of bug before this story was written, and this file was written afterwards
on the process zone anyway. On a US developer's machine every symptom disappears,
which is why the tests for it now force `process.env.TZ = "UTC"` — without that
they pass whether or not the bug exists.

**Status stays Done rather than being reopened**, because the fix lands in the
same commit as this note and the story is true at that commit. Flipping to
In Progress and back inside one commit would record a process, not a fact. What
was missing was never the Status: it was acceptance criterion 6, which did not
exist, so there was nothing for the view to fail.

The zone primitives now live in `lib/time/zone.ts` (`zonedDateParts`,
`zonedDateKey`, `startOfDayInZone`, `endOfDayInZone`) and `dayRange` delegates to
them, so there is one implementation of "midnight in a named zone" rather than
two. Tests: `test/owner-calendar.test.ts`.
