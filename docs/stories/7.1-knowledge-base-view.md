# Story 7.1 — Knowledge Base view

**Epic:** 7 — Knowledge Base
**Status:** Ready

## Story

As any logged-in TAG-side staff member, I want to read the CSM operating manual inside the app, so that I don't need to dig through static files outside the product to find process guidance.

## Context

The "TAG CSM Operating Manual" currently exists only as 14 standalone static HTML files in `_archive/` (`00.html`–`13.html`), generated from `_archive/manual-content.json` via `_archive/generate-manual.js`. It is not wired into the Next.js app at all — no route references it, and it is unreachable when a user logs in.

This story migrates the manual's content into Firestore and exposes it as real in-app routes under `app/knowledge-base/`, viewable by any logged-in TAG-side staff role. Editing (story 7.2) is out of scope here — this story is read-only.

## Acceptance criteria

1. A new Firestore collection `manual_pages` holds one document per manual page (id, num, title, eyebrow, lede, status, level, blocks[]), seeded from `_archive/manual-content.json`.
2. A one-time migration script reads `_archive/manual-content.json` and seeds `manual_pages`, following the `NODE_ENV`/project-detection guard convention used by `scripts/setup-*.ts`.
3. `app/knowledge-base/page.tsx` lists all 14 pages (title, eyebrow, status); `app/knowledge-base/[pageId]/page.tsx` renders one page's blocks.
4. Both routes are server components: `force-dynamic`, call `getSession()`, redirect to `/signin` if no session.
5. Access is gated via `hasAnyRole()` from `lib/auth/roles.ts` against all TAG-side roles (`ROLES.ADMIN`, `ROLES.TAG_EXEC`, `ROLES.TAG_CSD`, `ROLES.TAG_CSM`, `ROLES.TAG_SALES_MANAGER`, `ROLES.TAG_SALES`, `ROLES.TAG_SETTER_MANAGER`, `ROLES.TAG_SETTER`) — no inline role strings. Client-side roles are denied with an access-denied block, same pattern as `app/csm-dashboard/page.tsx`.
6. Data is fetched via a server action (`actions/get-manual-pages.ts` / `actions/get-manual-page.ts`), not the Firestore client SDK directly from a component.
7. `docs/data-model.md` gets a new row + rationale for `manual_pages` in the same commit as the code.
8. `npm run build && npm run test --watch=false && npm run lint` all pass.

## Dev notes

**Block types.** All six block types across the 14 pages: `paragraph`, `heading`,
`note` (has a `severity`: `hard`/`good`/unset), `table`, `procedure` (has
`steps[]`, optional `warning`/`note`), `instrument` (an interactive calculator
in the old static HTML — see 7.1's scope note below). `manual-content.json`'s
`blocks` field is kept as a loose `Record<string, unknown> & { type: string }`
union rather than six strict TS shapes — `app/knowledge-base/manual-blocks.tsx`
switches on `type` and reads fields defensively (`typeof x === "string"`
guards), and unknown/malformed blocks fall back to a raw JSON dump instead of
crashing the page. This also keeps the admin editor (7.2) simple: it edits
`blocks` as one JSON blob rather than needing six different form layouts.

**No server action for reads.** AC6 originally called for
`actions/get-manual-pages.ts` mirroring `csm-dashboard`'s pattern, but that
indirection exists there specifically because `csm-portfolio.tsx` is a
*client* component and can't import Firestore Admin SDK code directly. Here
both routes are plain server components (no interactivity needed for a
read-only view), so they call `lib/knowledge-base/db.ts` directly — this is
also what `app/admin/courses/page.tsx` does for its own list view. Deviated
from the story's own AC6 wording; the underlying goal (keep `@google-cloud/
firestore` out of the client bundle) is met either way.

**Instrument blocks aren't interactive.** The old static HTML manual had
JS-driven calculators (unit economics, cost-per-call) behind `instrument`
blocks. That JS wasn't ported — out of scope for a content-migration story —
so `instrument` renders as a static list of the calculator's field labels/
defaults and output labels. If the calculators matter, that's a follow-up
story, not a blocker for getting the content in-app and readable.

**Migration not run.** `scripts/migrate-manual-to-firestore.ts` requires
`GOOGLE_CLOUD_PROJECT` set explicitly (refuses to run without it — no
fallback to `lib/firestore.ts`'s default `"tag-success-hub"`) and writes real
Firestore data. Running it against the wrong project silently seeds
production or clobbers a project someone else is using. Not run as part of
this change — run it yourself once you've confirmed which GCP project to
target: `GOOGLE_CLOUD_PROJECT=<project> npx ts-node scripts/migrate-manual-to-firestore.ts`.

**Browser verification not run.** Verifying the signed-in view requires
`TEST_AUTH_ENABLED=true` plus real Firebase Admin credentials
(`app/api/auth/test-signin/route.ts` calls `adminAuth().createCustomToken`
and Firebase's `signInWithCustomToken` REST API) — not configured in this
environment, and not something to enable/exercise against a real Firebase
project without your say-so. Confirmed instead by: `npm run build` (all
routes compile and register, including `/knowledge-base` and
`/knowledge-base/[pageId]`), `npm run lint` (clean on the new files),
`npm run test --watch=false` (178 passing, unrelated to this change), and by
matching the exact `getSession()` → `hasAnyRole()` → `DarkScope` guard
pattern already verified in production by `app/csm-dashboard/page.tsx`.
Please click through as a `tag_csm` test session once the migration has run,
and flag anything before treating this as fully verified.
