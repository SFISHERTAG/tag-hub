# Story 7.7 — Write scope and team to the claim

**Epic:** 7 — Command surface and configurability
**Status:** In Review — all tasks complete; AC9 verified by inspection only, see Completion Notes

## Story

As a closing manager, I want the hat I wear to carry the team it manages, so that "my team's
numbers" is a thing the system knows rather than a thing my role name implies.

## Context

Story 7.6 added `RoleGrant.scope` and `RoleGrant.team`, and `resolveScope` reads both.
`lib/auth/session.ts` parses them defensively, dropping unrecognised values rather than
passing them through. Every part of the read path exists.

**Nothing writes them.** `setUserClaims` (`lib/auth/admin.ts`) writes exactly
`{ roles: [{ role, locations }] }`. There is no other caller of `setCustomUserClaims` that
sets a grant, so `scope` and `team` are `undefined` on every claim ever issued, and
`resolveScope` has always fallen through to `DEFAULT_SCOPE_BY_ROLE`.

The effect is narrow and total: the per-hat scope 7.6 designed is inert. A `tag_sales_manager`
gets `team` by role default and then `resolveScope` narrows them to `self`, because their team
list is empty and an empty team is deliberately treated as a misconfiguration rather than
permission to see everyone. So the manager sees their own rows, the same as a closer, which
is precisely the "indistinguishable to the data layer" problem 7.6 opens by describing.

This was found while scoping **Story 7.8**, and it is separable from it. 7.8 makes per-user
data reachable at all; this makes the grant able to say whose. Neither depends on the other to
land, but `team` scope produces nothing useful until both are done.

## Acceptance criteria

1. `setUserClaims` accepts and persists `scope` and `team` on each grant.
2. A grant written without them is unchanged in meaning — the role default still applies, so
   existing claims and existing callers keep working.
3. `team` is rejected unless the grant's `scope` is `team`, so a stored team cannot sit behind
   a `self` or `tenancy` grant waiting to be misread later.
4. `scope` is validated against the same three values `session.ts` parses; an unrecognised
   value is refused at the write rather than dropped at the read.
5. `team` entries are uids that exist, and a uid that does not resolve fails the write.
6. A user cannot be their own team member, and duplicates collapse.
7. The claim stays inside Firebase's size limit, and exceeding it fails the write with a
   message naming the limit rather than a generic Firebase error.
8. The admin surface can set both, and can clear them back to the role default.
9. Changing either invalidates the claims cache, as role changes already do.

## Tasks

- [x] Extend `setUserClaims` to take `scope` and `team` per grant, defaulting to omitted
- [x] Validate `scope` against the three levels; refuse anything else at the write
- [x] Refuse `team` on a grant whose scope is not `team`
- [x] Resolve every team uid before writing; fail the whole write if any is unknown
- [x] Drop self from team, dedupe, and cap the claim against the size limit
- [x] `PUT /api/admin/users/[uid]/role` accepts scope and team, with the existing role gate
- [x] Angular admin users surface can set and clear them
- [x] Tests: round trip through `parseRoleGrants`, each refusal, and the size ceiling
- [x] Test that a grant with no scope still resolves to its role default

## Dev notes

**The size limit is the risk worth designing for, not a footnote.** Firebase custom claims cap
at roughly 1000 bytes for the whole object, and `roles` is already an array of grants each
carrying a `locations` array. Adding a uid list per grant is the first thing here likely to
breach it, and the failure mode is bad: `setCustomUserClaims` rejects the write, so a role
change appears to fail for reasons unrelated to roles. AC7 exists so that message says what
actually happened. If teams turn out to be larger than the claim can hold, the answer is a
team *id* in the claim pointing at a Firestore document, not a truncated list — a silently
shortened team is a silently narrowed dashboard.

**Groups already exist and may be the better home.** `app/api/admin/users/groups` manages
named groups with `memberUids`. A `team` that duplicates a group is two sources of truth for
the same fact, and they will disagree. Worth deciding before building: either `team` names a
group id, or groups grow a scope and this story writes the derived list. This story does not
pick, because the choice belongs with whoever owns the admin model.

**Do not widen the fail-closed behaviour.** `resolveScope` narrows an empty team to `self` on
purpose. Making the write path guarantee non-empty teams does not make that branch dead code
worth deleting: a claim issued before this story still has none, and the branch is the reason
that user sees too little rather than too much.

## Dev Agent Record

### Implementation plan

Validation went into a new `lib/auth/grants.ts` rather than into `admin.ts`, so
it is pure and provable without Firebase. `admin.ts` keeps only the I/O:
normalise, size-check, resolve team uids, write, invalidate. The one part that
genuinely needs I/O, confirming a team member resolves to a real user, takes its
resolver as an argument for the same reason.

Red-green-refactor throughout. Each group of tests was written first and
confirmed failing — the first run failed with `Cannot find package
'@/lib/auth/grants'` before the module existed, and the team-resolution tests
failed against a missing `assertTeamUidsExist` before it did.

### Completion notes

All nine acceptance criteria are implemented and all nine tasks are complete.

**AC9 is the one caveat.** `setUserClaims` still calls `invalidateClaimsCache`
after the write, unchanged by this story, so cache invalidation continues to
behave as it did for role changes. It is verified by inspection rather than by a
test, because asserting it needs `firebase-admin` mocked and this story added no
other reason to build that harness. Stated here rather than implied by a checked
box.

**Two design questions the story raised are still open, and neither was decided
here.** The claim-size ceiling is enforced (AC7) but not designed around: if a
real team exceeds it, the fix is a group id in the claim pointing at a Firestore
document, not a shorter list, and the error message says so. And `team` still
duplicates what `app/api/admin/users/groups` already models — a group has
`memberUids`, a team grant now has `team`, and nothing keeps them in step. Both
belong with whoever owns the admin model.

**Scope on group assignment was deliberately not built.** `assignIndividualRole`
carries scope and team; `assignGroupRole` does not. A group's members share a
role, not a team, and writing one team to every member is a different feature
with a different meaning.

**What this does not do:** it does not make `team` scope produce data. Story 7.8
is what lets the data layer find a user's rows at all; until then a team grant
resolves correctly and the adapter still refuses to answer it.

### Review repairs, 2026-08-22

The 2026-08-22 adversarial review (docs/reviews/2026-08-22-branch-review-fix-plan.md,
Stream 2) found seven defects in and around this story's write path, all fixed:

- **functions/src/auth.ts mergeGrants wiped admin-set scope and team on
  re-provisioning** — the functions-side RoleGrant had no team field and a
  matched grant was replaced wholesale, so a webhook retry undid what this
  story's UI wrote (and narrowed multi-tenancy grants to the re-provisioned
  location). A matched grant now wins: provisioning only backfills scope onto
  a grant that has none. One old pin expected the opposite ("stale" scope
  healed to the default); that expectation was correct only while provisioning
  was the sole writer of scope, and is updated with the reasoning.
- **assertTeamUidsExist conflated an Auth outage with missing users** — the
  per-uid getUser had a bare catch returning false, so transient failures read
  as "these team members do not resolve", naming real people. The resolver is
  now a single getUsers batch whose notFound list is the only source of
  "missing"; any other failure propagates as itself. One round trip instead of
  N as a side effect.
- **assignIndividualRole detached from the group before validation**, so a
  rejected grant ("nothing was written") had already removed group membership.
  The pure validation now runs first; a test proves a rejected grant touches
  neither Firestore nor claims.
- **updateGroupRole let an invalid grant partially write** — per-member
  Promise.all with per-member validation. The identical grant is validated
  once before the fan-out.
- **Group routes surfaced GrantValidationError as a masked 500** — covered by
  the pre-fan-out validation above plus the routes' existing handling; the
  individual-role route already mapped it to 400.
- **readScope treated '' as "clear the override"** — the one malformed value
  that silently changed the grant instead of 400ing. Removed; the Angular form
  now holds null natively (FormControl<ScopeLevel | null>), deleting the ''
  sentinel and both translations.
- **A deleted team member was invisible and undeletable** — stored uids
  missing from the directory now render as labelled, deselectable options
  instead of silently round-tripping and failing every save.

Decision recorded (was flagged, not silently made): setUserClaims keeps
owning the entire claims object rather than preserving unknown keys. The two
legacy writers/readers were migrated instead: scripts/create-user.mjs writes
the roles-array shape (and retires the legacy `role` key it finds), and
user-directory.ts reads claims through parseRoleGrants — the same reader the
session uses — which also makes pre-migration users visible in the admin
directory instead of showing "no role" while holding a working session.
parseRoleGrants' doc no longer claims to be test-only.

Root tests 493 to 502, functions gains its first auth tests (5), web 577 to
580. All failing-first.

## Touched by story 14.1 (2026-08-23)

`lib/auth/groups.ts` moved behind the `lib/data` repository seam. Status and
Tasks are unchanged: 7.7's behaviour, acceptance criteria and claim shape are
untouched, and nothing here re-opens or lands the story.

What changed is only where the data comes from. Every `firestore()` call became
a `repository().groups` call, including the `array-contains` membership query
that `findMemberGroup` relies on. That query is the reason the group side holds
membership at all, per this story's own note that custom claims are capped and
already spent on role and locations — so the seam had to carry
`array-contains` rather than force a denormalised field onto the user.

One thing improved rather than moved. `fromDoc` took a
`FirebaseFirestore.DocumentData`, so a Firestore type was in the public shape of
a function in this module. It now takes `Omit<Group, "id">`. That leak was
invisible until the collection was typed at the seam, and it is the kind of
thing 14.10 would otherwise have discovered while trying to drop the SDK.

## Touched by story 14.B (2026-08-23)

`lib/auth/admin.ts` had a role string literal at line 175, inside
`promoteToExec`, and 14.B converted it to `ROLES.TAG_EXEC`. Status and Tasks are
unchanged: 7.7's behaviour, acceptance criteria and claim shape are untouched,
and nothing here re-opens or lands the story.

It is recorded because of *where* it was. This is the claim-**issuing** path, and
CLAUDE.md names a `"tag_admin"` versus `"admin"` mismatch as the exact failure
the role constraint exists to prevent. A typo in a literal here writes a claim
that nothing grants against, so the user is silently locked out rather than
refused — which is the failure mode this story's own notes care most about.

It survived because the check enforcing that constraint reads only files staged
in a commit, so it could never see a violation already in the tree. Story 14.B
closed that with `scripts/check-role-strings.mjs`, which scans the whole tree.
