# Story 3.2 — Client health signals

**Epic:** 3 — CSM portfolio and impersonation
**Status:** In Progress. Three separate states, recorded 2026-08-26: the health
signal ships and is wired end to end; the values behind it are fabricated
identically for every client; and its inputs differ from AC2-AC4 by a deliberate,
documented decision, which makes those criteria stale rather than unmet. See
Correction, 2026-08-26.

## Story

As a CSM, I want to see at a glance which clients need attention, so that I can prioritize calls and outreach.

## Context

Health is derived from appointment and conversion data:
- Show rate (showed ÷ booked) — indicates funnel quality
- DQ rate (DQ ÷ showed) — indicates lead quality or targeting issue
- Close rate (closed ÷ showed) — indicates offer/closer fit
- Delivery stalls (deals won but delivery not marked) — indicates churn risk

For MVP, "healthy" is binary: show rate > 30%, no open stalls. This is a default; actual thresholds are dynamically configurable from CSM dashboard (TODO).

## Acceptance criteria

1. A `getClientHealth()` function returns `{ status: "healthy" | "at-risk" | "critical", reason?: string }`.
2. Health is computed from recent outcomes (last 30 days).
3. "At-risk" means show rate 15–30%, or delivery stalls.
4. "Critical" means show rate < 15%.
5. Portfolio (3.1) displays health as a colored badge (green/yellow/red).

## Correction, 2026-08-26

Two code defects, and one stale specification. They are different kinds of thing,
and the difference decides what anyone should do about them.

**Defect 1 (code) — the values are fabricated, identically, for every client.**
`lib/dashboard/csm-clients.ts:81` calls `getMockMetrics(clientId)`.
`lib/dashboard/mock-metrics.ts:59` names that parameter `_clientId`, ignores it,
and returns `{ roas: 95, spend: 102, leads: 88, sla: 97 }` for every client in the
system. The consequence is arithmetic, not approximate. Weights are roas 35,
spend 25, leads 25, sla 15, already summing to 100, and `calculateComponentScore`
maps those four fixed inputs to 85, 100, 50 and 85:

```
85(.35) + 100(.25) + 50(.25) + 85(.15) = 29.75 + 25 + 12.5 + 12.75 = 80.0
```

Every client scores exactly 80 — "healthy", four stars. So `avgHealthScore` is
exactly 80 for every CSM book and for the department; "worst book first" in
team-health-rollup orders equal values and is therefore input order rather than a
ranking; and `needsAttentionCount` is permanently 0.

**Defect 2 (code) — `sla` is 15% of every score and has no producer.** Its only
assignment anywhere is `mock-metrics.ts:60`. It is consumed at
`health-scoring.ts:41`, `:108` and `:114`, and rendered by `client-card.ts:45` and
`overview-tab.ts:76`. No GHL, Meta or Postgres path supplies it. Unlike defect 1
this does not resolve by sourcing real data, because there is no source to point
at.

**Not a defect — AC2, AC3 and AC4 are stale. The code is right.** AC2 requires
computation from recent outcomes over 30 days; AC3 and AC4 define at-risk and
critical entirely by show rate. The implementation scores roas, spend, leads and
sla instead, and `csm-clients.ts:32-36` records why: `showRatePct` and
`deliveryStalled` each need a live per-client GHL fetch — calendar events for the
first, a resolved fulfillment-pipeline id for the second — added to what is today
a pure-Firestore read path. For the department-wide rollup that is dozens of live
GHL calls per page load.

That decision is deliberate, documented and correct. It simply never travelled
back to this story. **So the remedy is to rewrite these criteria, not the code.**
Anyone reading AC2-AC4 as unmet acceptance would bring the implementation back to
show rate and reintroduce the per-page-load GHL cost the code deliberately
avoided. That would be a regression authorised by a document, and this section
exists so that this story cannot be used that way.

### Open decisions — neither taken here

1. **What should AC2-AC4 say?** The headline question, not a cleanup. The system
   can afford roas, spend and leads from stored data; it cannot afford show rate
   per client per page load. Rewriting the criteria to what the system can afford
   is a product decision about what "health" means, and `csm-clients.ts:32-36` is
   the cost argument for it.
2. **`sla` gets a real source, or leaves the weighting.** Not a technical tidy-up:
   the weights re-normalise across the remaining three, so every score shifts and
   every historical comparison shifts with it. Removing it changes what a health
   score means.

### A gap this exposed

`check-story-status` could not have caught the checked task corrected above. It
compares a story's Status against its own Tasks. Nothing in this repo compares a
checked Task against the code that would satisfy it, so a task can stay checked
indefinitely while the code says otherwise in a comment four files away.

### What this correction deliberately does not do

It does not mint a new story. 3.2 owns this acceptance, and moving its unmet
criteria into a sibling would let 3.2 keep a Phase-1-complete reading while the
thing it promised lived under another number. If the fix needs its own
implementation story, that story descends from a corrected 3.2.
