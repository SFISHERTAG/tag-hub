# Story 6.5 — Delivery monitoring and retry

**Epic:** 6 — Acquisition loop
**Status:** Done

## Story

As TAG, I want to know if conversions reached Meta, and automatically retry if they failed, so that dropped conversions don't silently leave the algorithm blind.

## Context

Meta Conversions API can fail (network, auth, rate limit). Stories 6.2–6.3 log dispatch attempts to Firestore, but if a send fails, the conversion is lost and we don't know it.

This story monitors dispatch logs and retries failed sends on a schedule (hourly, 24h window).

## Acceptance criteria

1. Dispatch log (Firestore) tracks: event, timestamp, status (pending/sent/failed), error.
2. Sent: response from Meta included event_received: true.
3. Failed: error on send, or event_received: false.
4. Retry job runs hourly: query last 24h of failed conversions, retry up to 3 times.
5. Alert if conversions fail 3 retries (ops escalation, not user-facing).
6. Dashboard (Epic 4, optional): show conversion health (% delivered).

## Dev notes

**Reused existing infra instead of building parallel machinery.** `lib/webhooks/`
(signature verification, idempotency, dead-letter-queue) was already in the repo,
built but unwired — its README says Tag Hub currently polls GHL rather than
receiving webhooks, so none of it was live. Two of its three modules are pure
Firestore helpers with no dependency on inbound HTTP, so this story reuses them
directly for AC5's escalation sink rather than inventing a second collection:
`lib/webhooks/deadLetterQueue.ts`'s `recordFailure` + `flagForReview` record the
"3 retries failed" alert (`source: "meta_conversions"`, `reason: "handler_error"`).
`signature.ts` and `idempotency.ts`'s source+eventId dedup model didn't map cleanly
onto retry-attempt tracking, so those were not reused — the dispatch log itself
carries `attemptCount` / `lastAttemptAt` / `nextRetryAt` instead.

**Log model.** Stories 6.2/6.3 already wrote one Firestore doc per event to
`locations/{locationId}/metaConversionLog/{eventType}_{entityId}` with a
`status` field (`sent | skipped | error`). Extended in place rather than adding a
second log: `status` is now `pending | sent | failed | skipped`, and each doc also
carries `attemptCount`, `lastAttemptAt`, `nextRetryAt`, `createdAt`, and (once
escalated) `alertedAt`. `pending` is written before the Meta call so a mid-call
crash still leaves a retryable record. `sent` now requires Meta's response body to
report `events_received >= 1` — the previous implementation only checked HTTP
status, which meant AC2/AC3 (event_received true/false) were not actually
enforced before this story. See `lib/meta/conversions.ts`.

**Retry job.** `lib/meta/retry.ts`'s `runMetaRetryJob()` runs a Firestore
`collectionGroup("metaConversionLog")` query for `status == "failed"` within the
last 24h, filters in-memory for `nextRetryAt <= now` and `attemptCount <
MAX_ATTEMPTS` (4 = 1 original dispatch + 3 retries), and resends using the same
Meta `event_id` (the appointmentId/opportunityId) as the original dispatch —
confirmed by `lib/meta/retry.test.ts`. Backoff schedule is `RETRY_BACKOFF_MS =
[1m, 5m, 30m]`, indexed by how many retries have already run, computed by
`computeNextRetryAt` (exported from `conversions.ts` so the schedule isn't
duplicated). At `attemptCount === MAX_ATTEMPTS` the job escalates once
(`alertedAt` guards against re-alerting on a later run that rescans the same
doc) via the dead-letter queue, plus an optional Slack post through a new
`postAlert()` in `lib/slack.ts` (posts to `SLACK_OPS_CHANNEL_ID`, separate from
the per-client channels the rest of that module reads — logs to console instead
if unset).

**Idempotency confirmed.** Meta's Conversions API dedupes by `event_id` within a
48h window server-side. Both the original dispatch and every retry send the same
`event_id` (appointmentId for "showed", opportunityId for "closed_won"), so a
retry firing after Meta actually received the original but the HTTP response was
lost is a no-op on Meta's side, not a duplicate conversion. This holds because
`postConversionEvent`'s `eventId` param is threaded through unchanged on retry —
`lib/meta/retry.test.ts`'s first test asserts the final log's `eventId` still
matches the original dispatch's.

**Trigger wiring.** No Cloud Scheduler config existed in the repo yet (checked:
no `.tf`, no scheduler/cron/pubsub references outside this story doc). Built as
a Next.js route (`app/api/cron/meta-retry/route.ts`, `POST`) rather than a
separate Cloud Function in `/functions` — that package can't import `lib/`
(different deployable, own `package.json`), which would have meant duplicating
the dispatch/Firestore logic. The route reuses the Cloud Run service already
deployed for the main app. Auth is a shared-secret bearer token
(`CRON_SECRET`), mirroring the existing pattern in
`app/api/onboarding/intake-submit/route.ts` — not a user session, since Cloud
Scheduler has none to present. **Not yet provisioned**: the actual
`gcloud scheduler jobs create http` command to hit this route hourly still needs
to be run against the deployed Cloud Run URL, with `CRON_SECRET` and
(optionally) `SLACK_OPS_CHANNEL_ID` set in the Cloud Run service's env.

**AC6 (intentional failure test).** `lib/meta/retry.test.ts` fakes Firestore and
`fetch` in-memory and drives the real code path end to end: `dispatchShowed`
against a failing mock Meta call → doc lands `status: "failed"` with a future
`nextRetryAt` → backoff window force-opened → `runMetaRetryJob()` retries against
a now-succeeding mock → doc lands `status: "sent"`, `attemptCount: 2`, same
`eventId`. Separate tests cover: a failure whose backoff window hasn't elapsed
yet is left alone (no `fetch` call), and a failure at `attemptCount === 3` that
fails once more escalates (DLQ entry + `flagged: true` + one `postAlert` call).
Existing 6.2/6.3 tests (`test/dispatch-showed.test.ts`,
`test/dispatch-closed-won.test.ts`) updated for the `error` → `failed` rename and
the new events_received body check.

Dashboard conversion-health view (AC6, optional) not built — out of scope for
this pass; the underlying data (`status`/`attemptCount` per doc) is there for
Epic 4 to query later.
