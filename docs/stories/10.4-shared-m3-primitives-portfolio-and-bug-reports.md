# Story 10.4 — Shared M3 primitives, portfolio and bug reports

**Epic:** 10 — Angular migration
**Status:** In Progress

## Story

As any signed-in user, I want the first real screens in Angular, built on shared
Material 3 primitives that every later feature reuses rather than reinvents.

## Context

Split from the old 10.4 on 2026-08-21. That number carried two different
stories: `docs/epics.md` used it for this one, while the story file of that
number was a production-hardening and release story. The release story moved to
10.9, where a release belongs, after 10.8 sweeps `legacy/`. This is the feature
story, and it is the one Story 11.4 calibrates its estimates against.

It is deliberately first among the feature stories, and deliberately small.
`features/` currently contains one directory, `auth`. Everything a feature needs
that is not a feature — a page shell with a title, an empty state, a loading
state, an error state, a data table, a confirm dialog — does not exist yet. The
first feature story either builds those or inlines them, and inlining them means
10.5, 10.6 and 10.7 each invent their own.

Portfolio and bug reports are the right first features because they are the two
simplest real screens in the app. Portfolio is a list of tenants with an action;
bug reports is a form and a list. Between them they exercise the whole path
end to end — endpoint, typed service, guard, list, form, empty and error states —
without the parent-route resolver that makes 10.5 large.

That is also what makes this the calibration story. It is the smallest complete
instance of the work that 10.5, 10.6 and 10.7 repeat at scale, so its numbers
are the unit the rest are estimated from.

## Acceptance criteria

   state, error state, loading state, data table, confirm dialog. Each is
   standalone, `OnPush`, and themed only through M3 system tokens.

   `!important` or a deep selector.

   an `app/api/**` endpoint rather than importing `lib/`.

**AC5 is unmet with a deliberate alternative recorded, and the distinction
matters.** The criterion is meetable, so this is not the AC7 amendment; its
source of truth is alive, so it is not the AC9 withdrawal. It is a third case:
the letter is unmet, the intent may already be served, and the difference is a
decision nobody has made.

Both halves, so whoever decides has them. Against the verdict: bug reports sits
in `layout/user-menu/user-menu.html`, and that placement matches the precedent
`app.routes.ts` sets for settings, "Reached from the user menu, not the nav: it
is an account screen rather than a destination in the product." Reporting a bug
is plausibly the same kind of thing. For the verdict: this story's own task line
reads "Nav entries for both, matched to their guards", so the story asked for a
nav entry and there is not one, and the settings precedent was written for a
different story about a different screen.

Scored unmet rather than met-by-relocation because rounding it up would settle a
design question by absorbing it into a status pass.

The asymmetry that justifies choosing unmet is worth stating, because an earlier
draft of this reasoning used one that does not work. Arguing that `epics.md` and
`sprint-status.yaml` carry a status rather than an evidence cell, so a contested
verdict and a clean one look identical downstream, is true of unmet exactly as it
is of met, and a symmetric argument cannot pick a side. The real asymmetry is
that the two verdicts fail differently: an unmet criterion demands attention and
a met one closes the question silently. Unmet is the conservative score because
it forces someone to look, not because it is more visible. Leaving it unmet forces the
decision to be made by someone entitled to make it. If the user-menu placement is
the intended answer, amend the criterion and say so; do not let a checkbox decide
it.

**Carried-forward resweep item: survived.** "One unreachable tenant does not
empty the whole portfolio" is met. `app/api/portfolio/tenants/route.ts` uses
`Promise.allSettled` over `getTenant`, and carries the defect note inline so the
`Promise.all` cannot be reintroduced by someone tidying. This is the counterpart
to Story 10.5's freshness indicator, which did not survive: same class of
carried-forward item, opposite outcome, and the difference is that this one was
written into the code rather than left to the story doc to remember.

**A latent drift this pass found and did not fix.** `layout/nav/nav-items.ts`
does not import `PORTFOLIO_ROLES`; it hand-copies the four roles and asserts
equality in a comment. The two lists do agree today, diffed value by value. They
are not enforced to: nothing imports the constant into the nav, and no test
compares them. The mirror is structurally forced, because
`web/eslint.config.js` forbids `layout/**` from importing `features/**`, which is
the architecture boundary working as intended. So the nav cannot import the
guard's list, and the only thing keeping them in step is a comment. Recorded here
rather than fixed, because the fix is an architecture question about where shared
role lists live, not a story correction.

## Dev notes, why the primitives belong here rather than in 10.1

10.1 was contract hardening and was deliberately feature-free: lint zones,
strict mode, guards, the boundary the build enforces. Primitives are not
contracts. Designing an empty state before any screen needs one produces a
component shaped by imagination rather than use.

Building them here, against two real screens, means they are shaped by two real
consumers. Building them any later means 10.5 has already inlined its own.

## Dev notes, what "smallest complete instance" has to include

If this story skips the endpoint layer by having portfolio read something that
already exists, it stops being a calibration instance and its numbers stop
transferring. The point is that it does every step 10.5 does, at the smallest
scale where each step is still real.
