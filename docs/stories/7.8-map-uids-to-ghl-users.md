# Story 7.8 — Map uids to GHL users

**Epic:** 7 — Command surface and configurability
**Status:** Draft

## Story

As a closer, I want my dashboard to show my own deals, so that the number I am judged on is
mine rather than the whole tenancy's.

## Context

`ScopeFilter.uids` holds Firebase uids. Every row that could answer "whose" carries a GHL user
id instead — `Opportunity.assignedTo`, `Appointment.assignedUserId`. These are separate
identity spaces with nothing joining them. `Tenant.ownerGhlUserId` maps exactly one person per
tenant, for Story 4.6's owner calendar, and the `users` side is Firebase Auth claims.

So `lib/sources/metric-source.ts` cannot answer a per-user query, and says so: it throws
`UnsupportedScopeError` rather than returning every row (the leak Story 7.6 exists to prevent)
or no rows (a real zero on a dashboard that could not answer, which is the error-as-empty
confusion the `ApiResult` contract refuses elsewhere). Location scoping is real today; uid
scoping is unreachable.

The consequence is live, not theoretical. `DEFAULT_SCOPE_BY_ROLE` gives `self` to `tag_sales`,
`tag_setter`, `client_closer` and `client_setter`, and all three registered metrics list
`client_closer` in `availableFor`. Wiring a metric to a route today means a closer gets an
error every time. **Nothing is wired yet, so this story is what unblocks route wiring**, not a
repair of something users are hitting.

Sibling to **Story 7.7**: that one lets a grant say *whose rows*, this one lets the data layer
find them. Independent to build; `team` scope needs both.

## Acceptance criteria

1. A stored mapping resolves a `(uid, locationId)` pair to a GHL user id.
2. Keyed by uid **and** location, not uid alone — one person may be a different GHL user in
   each tenant they work.
3. `lib/sources/metric-source.ts` resolves `scope.uids` through it and passes the resulting
   GHL user ids down as a filter, rather than fetching wide and narrowing after.
4. An unmapped uid fails the query. A partially resolved team is a failure, not a subset —
   returning the mapped members silently under-reports a manager's team.
5. The failure stays distinguishable from "no rows", as `UnsupportedScopeError` is today.
6. A backfill matches on email, reports every unmatched user, and never fuzzy-matches.
7. The resolved id is stored, not re-derived from email per query.
8. An admin can set and correct a mapping by hand, for the users the backfill cannot match.
9. `docs/data-model.md` documents the store, in the commit that adds it.

## Dev notes

**The external unknown is GHL's users endpoint.** `lib/ghl/` has no users client, so whether
this API version exposes a location's users with their emails has to be confirmed against the
GHL docs before the rest is worth building. If it does not, the backfill has no source and
every mapping is manual, which changes AC6 and AC8's weight completely. Confirm this first.

**Email is the backfill key and must not become the stored key.** Both sides have an email and
this codebase already uses email as its identity bridge — `csm/{email}` is keyed that way
precisely "to match `clients.csm_assigned`". But emails change and GHL users get deleted and
recreated, so resolve once and store the id (AC7). Re-deriving per query also puts an email
lookup on every dashboard read.

**Silent misattribution is the expensive failure, and it reviews clean.** A wrong join shows
one closer another closer's deals, and the number looks entirely plausible. That is why AC6
forbids fuzzy matching: an unmatched user reported to an admin costs a minute, and a
confidently wrong match costs someone's commission argument. For the same reason AC4 refuses a
partial team rather than returning what resolved.

**Ad spend has no per-user answer at all.** Meta attributes spend to an ad account, not a
person. `readAdSpend` should keep refusing a per-user scope after this story, and AC10 pins
that so a later reader does not "finish the job" by inventing an attribution.

**Do not put this in the claim.** Claims cap near 1000 bytes and Story 7.7 is already spending
that budget on `team`. More decisively, a team filter needs *other people's* GHL ids, which a
caller's own claim cannot carry. The store has to be readable per-uid by someone who is not
that uid.

**The adapter is already the right shape.** `lib/sources/metric-source.ts` sits outside the
`import/no-restricted-paths` zone, so it may read the mapping directly, and
`requireTenancyScope` is the single function that changes. Nothing in `lib/dashboard/` moves.
