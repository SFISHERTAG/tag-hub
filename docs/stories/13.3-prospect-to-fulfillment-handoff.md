# Story 13.3 — Prospect to fulfillment handoff

**Epic:** 13 — Lifecycle handoff and churn prevention
**Status:** Draft — blocked on the Fulfillment location decision below
**Depends on:** 13.1

## Story

As TAG, I want a closed prospect to leave the sales pipeline and appear in
Fulfillment automatically, so that a client's journey is continuous and no deal
is worked twice.

## Blocking decision: which location holds Fulfillment

The codebase and the live data disagree, and this story cannot be built until
one of them is chosen.

- `functions/src/webhooks/phase1-provisioning.ts` creates the Fulfillment
  opportunity in the **newly cloned client sub-account**.
- The 2026-08-21 audit found all 37 Fulfillment opportunities in **TAG's own
  sub-account**, `rb6hPt8Ue77L4abghRMc`.

Either the webhook has never run for these clients, or two Fulfillment models are
operating at once. Everything below assumes one answer. Record it here before
starting.

## Context

The trigger already exists. `handlePhase1` fires on a GHL webhook when the
"Initiate Onboarding" checkbox is set and the deal is in Closed Won, and it
already provisions the sub-account, Slack channel, Drive folder, sign-in
whitelist, intake email, and a Fulfillment opportunity. It is idempotent on the
opportunity id.

What it does not do is close out the prospect opportunity. The sales record stays
open on the board after the client has moved into delivery, so the sales pipeline
accumulates deals that are no longer deals.

"Archive" is not a state GHL has. An opportunity is `open`, `won`, `lost`, or
`abandoned`. A converted prospect is `won`; marking it `abandoned` would
understate the close rate. So archiving here means setting the real terminal
status and filtering terminal opportunities out of the working views, not
inventing a fourth state.

## Acceptance criteria

1. On the Closed Won plus Initiate Onboarding trigger, the prospect opportunity
   is set to its terminal status (`won` for a conversion) with its monetary
   value preserved.
2. A Fulfillment opportunity is created for the same contact at the pipeline's
   first stage, via `lib/ghl/`'s `createOpportunity` from 13.1.
3. The new opportunity records the originating prospect opportunity id, so the
   handoff is traceable in both directions.
4. Working views filter out terminal opportunities by default. A closed prospect
   is still retrievable, just not on the board.
5. The handoff is idempotent. Re-firing the webhook must not create a second
   Fulfillment opportunity. The audit found Frank Gutta already holding two.
6. A failure creating the Fulfillment opportunity does not leave the prospect
   opportunity closed with nothing downstream. Either both land or the failure is
   surfaced and retryable.
7. An audit record is written for each handoff.
