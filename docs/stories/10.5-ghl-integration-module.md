# Story 10.5 — GHL integration module

**Epic:** 10 — Angular migration
**Status:** In Progress

## Story

As a closer, setter or client manager, I want the pipeline, today view, contacts
and follow-up queue in Angular, reading the same GHL data through HTTP rather
than through a server component that imports `lib/` directly.

## Context

This is the first story that moves real features, and the largest single block
of them. The GHL surfaces are the daily-use screens: `app/l/[locationId]/**`
(pipeline, today, contacts, prep, follow-up config), plus `/today`, `/followup`
and `/contacts` at the root.

They are also the densest concentration of server actions in the app. Every one
of them has to become an endpoint under `app/api/**` before the Angular screen
can exist, because an SPA cannot call a Server Action. That is the shape of
this story: endpoints and screens ship together, per Epic 10's rule, and the
matching Next pages are deleted in the same commit so no screen exists twice.

`features/ghl/` is an integration module. Per CLAUDE.md and
`docs/frontend-file-tree.md` it may import `core/` and `shared/` and nothing
from a sibling integration. If a GHL screen needs Meta data, it goes through an
endpoint, not an import.

## Acceptance criteria

1. `features/ghl/` exists with `location/` (parent route carrying the
   `locationId` resolver and guard), `pipeline/`, `today/`, `contacts/`,
   `services/` and `widgets/`, all lazy-loaded, standalone and `OnPush`.
2. Every GHL server action reachable from these screens has an `app/api/**`
   equivalent, typed on both sides, with the same ownership checks the action
   carried.
3. No component calls `HttpClient` directly; all traffic goes through a typed
   service in `features/ghl/services/`.
4. `features/ghl/` imports nothing from `features/meta/`, `features/drive/`,
   `features/slack/` or `layout/`, enforced by the `no-restricted-imports`
   zones rather than by review.
5. The four GHL widgets (pipeline-board, day-view, leads-funnel, owner-calendar)
   register through `WidgetRegistry` by id and required permission, and the
   dashboard shell still names no integration.
6. `locationId` is resolved once by the parent route and never read from a
   component's own parameter snapshot.
7. The Next pages these replace are deleted, and their routes point at
   Angular. The deletion sweep is owned by Story 10.8.

## Dev notes, why this story is big and should not be split by screen

Splitting by screen looks tempting and produces a worse outcome. The four GHL
screens share the `locationId` parent route, the tenant guard, the typed
service layer and the token-resolution seam behind it. Shipping pipeline alone
means building all of that for one screen, then either rebuilding or retrofitting
it three times. The endpoints are also not one-to-one with screens: the same
appointments read backs the today view, the follow-up queue and the day-view
widget.

What can be split is the widget set. If the bundle budget or the calendar
demands it, the four widgets can follow in a fast-follow, because they consume
endpoints this story already ships.

## Dev notes, the ownership checks must survive the move

Each server action being replaced carries a tenant-ownership check, and several
of those checks were added specifically because the action was reachable without
one. When the logic moves to an endpoint the check moves with it — an endpoint
that trusts a `locationId` from the request is the same defect the resweep
closed, in a new place. `requireLocationAccess` and `ownsLocation` in
`lib/auth/session.ts` are the sanctioned path; an endpoint should call one of
them, not re-derive the rule.
