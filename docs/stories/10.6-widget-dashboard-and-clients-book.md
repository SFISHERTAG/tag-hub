# Story 10.6 — Widget dashboard and the clients book

**Epic:** 10 — Angular migration
**Status:** Draft

## Story

As a CSM, CS Director or executive, I want the configurable dashboard and the
clients book in Angular, with widgets resolved at runtime by id and permission
so the shell never learns an integration's name.

## Story, the second half

As a client owner, I want my own dashboard to show my tenant's numbers, which
means the widget data path resolves my location from my session.

## Context

Two surfaces, one story, because they share the widget registry and most of
their data. `/dashboard` is the configurable grid; `/csm-dashboard` is the book
of business at 1,562 lines of working views (grid, list, kanban, escalation,
plus the client detail modal's four tabs).

`features/clients/` is deliberately **not** an integration module. It shows GHL
pipeline data next to Meta spend next to Drive creatives, and the rule that
integrations may not import each other would make that impossible if it were
one. Cross-integration data arrives through one backend endpoint that does the
joining server-side. That is the constraint that decides this story's endpoint
shape: not one endpoint per integration, but one per view.

The dashboard shell knows no integration by name. Widgets register through
`WidgetRegistry` and are resolved by id plus required permission, loaded through
dynamic `import()` named only in `widget-loaders.ts`, the one declared exemption
to the boundary rule.

## Acceptance criteria

1. `features/dashboard/` holds the widget shell and `customize/`, and imports no
   feature module by path.
2. `features/clients/` holds `book/` (grid, list, kanban, escalation),
   `client-detail/` (overview, campaigns, creatives, status) and its own
   widgets.
3. Cross-integration reads for the clients book go through a single endpoint per
   view; no Angular service composes two integrations client-side.
4. Widget entitlement is enforced server-side on both the save path and the read
   path. A saved layout naming a widget the role may not use neither saves nor
   fetches.
5. The layout save round-trips through an endpoint, and the saved layout is keyed
   per `(uid, hat)`.
6. `widget-loaders.ts` is the only file naming a feature by path for widget
   loading.
7. The Next pages these replace are deleted in the same commit.
8. `ng build --configuration production && ng lint && ng test --watch=false`
   pass.

## Dev notes, why the mock-metrics disclosure is an acceptance concern

`getMockMetrics()` ignores its client id and returns the same four numbers for
every client. Those numbers become the health score, the status badge and the
escalation bucket that a CSM acts on. The Next app rendered them with no
disclosure until the resweep, which is how a CSM ends up escalating on an
invented figure.

Porting the widget without porting the disclosure recreates that exactly, and it
will look like new work rather than a regression. Until per-client spend and
lead targets exist in the schema, the honest state is real-shaped numbers plus a
banner nobody can miss.

## Dev notes, the clients book is not legacy

Epic 3's six stories are Ready and `/csm-dashboard` is working code. Its absence
from the Next nav was a bug, fixed in 10.3, not evidence that the surface was
abandoned. This story ports a live feature.
