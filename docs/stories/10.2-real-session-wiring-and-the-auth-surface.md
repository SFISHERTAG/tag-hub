# Story 10.2 — Real session wiring and the auth surface

**Epic:** 10 — Angular migration
**Status:** In Progress

## Story

As someone signing in to the Hub, I want the Angular app to establish and carry a
real session, so that what I can see is decided by my actual roles rather than by
a hardcoded development stub.

## Context

10.1 left `RBAC_SERVICE` bound to `MockRbacService` in development and
`SignedOutRbacService` in production. Neither talks to a server, `app.routes.ts`
is still empty, and there is no HTTP surface for a browser to establish a session
against: today the Next app resolves everything by render, and the sign-in
exchange finishes in the browser using the Firebase Web SDK.

This story replaces all of that with endpoints, wires Angular to them, and ships
the first feature module.

The design pass for this story found several defects in code that already
shipped. They are listed under Findings because fixing them is part of the work,
not incidental to it.

## Decisions

Taken here, so an implementer does not rediscover them:

1. **One payload shape.** Every endpoint that resolves or changes a session
   returns the same `SessionPayload`, and the client **replaces the whole Session
   object, never merges**. `locations` is a derived function of `currentRole`
   (`lib/auth/session.ts:113-126`) and for `tag_exec` / `tag_csd` / `admin` it is
   the result of `listAllLocationIds()`. No browser-side expression can produce
   it, so a partial update desynchronises tenant access from the displayed hat.
2. **The custom token never reaches the browser.** It is a bearer credential for
   that uid. `otp/verify`, the Google callback and `refresh` all complete the
   exchange server-side and set the cookie themselves.
3. **Impersonation ordering is load-bearing.** The audit document is created
   before the cookie is set, because the cookie carries the Firestore auto-id
   that only exists once the document does, and because a crash between the two
   must leave a record with no access rather than access with no record. Exit is
   the mirror: close the entry before clearing the cookie.
4. **A hat switch closes any open impersonation first.** Both
   `lib/auth/session.ts:171` and `lib/auth/api-session.ts:87` gate the
   impersonation grant on `currentRole === ROLES.TAG_CSM`, so switching to any
   other hat leaves a live cookie and banner attached to a dead grant, with the
   audit entry never closing.
5. **Google identity matches on verified email**, not `sub`. `sub` is the more
   durable key, but nothing in this codebase stores it on the Firebase user
   record, so keying on it needs a backfill first. Gated on
   `payload.email_verified === true`. The hazard is recorded as a follow-up: a
   Workspace mailbox rename breaks that person's sign-in.
6. **An unprovisioned Google account is rejected**, matching what OTP already
   does at `app/api/auth/otp/request/route.ts:72`. Auto-provisioning would hand
   out a cookie to a user with no role grants, and `lib/auth/session.ts:104`
   returns null for exactly that, so they would sign in and immediately read as
   signed out.
7. **Google sign-in is config-gated, never silently permissive.** With no client
   id, the endpoint answers 503 and the button does not render. It never
   degrades to a permissive path.
8. **Coverage is allowed.** A CSM entering a peer's client is permitted, per the
   recorded three-tier rollup model where books roll up to CSD with
   cross-visibility for coverage. So `enter` gates on role and tenant-registry
   membership, not on the caller's own book.

## Findings fixed here

Defects in already-shipped code, surfaced by this story's design pass:

- **`POST /api/auth/refresh` threw in production.** It read
  `process.env.NEXT_PUBLIC_FIREBASE_API_KEY`. That is a `NEXT_PUBLIC_` name, so
  Next inlines it at build time, and `cloudbuild.yaml:24` defaults the
  `_FIREBASE_API_KEY` substitution to `""` while `--set-env-vars` on line 121
  never passes it. Nothing validated it. Shipped in 10.1; fixed by `lib/config.ts`.
- **No CSRF machinery existed anywhere.** No Origin check, no Sec-Fetch check,
  no token, on any route. With `hub_session` SameSite=lax the exposure is login
  CSRF: an attacker posts their own credential to a session-minting endpoint and
  the victim is silently signed in as them. `rejectCrossSite` now guards every
  such route.
- **`closeImpersonationEntry` validates nothing.** `lib/audit/store.ts:131-136`
  does a bare `.update()` on any document id under any location, checking neither
  the document's `action` nor its `actorId`, with both values arriving from the
  unsigned `hub_impersonation` cookie. httpOnly stops browser JS, not curl.
- **The OTP cooldown is resettable by the caller.** `lib/auth/otp.ts:59-72` only
  applies the 60s cooldown when the document exists, and `verifyCode` deletes
  that document on the too-many-attempts and expired branches. Burn five guesses
  and the next request issues immediately.
- **The OTP request response is an account-existence oracle.** The unknown-address
  path returns `{ok:true}` from the catch at line 72 before `issueCode` runs, so
  the cooldown body is only ever reachable for an address that has a user.
- **The OTP attempt cap has a read-modify-write race.** `lib/auth/otp.ts:98-122`
  reads a snapshot, gates on it, then writes; N parallel guesses all pass the
  gate. Needs a transaction, not an increment.

## Acceptance criteria

1. A user signs in with a 6-digit code end to end and lands on a guarded route.
2. Switching hats round-trips to the server and replaces the whole session;
   `locations` changes with the hat.
3. Entering and exiting a client tenant writes a correlated audit pair, in that
   order, and the banner survives a reload.
4. Signing out clears all three cookies and closes any open impersonation entry.
5. No route mints a session for a cross-site request.
6. With `GOOGLE_SIGNIN_CLIENT_ID` unset, the sign-in screen works and the Google
   button does not render.

## Dev notes

`provideAppInitializer` was verified against the installed Angular, not assumed:
it awaits returned promises via `Promise.all`, and the router's default
`initialNavigation` runs in an `APP_BOOTSTRAP_LISTENER` after `donePromise`
settles, so route activation genuinely does wait. This holds only while nobody
adds `withEnabledBlockingInitialNavigation()`, which registers a competing
initializer and navigates concurrently. Do not add it.

`POST /api/auth/role` is deliberately *not* placed under `/api/auth`.
`proxy.ts:19-23` exempts that whole prefix from the optimistic cookie gate, and
`web/src/app/core/interceptors/auth.interceptor.ts:26` skips the 401 refresh for
any URL containing `/api/auth/`, so a hat switch on an expired cookie would get a
hard 401 with no refresh attempt.

Adding `rejectCrossSite` to `refresh` broke the interceptor that calls it:
`http.post(url, null)` sends no Content-Type, because HttpClient only infers one
when it can, so the request 415'd. The interceptor now posts `{}`. Worth
remembering for every other endpoint the Angular side calls with no body.

## Dev notes, endpoints batch

`resolveSession(cookie, requestedRole)` was extracted from `getSession()`.
Without it the role endpoint had a privilege leak: it patched `currentRole` on
the session already in hand and returned it, so switching **down** from
`tag_exec` to a narrow hat kept the wide `locations` list. `Session` does not
expose `roleGrants`, so there was no way to re-derive locations correctly from
outside `session.ts`. Pinned by a test that switches down and asserts the list
narrows.

Adding `rejectCrossSite` to `POST /api/auth/otp/verify` broke the live Next
sign-in form, which is the correct outcome for a contract change under a live
UI. The form did the custom-token exchange in the browser; it now just navigates,
because the cookie is already set. `app/signin/signin-form.tsx` lost its
`firebase/auth` import in the process, which is a step toward the cutover commit.

`lib/config.ts` throwing at import broke the existing test suite, which is the
module working as intended. `vitest.config.mts` now supplies dummy values, the
same as any real environment would.

`docs/data-model.md` described an `otp` collection and a top-level `audit_log`.
Neither exists. The real names are `authCodes` and a per-location `auditLog`
subcollection. Corrected, along with the new `authCodeCooldowns`. Neither auth
collection has a TTL policy configured; noted there as a follow-up rather than
fixed here.

Signout deliberately has no cross-site check. Refusing to clear a session because
the request looked odd is the wrong failure direction for that one endpoint. It
also switched from a 307 to a 303, since a 307 preserves the method and would
re-POST to /signin.

## Dev notes, Angular batch

`app.routes.ts` is no longer empty. `/signin` is the first real route, lazy
loaded, and it is the one place `PUBLIC_ROUTE` is load-bearing rather than
convenient: under default-deny it would otherwise be refused, and authGuard
would redirect a signed-out visitor to the page they are already on.

**The initial bundle went from 430 kB to 485 kB against a 500 kB warn budget.**
The jump is the router's lazy-loading machinery, which was almost entirely
tree-shaken while `routes` was `[]`. Transfer size is 116 kB. Deliberately not
raising the budget to make room: the next feature module will cross it, and that
is the moment to decide between a considered budget and splitting the initial
chunk, rather than quietly moving the line now.

Two bugs in my own first draft, both caught by tests rather than review.
`backToEmail()` cleared the countdown timer but not the displayed number, so the
email step still read "Resend in 47s" against a countdown that had stopped. And
the interval leaked on destroy; it is now cleaned up through `DestroyRef`.

`provideNoopAnimations` is not used in the signin spec because
`@angular/animations` is not installed: Material 22 dropped that peer dependency.
Adding the package purely to satisfy a test provider would be the wrong
direction.

`locationAccessGuard` mirrors `requireLocationAccess`, and its spec exists mainly
to pin the CSM case. A CSM's static grant does not contain their book, so gating
purely on `session.locations` would deny every legitimate CSM and break Story
3.3 outright. Impersonation for that specific location is the grant.

Still open: the Google button and `POST /api/auth/google`, both gated on
`GOOGLE_SIGNIN_CLIENT_ID`, and the cutover deletion of `app/signin/*`. The
cutover waits until the Angular sign-in is actually serving, since deleting the
Next form before then leaves no way in.

## Dev notes, Google sign-in

Shipped whole, and inert until configured. `GOOGLE_SIGNIN_CLIENT_ID` is optional
in `lib/config.ts`; with it unset the Angular button is not rendered and
`POST /api/auth/google` answers 503 rather than 500 or, worse, a silent pass.
Filling the value in later is a config change with no code change.

**Wrapped, not reproduced.** `google-button.ts` owns the script, the container
and the lifecycle; Google owns every pixel inside it. There is no Material
styling on the button and the host is styled for layout only. `outline_dark` is
the single visual choice, and it is a value Google supplies for exactly this
case, since the app body is true black.

**The audience check is the load-bearing one.** `verifyIdToken` validates the
signature against Google's keys, but an ID token minted for any other Google
application is also correctly signed. Pinning `aud` to our own client id is what
stops such a token signing its bearer in as whoever the email matched. A test
asserts the exact argument.

Verified against current Google documentation rather than memory, because this
area has moved: `use_fedcm_for_prompt` is deprecated and ignored, so it is
deliberately absent from the local typings; `use_fedcm_for_button` still
defaults to false and is opted into explicitly; and the old `platform.js` /
`gapi.auth2` library is dead and unused.

**Matching on email, not `sub`.** Google's guidance is to key on `sub` because an
address can change, and that guidance is right. Nothing in this codebase stores
`sub` on the Firebase user record, so sub matching needs a backfill first. The
live hazard until then: a Workspace mailbox rename silently breaks that person's
Google sign-in. They can still use a code. The backfill belongs with the admin
work in 10.7.

**No auto-provisioning.** An unknown Google account gets 401, matching what OTP
does. An auto-created user would carry no role grants, so `resolveSession`
returns null and they would receive a cookie and then read as signed out.

Local typings for GIS rather than `@types/google.accounts`: strict TS forbids
`any`, the script loads from Google's CDN at runtime so nothing is bundled, and
this app uses four fields of a large API.

## Dev notes, Google sign-in configured

`GOOGLE_SIGNIN_CLIENT_ID` is set, so Google sign-in is live rather than inert.
The client is separate from the Drive Picker's, deliberately: the Picker uses a
sensitive scope, and sharing one client would drag sign-in into a verification
process it does not otherwise need.

The value lives in two places by necessity, not by duplication: the browser
initialises the GIS button with the copy baked into the Angular bundle, and the
server passes its own copy to `verifyIdToken` as the expected audience. If they
drift, every Google sign-in fails with a wrong-recipient error that reads like a
code bug. Check 5 in `scripts/check-story-status.mjs` now fails the commit on a
mismatch, verified against a deliberate drift.

Both empty stays a valid state, so the check does not fire on a deployment that
simply has Google sign-in switched off.

The client secret is deliberately absent from this repo. The Sign in with Google
flow does not use one: the browser receives an ID token and the server verifies
its signature against Google's public keys. If an authorization-code flow is ever
added, the secret belongs in Secret Manager and reaches the app through the
`--set-secrets` mechanism cloudbuild already uses, never in a file here.
