# Story 5.10 — Opportunity custom fields in the GHL client

**Epic:** 5 — Onboarding and campaign launch
**Status:** Draft
**Blocks:** 13.5. Land this first.
**Note:** 5.7/5.8/5.9 were superseded by 13.5; this story survived the
reconciliation unchanged because nothing in Epic 13 covers it. See
`docs/epic-5-13-reconciliation.md`.

## Story

As the Hub, I want to read and write custom fields on a GHL opportunity, so that
onboarding milestones can be recorded as dated facts on the record they belong
to.

## Context

`docs/fulfillment-pipeline-architecture.md` makes opportunity custom fields the
source of truth for onboarding state: each milestone is a date field, and the
seven Fulfillment stages are a rollup derived from which fields are populated.

Nothing in this codebase reads them. `lib/ghl/opportunities.ts`'s `Opportunity`
type carries id, name, pipeline, stage, status, value, and timestamps, and stops
there. Every story that depends on the new architecture depends on this one.

Sequence is 5.10, then 13.2, then 13.5.

## Acceptance criteria

1. `Opportunity` carries its custom fields, typed. A field is addressed by a
   stable key, never by the GHL-generated field id, which differs per
   sub-account and cannot be hardcoded across 40 tenants.
2. A resolver maps field key to per-location field id, cached the way
   `getPipelines()` caches (stage and field definitions change rarely). Cache
   miss falls through to a live lookup rather than failing.
3. Reads return a typed, parsed value. A date field yields a date or null. A
   malformed or unparseable value yields null and logs; it must not throw and
   must not silently become a valid-looking date.
4. Writes are typed and single-field. Writing one milestone must not clear the
   others, which is the standard failure mode of a full-object PUT against a
   partial payload.
5. Writing a date that is already set is a no-op, not an overwrite. A milestone
   records when something first happened; re-stamping it would destroy the only
   copy of that fact and quietly corrupt every duration derived from it.
6. A field absent from the location's field set is a typed, non-fatal result.
   During the migration some sub-accounts will have the folder and some will
   not, and a client mid-migration must not break the checklist.
7. All calls go through `lib/api/errorInterceptor.ts`. No catch-to-empty. Errors
   return a typed result or re-throw with context.
8. `lib/ghl/` only. No component or route touches custom fields directly; they
   go through the service layer like every other GHL call.

## Dev notes

**Verify the API before building on it.** Open question 2 in the architecture
doc: opportunity custom field support on `2021-07-28` is assumed, not confirmed.
That check is the first task, not the last. If it does not hold, the architecture
needs the contact record as a fallback carrier and this story changes shape.

**Field ids are per-location.** This is the trap. GHL generates a distinct id for
the same logical field in every sub-account, so anything hardcoded works in dev
and fails on client two. The key-to-id resolver exists solely for this, and it is
the same lesson `findStageIdByName()` already learned for stages.

**Do not add a write path for anything a workflow should own.** Per the
architecture doc, GHL workflows stamp fields from GHL-native events. This client
exists for the fields the backend must write because their source is external:
Meta state, Drive contents, A2P status.
