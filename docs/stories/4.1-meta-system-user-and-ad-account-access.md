## Notes

- **System User role:** Created as Employee, not Admin — Meta blocks Admin-role System User creation on Business Managers under 7 days old. Employee role is sufficient: it only needs asset-scoped API access (the assigned ad account and app), not Business Manager admin rights. See `docs/meta-live-launch-plan.md` Phase 2 for the full sequence, including the app-asset-assignment workaround via the Business Management API.
- **Token expiry:** first generation came back 60-day expiring; regenerated with the "Never" option and got a non-expiring token instead, confirmed via `debug_token` (`expires_at: 0`). Old token revoked. No refresh job needed.
- **Access tier risk:** Verify `ads_management` standard tier works for this account volume. If not, budget time for partner/premium access request.
- **Client onboarding:** Each new client must grant TAG partner access to their ad account — automate or document this as part of client onboarding workflow.
- **Conversion pixel state:** Before Epic 6 (acquisition loop) can safely send conversions, audit existing GHL integrations on each client pixel to prevent double-counting.

## Decision, 2026-08-25: pursue Full Access and App Review now

Sam's call. The alternative was accepting Limited Access and writing the
resulting ceiling into Epic 4 permanently.

**Why now rather than when Epic 4 needs it.** App Review runs on Meta's calendar,
not ours. Starting it costs little while other work continues; discovering the
ceiling later costs a rebuild of whatever was designed against Limited. The
clock is the scarce thing, so the clock starts.

**The contradiction with 4.2 is not a contradiction. Both are true about
different things.** 4.1 said "System User + token live"; 4.2 said "Meta
credentials not actually live". Read as competing claims about one fact, one has
to be false. They are not competing claims:

| Claim | Subject | True? |
| --- | --- | --- |
| 4.1: System User and token live | Meta Business Manager | **Yes.** Minted, non-expiring, `debug_token` verified, four client ad accounts reachable |
| 4.2: credentials not live | The running service's environment | **Yes.** `META_SYSTEM_USER_TOKEN` is not set on Cloud Run |

`app/api/meta/status/route.ts` conflates them in its own comment: "doesn't exist
yet" is accurate about the environment and misleading about Meta, and it is the
sentence that led one reader — me — to reverse this story's status on 2026-08-26
before reversing it back the same morning.

**The real gap is a deploy step nobody owns.** `cloudbuild.yaml` mounts five
secrets and `META_SYSTEM_USER_TOKEN` is not among them, and the deploy uses
`--set-env-vars`, which replaces the whole set, so setting it on the service by
hand is undone by the next build. Until it is added there, every Meta-dependent
story stays blocked on something neither its own work nor Meta's.

**The lesson worth keeping**, since it cost two reversals in one morning: code
can only observe its environment. A comment saying a credential "doesn't exist"
means it is not in `process.env`, never that it was not created. Those two
readings put a story's status in opposite states.
