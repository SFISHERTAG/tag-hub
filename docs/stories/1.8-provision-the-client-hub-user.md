# Story 1.8 — Provision the client's Hub user at Phase 1

**Epic:** 1 — Foundation and access
**Status:** Done

## Story

As a newly onboarded client, I want to be able to sign in to the Hub as soon as my account is
provisioned, so that the intake gate, the welcome tour and my dashboard are actually reachable.

## Context

Phase 1 cloned the GHL tenancy, created the Slack channel and Drive folder, opened the
Fulfillment opportunity and added the client's email to the OTP whitelist — but never created
a Firebase Auth user or set any custom claims. **No provisioned client could sign in.**

Two independent failures, both silent in their own way:

1. **No Auth user.** `app/api/auth/otp/verify` calls `getUserByEmail`, which throws
   `auth/user-not-found`. The client entered a correct code and was told
   "Could not verify that code."
2. **No claims.** Even with a user, `getSession()` returns null when a token carries no valid
   roles (`lib/auth/session.ts`) — so they would authenticate successfully into a blank product
   rather than an error.

The whitelist decides *who may request a code*. The Auth user is *who that code signs in as*.
Having only the first is what made this look configured while being unusable.

Provisioning has to do this, not first-sign-in, because the intake gate, the embedded form and
the tour all live **inside** the app (see `docs/ONBOARDING_INTAKE_WIZARD_BRIEF.md` §3f). Nothing
in that flow is reachable until the client can sign in.

## Acceptance criteria

1. Phase 1 creates the Firebase Auth user, or reuses it if the email already has one.
2. The user receives grants scoped to the tenancy just cloned, and to no other.
3. `client_owner` is first in the array.
4. No TAG-side or admin role is ever granted.
5. Re-running Phase 1 for the same client changes nothing (idempotent).
6. Provisioning a *second* tenancy for the same person is additive — no existing access is lost.
7. No password is created; sign-in stays OTP.
8. A valid code with no account behind it reports that distinctly, not as a bad code.

## Dev notes

**Why a functions-side auth module.** CLAUDE.md forbids Cloud Functions importing from `app/`,
and `lib/auth/admin.ts` is `server-only` besides. `functions/src/firestore.ts` exists for the
same reason. The cost is a duplicated claim shape, so `functions/src/auth.ts` carries an
explicit warning: it must stay identical to `setUserClaims`, because the app reads what this
writes and a divergence signs people out rather than failing loudly.

**Three things in the grant are load-bearing** and each is covered by its own test:
`client_owner` not `tag_exec` (which is cross-tenancy by construction and would show a client
every other client's numbers); `client_owner` first (with no hat cookie, the app falls back to
`availableRoles[0]`, so a reorder puts the founder in the setter view on their first ever
screen); and every grant naming this one location (an empty array is the all-tenancies
wildcard, not "none").

**Merge, not overwrite.** `mergeGrants` is pure and separately tested because this is where a
mistake removes access silently. A TAG staff member who is also an owner at a client, and
anyone provisioned for a second tenancy, are both real cases that overwriting would break.

**Scope is explicit** on each grant rather than left to the role-derived default in
`lib/dashboard/scope.ts` (Story 7.6), so intent is visible on the claim itself.
