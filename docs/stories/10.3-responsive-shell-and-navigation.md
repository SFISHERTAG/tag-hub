# Story 10.3 — Responsive shell and navigation

**Epic:** 10 — Angular migration
**Status:** In Progress

## Story

As any signed-in user, I want one shell that adapts to my screen rather than two
layouts that drift apart, and a navigation that cannot show me a link my route
guard will refuse.

## Context

CLAUDE.md requires "one responsive shell, not two separate layouts":
`mat-toolbar` + `mat-sidenav` at >=840px, `mat-toolbar` + bottom nav below it,
same component tree, breakpoint-driven.

Phase 2 built that shell, but built it as `app.ts`, the root component. That had
a cost nobody had measured until the initial bundle reached 486 kB against a
500 kB warn budget.

## Acceptance criteria

1. The root component imports nothing but `RouterOutlet`.
2. The shell loads lazily, behind `authGuard`, so a signed-out visitor never
   downloads it.
3. **Desktop (≥840px):** Sidenav is a collapsible drawer (hidden by default), toggled by a ☰ menu button in the toolbar. Content stretches full-width when drawer is closed. Matches Claude's sidebar UX.
4. **Mobile (<840px):** Bottom nav only. Sidenav does not appear.
5. Nav items derive from `PermissionService`, and no role sees a link its route
   guard denies.
6. `tag_csd` has a reachable nav set.

## Dev notes, the bundle split

Measured before cutting. `main.js` was 90 kB, and about 75 kB of that was shell
chrome: `list` 27.6 kB, `sidenav` 27.0 kB, `icon` 11.9 kB, `scrolling` 5.0 kB,
`toolbar` 3.5 kB. All of it downloaded by every visitor, including a signed-out
one whose only destination is `/signin`, a page that uses none of it.

Two further items were in the shared initial chunk for the same reason:
`@angular/forms` at 37.8 kB, used only by the sign-in form, and `button` at
28.5 kB, shared only because the root component also used it. Once the root
stopped importing Material, both followed their real consumers into lazy chunks.

Result: **initial 486.14 kB to 301.38 kB, transfer 116.32 kB to 81.27 kB.** The
shell is now an 81 kB lazy chunk that loads when there is a session to show it
to.

This is why `app.ts` must stay empty. Anything imported there is paid for on
first paint by everyone, forever, and the cost is invisible until someone runs
the numbers. `app.spec.ts` now asserts the root renders a router outlet and no
chrome, so the regression fails a test rather than quietly costing bytes.

The route structure carries the same reasoning: `/signin` sits outside the shell
because rendering it inside would mean downloading a toolbar and sidenav to show
a page that has neither. Feature modules become children of the shell route,
each with its own `permissionGuard`; the shell route itself requires only a
session, because every signed-in role sees the shell.

## Dev notes, navigation

`layout/nav/nav-items.ts` is the single source. One list, both presentations.
The side rail and the bottom bar render from it, which is what makes "one shell,
not two layouts" true rather than aspirational: there is no second list to
drift. A spec asserts the two renderings produce the same count.

`tag_csd` now has a nav set. In the Next app they matched zero entries, so a CS
Director signed in to an empty tab bar and the `team_health_rollup` widget built
for them was unreachable. A director sees the whole department, so they appear
anywhere a CSM does.

The permission rule these entries must obey: an item's list has to be a SUBSET
of what its route guard allows. Showing a link the guard refuses sends people
into a redirect; hiding one the guard permits makes a feature undiscoverable.
When feature routes land, `data.permission` and the entry here are set together.

## Dev notes, defects found by adversarial review

A ten-agent review of the Hot Path library proposal found three real defects in
this repo, all in code written the previous day and all confirmed by hand before
acting:

**`fail()` had diverged across the network boundary.** The server's is
`fail(context, cause: unknown)`; the client's was `fail(context, message,
status?)`. Same name, incompatible arity. The header comment claimed "same shape
on both sides", true of the types and false of the functions. Nobody noticed
because the client-side `fail` had zero callers. Removed it and corrected the
comment to say what is actually true: the types mirror, the constructors do not,
because `errorInterceptor` has already converted an `HttpErrorResponse` into an
`ApiError` before any caller sees one.

**The `*hasPermission` directive had never rendered.** Its only importer was its
own spec, and no template referenced it. It is now what gates every nav item, so
it has a real consumer in the shipped app rather than a test harness built for
it. Its usage example also showed bare role strings, which the pre-commit check
strips before matching and would therefore have been copied into real code.

**`permissionGuard`'s allow path still has not executed.** Zero routes declare
`data.permission`; the only textual match is a doc comment. Every real
invocation takes the PUBLIC_ROUTE early return or the deny branch, so the
permission check itself has never run in the application. Left open
deliberately: it needs a real permission-gated feature route, which arrives with
the first ported feature module, not before.

**Why the theme toggle is rejected, which is the part that matters most.**
`web/src/styles/_theme.scss` opens with: "TAG Cockpit is dark-only by design
(true black has no light-mode equivalent), so this file sets static values
rather than light-dark() pairs." There is no light theme to toggle to. The
control would ship three states of which one works.

This is recorded twice now because it was re-added within the hour of being
declined. If a light variant is ever wanted, `_theme.scss` says exactly how —
wrap each override in `light-dark()` — and the toggle is the last step of that
work rather than the first.

**Built: the impersonation banner** (`layout/impersonation-banner/`). It sits
above the sidenav container so it cannot scroll away; uses `tertiary-container`
rather than `error`, because this is a state to be aware of and not a fault; and
a failed exit surfaces the error *without* navigating, since a banner that
vanishes while the cookie survives states the opposite of the truth.

Note for whoever builds the collapsible drawer: the banner is deliberately
outside `mat-sidenav-container`. A drawer that overlays it, or a layout that
moves it inside, reintroduces the scroll-away problem.

**Built: app identity.** Title and manifest read `TAG Cockpit`, short name
`TAG`. The eight PWA icons under `web/public/icons/` are still Angular's
defaults and are the remaining half of this — they declare `purpose:
"maskable any"`, so they need a safe-zone inset rather than a plain resize.

**Already done, verified rather than assumed:** the nav-vs-guard reconciliation
and the empty-nav assertion both live in `app.routes.spec.ts`; the hat switcher
shipped in 10.9 with exactly the rule specified here.
