# Story 22.2 — Arming is not installing

**Epic:** 22 — The guard suite
**Status:** Draft — the hole is measured and named; no fix is designed yet
**Depends on:** none. Blocks nothing, and that is the problem.

## Story

As anyone relying on a guard, I want "is it armed" to be a checkable fact rather
than an assumption, so that a clone committing with every gate off is a state
something reports rather than a state nobody can see.

## Context

**`.githooks/pre-commit` is a source file, not the hook.** `npm run
hooks:install` copies it into `.git/hooks`, and that has to happen **per clone**.
So a guard can be correct, wired into `package.json`, green when invoked, present
in CI, and still not running for the person committing.

Three separate observations, all 2026-08-29/30:

- Adding a check to `.githooks/pre-commit` and committing immediately **did not
  run the new check**, because the installed copy was stale. The commit was
  allowed through by a hook that did not contain the rule that had just been
  added to its source.
- One clone's `.git/hooks/pre-commit` did not carry `check:story-parity` at all
  after that guard landed on `main`.
- A separate investigation found a container where `.git/hooks/pre-commit` did
  not exist — only samples — so **every gate was off and nothing said so**.

**`.git/hooks` is shared by every worktree in a clone.** Running the install from
one worktree arms every session in that clone at once, including sessions
mid-task. That is why arming is not simply "run it more often": it is a shared
mutable resource with no announcement.

## The hole, stated precisely

`main` can carry a guard that no clone is running, and there is no artefact
anywhere that would reveal it. CI catches the same class for anything wired into
the Contracts job — which is the argument for putting guards there rather than in
pre-commit — but pre-commit exists to fail fast, and a pre-commit that is
silently absent is worse than one that was never written, because it is trusted.

## Acceptance criteria (proposed, not agreed)

**AC1 —** a session can determine whether its clone's installed hook matches
`.githooks/pre-commit`, in one command, without modifying anything.

**AC2 —** a stale or absent installed hook is reported rather than assumed, and
the report names which checks are missing.

**AC3 —** whatever is built is itself validated by planting a stale hook and
observing the check fail, per standing order 2. **A check for arming that has
never been seen to fail is the same defect one level up**, and this story is the
easiest place in the repo to commit it.

**AC4 —** arming does not become a fourteenth thing to remember. If the answer is
a norm, the story has failed.

## Tasks

- [ ] Decide where the check lives: it cannot be the pre-commit hook itself
- [ ] Determine whether CI can meaningfully assert this, given a runner installs fresh
- [ ] Design for the shared-`.git/hooks` case, where arming affects live sessions
- [ ] Validate by planting a stale hook and watching it go red
- [ ] Decide whether a stale hook blocks or warns

## Why this is Draft rather than Ready

Nobody has designed the fix. The obvious answers are each unsatisfying: a
pre-commit self-check cannot fire when the hook is absent, and CI runs on a fresh
checkout where the question does not arise. **Writing the story now so the hole
has an owner is the point**, per §11 — work with no story cannot regress, and
this hole has been rediscovered three times in two days by sessions that each
thought they had found it first.
