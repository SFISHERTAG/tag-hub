# Story 11.6 — Resolve the courses store split

**Epic:** 11 — Migration readiness
**Status:** Ready — decision made 2026-08-22: **Option A, finish the move to Postgres**
**Depends on:** none. Blocks 10.7's `features/courses/` port.

## Story

As TAG, I want per-user course progress to live in exactly one store, so that
porting the courses feature does not carry a split-brain into Angular.

## Context

Found 2026-08-22 while checking whether the project is moving off Firestore. It
is not, but this one feature is half-migrated and has been sitting unresolved.

The state, verified against the code rather than the docs:

- **Structure** is on Postgres. `functions/sql/007_courses.sql` creates
  `courses` and `course_sections`; every `app/api/admin/courses/*` route reads
  and writes through `lib/course/db.ts`. Landed in `4638e98`.
- **Per-user progress** is on Firestore, through `lib/course/firestore.ts`, read
  by `app/api/courses/progress/route.ts` and `app/api/courses/[courseId]/route.ts`.
- A `course_progress` table exists in Postgres, created by
  `003_migrate_firestore_to_postgres.sql` line 258. **Nothing reads or writes it.**

One entity, two stores, one live and one an empty schema. That is the
split-brain condition CLAUDE.md says the pre-commit hook exists to block, sitting
in the tree already.

**Why it stalled, which matters more than the technical detail.**
`docs/data-model.md` recorded the blocker as "Decision pending: see
`docs/stories/X.X-courses.md`". That filename is a literal placeholder. No story
was ever created, no number assigned, no owner named. Nothing technical was in
the way. It was a to-do written inside a document, where no sprint would ever
surface it. This story exists so the decision has somewhere to be made.

## The decision

Exactly one of these. Both are small. Leaving it split is the only wrong answer.

**Option A — finish the migration.** Move progress writes to `course_progress`,
backfill existing Firestore progress, drop the Firestore read path.
Consistent with structure already being on Postgres, and makes cross-user
reporting (completion rates by client, by cohort) a query rather than a scan.

**Option B — revert progress to one store, Firestore.** Drop `course_progress`
from `003`. Progress is a per-user keyed write with no cross-entity joins, which
is the shape Firestore is documented as being for here, and the read path already
works. Cheaper, and leaves structure and progress deliberately split by
*purpose* rather than accidentally split by history.

**Decision, 2026-08-22: Option A.** Progress moves to Postgres and the Firestore
path goes. Recorded against Sam.

This went against the recommendation above, which was B. Noting that here rather
than quietly rewriting it, because the reason matters to whoever implements: B
was recommended only on the assumption that nobody needed aggregate progress
reporting. Choosing A means that assumption was wrong, so build for the query
that motivated it (completion rates across users, clients, or cohorts) rather
than porting the per-user read one-for-one and leaving the reporting for later.
If that query never materialises, this was the more expensive option for nothing.

## Acceptance criteria

1. Progress reads and writes go to `course_progress` in Postgres.
2. Existing Firestore progress is backfilled, and the backfill is **verified by
   count**, not by assumption. A backfill declared done without a count is the
   exact failure CLAUDE.md names.
3. The Firestore progress path in `lib/course/firestore.ts` is deleted, not left
   dormant. No code path can read progress from Firestore afterwards.
4. `course_progress` has its own GRANT. The blanket grant in `003` only covers
   tables existing when it ran, and a table without one works on a fresh deploy
   and fails on an existing database.
5. At least one aggregate query is built and used, since that is the reason this
   option was chosen over keeping Firestore.
6. `docs/data-model.md` reflects the outcome in the same commit.
