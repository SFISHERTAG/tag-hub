# Story 7.2 — Knowledge Base admin edit

**Epic:** 7 — Knowledge Base
**Status:** Ready

## Story

As an admin, I want to edit knowledge base content in the app, so that the manual can be kept current without hand-editing JSON and re-running a static site generator.

## Context

Depends on 7.1 (`manual_pages` Firestore collection and read routes must exist first). This story adds an admin-only editor, modeled on `app/admin/courses/[courseId]/course-editor.tsx` + `actions.ts` (paired `page.tsx` + editor client component + actions file) — but Firestore-only, not the `courses` Firestore/Postgres split-brain pattern (that pattern is flagged blocked in `docs/data-model.md` and must not be copied).

Edits are versioned, not overwritten in place, mirroring the `flow_audit_log` / `lib/audit/log.ts` pattern already used for FLOW scripts — every save records author + timestamp so an admin can view and revert history.

## Acceptance criteria

1. `app/admin/knowledge-base/[pageId]/page.tsx` + editor client component let an admin edit a manual page's title/eyebrow/lede/status/level/blocks.
2. Access gated via `hasAnyRole([ROLES.ADMIN])` — no inline role strings, no new roles added to `lib/auth/roles.ts`.
3. Every save writes a new version to a version sub-collection/fields (e.g. `manual_pages/{id}/versions/{versionId}`) with author uid, author name, timestamp, and the full prior content — modeled on `lib/audit/log.ts` — instead of overwriting `manual_pages/{id}` destructively. The live doc is updated to the new content; history is preserved and viewable.
4. Admin can view version history for a page and revert to a prior version (reverting itself creates a new version, it does not delete history).
5. Writes go through the shared error interceptor pattern (`lib/api/errorInterceptor.ts`) — no silent-catch-to-empty.
6. `docs/data-model.md` updated with the version sub-collection/fields for `manual_pages`.
7. `npm run build && npm run test --watch=false && npm run lint` all pass.

## Dev notes

**Version schema is a sub-collection, not an array field.** `manual_pages/{id}/versions/{versionId}`,
each a full `ManualPage` snapshot plus `authorUid`/`authorEmail`/`createdAt`.
An array field on the live doc would hit Firestore's 1MiB document limit
after enough edits and requires a read-modify-write race guard; a
sub-collection avoids both and is what `flow_audit_log` does in spirit
(separate append-only log, not embedded in the live row).

**What gets versioned, and when.** `lib/knowledge-base/db.ts#updateManualPage`
reads the *current* live doc, writes it as a new version, then writes `next`
as the new live content — both in one Firestore batch, so a version is never
recorded without the live doc actually changing (or vice versa). This means
a version captures what the content *was* right before this edit, not what
it became — reads as "here's what changed away from", which is what an
admin scanning history wants to see.

**Revert creates a new version, never deletes.** `revertManualPage` calls
`updateManualPage` with the target version's content, which itself records
the *current* (pre-revert) state as one more version first. History only
grows; nothing is ever destroyed by a revert.

**Blocks edited as raw JSON, not per-type fields.** See 7.1 Dev notes — six
block types with different shapes each. The editor's `JSON.parse` validates
before save and the read view (`ManualBlocks`) degrades a malformed/unknown
block to a raw dump rather than crashing, so a bad paste here is recoverable,
not destructive.

**Storage encoding fixed after 7.1's migration run exposed it.** Firestore
rejects an array nested directly inside an array; the manual's `table`
blocks carry `rows: string[][]`, which trips that. `lib/knowledge-base/db.ts`
now stores/reads `blocks` via `lib/knowledge-base/serialize.ts`'s
`toFields`/`fromFields` (JSON-encoded as `blocksJson`) instead of a native
array, for both the live doc and the version snapshots this story's editor
writes. Also fixed in the same pass: `revertManualPage` was casting a
version doc straight to `ManualPageVersion` without deserializing — this
editor's "Revert to this" button would have thrown on any table-block page.

**Not built:** a diff view between versions (history currently shows
title + author + timestamp per version, not a field-level diff). Left for a
follow-up if admins find "revert and re-diff" too coarse in practice.

## Post-implementation change: tenant-ownership gate (resweep critical group 1)

Files this story references were changed by a cross-cutting security fix, not
by further work on the story itself. Status is unchanged.

The full-codebase resweep found that server actions and route handlers here
accepted a caller-supplied tenant id (`locationId`, `orgId`, `clientId`)
without checking it against the caller's session — a role check alone does not
establish which tenant the caller belongs to. `lib/auth/session.ts` now owns
that check (`ownsLocation` and its `requireOwnedLocation` /
`requireOwnedClient` / `requireInternalRole` wrappers), and every action this
story touches calls through it. Behaviour for a correctly-scoped caller is
unchanged; an out-of-tenant caller now gets a typed 401/403 instead of the
other tenant's data.

## Post-implementation change: dashboard tenancy + widget allowlist (resweep criticals 2, 3)

Files this story references were changed by a cross-cutting security fix, not
by further work on the story itself. Status is unchanged.

Two changes touch this story's surface:

- The dashboard widget fetchers (`day-view`, `pipeline-board`, `roas`,
  `owner-calendar`, `funnel`) now take a `locationId` argument instead of
  resolving one from the global `GHL_LOCATION_ID` env var via
  `devLocationId()`. `app/dashboard/page.tsx` resolves it from the session
  through `resolveDashboardLocation` and access-checks it before fetching.
  Single-tenant behaviour is unchanged; multi-tenant behaviour is now correct.
- `availableFor` in the widget registry is enforced as a permission
  (`canUseWidget` / `filterWidgetsForRole`), rejected on layout save and
  filtered on read, rather than only filtering the customize picker.
