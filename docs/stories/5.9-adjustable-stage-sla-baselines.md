13.5 AC1 already requires thresholds to be admin-editable without a deploy, and

## Story

As a TAG exec, I want to adjust the per-stage SLA hours from the admin surface,
so that calibrating a threshold does not require a deploy.

## Context

5.7 ships baselines as config-as-code. That is the right default while the
numbers are unmeasured and every change wants a reviewer. It stops being right
once the numbers are being tuned against real data from 5.8, because the tuning
loop is short and a PR per adjustment is friction on exactly the work that makes
the instrument accurate.

This is the same shape as story 3.2's outstanding Phase 1.5 item, dynamic
CSM-configured health thresholds. If both land, they should share one settings
pattern rather than growing two.

**The baseline stays in code.** An override does not replace
`STAGE_SLA_HOURS`, it shadows it. Deleting an override returns that stage to the
committed baseline, so the config file remains a readable statement of intent
and there is always a defined value even with an empty override store. 5.7 AC2
already routes every read through `slaHoursFor(stage)`, so this story changes
one function body rather than every call site.

**Org-wide, not per client.** Per-client SLA is a plausible next want and is
deliberately excluded. It multiplies the surface, and there is no evidence yet
that stage durations vary by client rather than by stage. Revisit when 5.8 has
data showing they do.

## Acceptance criteria

1. Track SLAs are overridable on the same footing as stage SLAs. The A2P
   baselines are the ones most likely to need tuning, since they are guesses
   about an external carrier's turnaround, so an override mechanism that covered
   only stages would miss the main case.
2. Overrides persist in Firestore, not Postgres. This is configuration read on
   the request path, which is what `docs/data-model.md` says Firestore is for;
   `dashboard_configs` is the nearest existing precedent for the shape.
3. `slaHoursFor(stage)` resolves override first, committed baseline second. An
   absent override store, an unreachable Firestore, or a malformed value all
   fall through to the baseline rather than throwing or yielding no deadline.
   A stage SLA is not important enough to fail a checklist render over.
4. An override value is validated on write: positive integer hours, bounded to a
   sane ceiling. An explicit "no SLA" is expressible for a stage, distinct from
   "not overridden".
5. Admin UI under the existing admin feature module
   (`web/src/app/features/admin/`) lists each stage with its effective value,
   the committed baseline alongside it, and whether the effective value is an
   override. Clearing an override is a visible action, not a matter of blanking
   a field.
6. Write access is gated through `PermissionService` against an existing role.
   No new role string, no inline role literal in component or template, no
   change to `lib/auth/roles.ts` unless a genuinely new permission is needed, in
   which case that change lands in the same commit.
7. Every override write records who changed what, from what value to what value,
   and when. A threshold that silently moved is indistinguishable from a bug in
   the sweep.
8. 5.8's sweep reads through the same accessor, so an override takes effect on
   the next run with no redeploy. Changing an override does not retroactively
   resolve or open historical breach rows; it applies from the next sweep
   forward.
9. `docs/data-model.md` updated in the same commit for the new collection.

## Dev notes

**Do not build this before 5.8 has produced data.** The point of adjustability
is calibration, and there is nothing to calibrate against until the sweep has
run in observe-only mode for two to three weeks (5.7 Dev notes). Landing 5.9
first delivers a knob nobody knows how to turn.

**Cache with care.** The accessor is called on every checklist render and once
per tenant per sweep. Reading Firestore each time is wasteful and caching
forever means an override appears not to work. A short TTL is fine; whatever is
chosen, an admin who changes a value must see it reflected within a bounded and
stated interval, and that interval belongs in the admin UI copy.
