## Story

As a CSM, I want each onboarding stage to carry a deadline, so that I can tell
the difference between a client who is progressing and one who is stuck.

## Context

Story 5.1 shipped time-in-stage: the onboarding checklist reports `daysInStage`,
derived from the Fulfillment opportunity's `lastStageChangeAt` via `daysSince()`.
That answers "how long", and it does not answer "too long". A client parked in
PR2 for three weeks and one parked there for two days render the same way apart
from a number nobody has a threshold for.

This story adds the threshold. It is deliberately small, and it adds no new
store.

**The deadline is derived, not stored.**
`dueAt = stageEnteredAt + slaFor(stage)`. GHL stays the single source of truth.
Persisting a parallel copy of stage state would be exactly the split-brain
`docs/data-model.md` and the pre-commit hook exist to prevent, and it would buy
nothing: the input is already on every read path that needs the output.

**Where `stageEnteredAt` comes from, and why not `lastStageChangeAt`.** The
architecture doc replaces stage transitions with dated milestone custom fields,
because `lastStageChangeAt` only describes the stage an opportunity is in *now* —
the duration of every stage it has already left is unrecoverable. So a stage's
entry time is the milestone date that completed the previous stage, read from the
custom fields via 5.10, and `lastStageChangeAt` is a fallback for accounts that
have not been migrated to the field folder yet. Both paths must work during the
migration.

Consequently this story touches no Firestore collection, no Postgres table, and
no migration. Story 5.8 adds the one thing that genuinely needs persistence,
which is remembering that a breach was already escalated.

**Tracks are in scope, and they are the point.** The architecture doc models A2P
registration and the Meta ad account handoff as parallel tracks with their own
clocks, not as stages. A stage-only SLA cannot see them: a client can be
progressing through Build while A2P has been sitting untouched for a month, and
the stage clock reads healthy the whole time. This story therefore computes two
kinds of deadline, stage and track, from one function.

**Not in scope.** The GHL-side configuration — creating the field folder,
renaming the stages, building the rollup workflow — is agency configuration work
described in the architecture doc, not code, and it precedes this story.

## Acceptance criteria

1. A per-stage SLA baseline config exists in `lib/onboarding/stage-sla.ts`,
   keyed by `FulfillmentStage` (PR1–AP5), expressed in hours. Config-as-code,
   following the precedent of `lib/rules/configs/escalation.config.ts`. A stage
   with no configured SLA is valid and yields no deadline, rather than
   defaulting to an invented one. Baselines:

   | Stage | Whose move | Baseline | Rationale |
   | --- | --- | --- | --- |
   | PR1 | TAG | 72h (3d) | Access issuing and sub-account setup. Entirely TAG-side, no external dependency, should never sit. |
   | PR2 | Client | 120h (5d) | Waiting on the client to complete intake. The longest legitimate client-dependent wait, and chasing it earlier than five days reads as nagging. |
   | AP1 | TAG | 120h (5d) | Automations, funnel, VSL script. Real production work, and the largest genuine block of TAG effort in onboarding. |
   | AP2 | Client | 168h (7d) | Client produces VSL creative. Filming needs scheduling; a shorter clock would breach on every client who is simply booking a shoot. |
   | AP3 | TAG | 48h (2d) | Launch. Everything is built and approved, so this is execution. A funnel sitting built-but-dark is pure waste. |
   | AP4 | Client | none | First close is the client's sales motion on real leads. Outside TAG's control and not a queue. |
   | AP5 | Both | none | Steady state. A client can legitimately sit here for months; ascension timing is story 3.6's concern, not an SLA breach. |

   Track baselines, which run independently of stage:

   | Track | Baseline | Rationale |
   | --- | --- | --- |
   | A2P submitted | 120h (5d) from PR1 | Time to get registration details out of the client and filed. This is the clock that matters most: it starts on day one, gates AP3, and is the one thing that can be a month late while every stage clock reads green. |
   | A2P completed | 336h (14d) from submission | External carrier approval. TAG does not control it, so the SLA measures "chase it" rather than "do it". |
   | Meta partnered | 120h (5d) from PR2 | Client-side action in their Business Manager. Known long pole (5.1 AC2). |
   | Meta system user | 24h (1d) from partnered | TAG-side, one setting, immediately after the client's half lands. |

   These are instruments, not commitments. Nothing in TAG currently promises
   them; see Dev notes on calibration.
2. Every read of an SLA duration goes through one accessor,
   `slaHoursFor(stage)`, never a direct lookup into the config object. Story 5.9
   makes that accessor consult a stored override before falling back to the
   baseline; writing every caller through it now is what keeps 5.9 from being a
   refactor of every call site.
3. One pure function computes both kinds of deadline:
   `sla(startedAt, slaHours, now)` returns
   `{ slaHours, dueAt, hoursRemaining, state }` where `state` is
   `"on-track" | "due-soon" | "breached" | "none"`. `"due-soon"` is the final
   25% of the window. `"none"` covers an unconfigured SLA, an unparsed stage, or
   a missing start time. Stage and track differ only in what is passed as
   `startedAt` and which config supplies the hours; they must not become two
   implementations of the same arithmetic.
4. `GET /api/onboarding/checklist` extends its `state: "ready"` shape with
   `sla` for the current stage and `tracks: { key, label, sla }[]` for the open
   tracks. The three existing discriminated states are unchanged, and
   `daysInStage` stays where it is so no current reader breaks. A location with
   no custom field folder yet returns `tracks: []` rather than an error.
5. The Angular onboarding checklist
   (`web/src/app/features/onboarding/checklist/`) renders the stage deadline
   beside the stage, and the open tracks as their own row with their own
   deadlines. A breached track must be visible on a client whose stage is
   on-track, since that is the exact case the stage clock hides.
6. Colour comes from M3 system tokens only. No raw hex in any component `.scss`,
   no `!important`, no deep selectors. Breach state must be distinguishable
   without relying on colour alone, since colour-only status fails both
   accessibility and a phone screen in daylight.
7. The client-facing read is unchanged in permission terms: the checklist is
   already read-only for client users (5.1 AC5), and the SLA field inherits
   that. No new role string, no change to `lib/auth/roles.ts`.

## Dev notes

**Wall-clock, not business hours, for MVP.** A 72-hour SLA that starts Friday
afternoon breaches over the weekend. That is a real objection and the honest
answer is that business-hours arithmetic needs a holiday calendar and a timezone
per client, neither of which exists yet. Ship wall-clock, set the configured
durations with weekends in mind, and revisit if the false-breach rate is
actually a problem rather than a predicted one.

**Where the numbers come from, and what to do about it.** TAG has no stated
onboarding SLA today. Tracking has been a spreadsheet, so there is no historical
distribution to fit these to and no promise anyone is currently breaking. The
baselines in AC1 are reasoned from what each stage depends on, and they are
wrong in the specific sense that nobody has measured them yet.

That is a reason to ship them, not to withhold them. The instrument has to exist
before the distribution does. The recommended sequence:

1. Land 5.7 with these baselines. The checklist starts showing due dates.
2. Land 5.8 **with notifications off**. It opens and resolves breach rows and
   nobody gets pinged. Two to three weeks of that produces the first real
   picture of how long each stage actually takes.
3. Reset the baselines from that data, then turn notifications on.

Turning notifications on at step 1 would train everyone to ignore them, which is
the failure mode this story exists to avoid. Expect the first revision as
planned work, not as a correction.

Story 5.9 makes these adjustable without a deploy. Until it lands, adjusting a
baseline is a one-line PR, which is the correct cost while the numbers are still
being calibrated and every change wants a reviewer.

`daysInStage` and `sla.hoursRemaining` are computed from the same
`lastStageChangeAt`. Do not let them drift into two different derivations of the
same fact; if `daysSince()` changes, this changes with it.
