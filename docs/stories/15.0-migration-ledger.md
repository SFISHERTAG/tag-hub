# Story 15.0 — Migration ledger

**Epic:** 15 — No hats
**Status:** Review — implemented 2026-08-23. Migration `011` is written and **not yet applied** to the database (see Completion Notes).
**Depends on:** none. Blocks every later story in this epic that adds SQL.
**Plan:** `docs/ROLES_AND_GRANTS_PLAN.md`, sequenced by `docs/no-hats-sequence.md`

## Story

As whoever deploys this, I want to know which migrations have run, so that
applying the next one is not a guess.

## Context

There is no migration runner. `docs/RESWEEP_DEPLOY_RUNBOOK.md` says so outright
and `cloudbuild.yaml` has no SQL step: migrations are hand-applied through psql
and **nothing records what was applied**. Correctness depends on someone
remembering.

It has already failed. `006_rename_csm_directory_to_csm.sql` assumed it ran
before `003`, and failed on every clean sequential deploy with
`relation "csm" already exists`. It was rewritten as idempotent `DO` blocks,
which fixes that file and not the absence underneath it.

This epic adds two more migrations, and the Firestore exit
(`docs/firestore-exit-assessment.md`) adds one per collection. That is a pile
nobody is counting, growing.

**The critical finding this also closes.** `ROLES_AND_GRANTS_PLAN.md` §9 records
one finding as critical and explicitly not a design flaw: *the fixture enforcing
the grant-ordering fix runs in no gate.* A test that no pipeline executes is not
a test. `npm run check:functions` exists and is not wired into `cloudbuild.yaml`,
so nothing functions-side is verified before a deploy.

## Acceptance criteria

1. `functions/sql/011_schema_migrations.sql` creates a `schema_migrations`
   ledger: filename as primary key, applied-at timestamp, and a checksum of the
   file's contents.
2. The migration is idempotent and safe on a fresh database and on the live one,
   per the standing rule in `docs/data-model.md`. It carries its own `GRANT`;
   `003`'s blanket grant only covered tables existing when it ran.
3. `011` backfills rows for `001`–`010`, which are already applied in production.
   It must not claim a migration ran that did not: the backfill records the
   files present in `functions/sql/` at the time it runs, and the runbook states
   that this is an assertion about production rather than a discovery.
4. A checked-in script reports drift: which files exist on disk with no ledger
   row, and which ledger rows have a checksum that no longer matches the file.
   Read-only. It reports, it does not apply.
5. A checksum mismatch is reported as an error and not silently reconciled. A
   migration edited after being applied is exactly the condition this exists to
   surface.
6. `npm run check:functions` runs in `cloudbuild.yaml` before the image is
   built, so the functions-side gate is actually a gate. Closes the §10 finding.
7. `docs/data-model.md` documents the ledger in the same commit.
8. `docs/RESWEEP_DEPLOY_RUNBOOK.md`'s statement that nothing tracks applied
   migrations is corrected, since it will no longer be true.

## Dev notes

**Report, never auto-apply.** The temptation is a runner that applies what is
missing. Do not, in this story. There is no staging environment, migrations are
hand-applied against production today, and a runner that guesses wrong is worse
than a human with a list. The ledger makes the list trustworthy; automating the
apply is a separate decision with a separate blast radius.

**Checksums are the point, not the timestamps.** Knowing `006` ran is mildly
useful. Knowing `006` ran and has since been edited is what would have caught
the incident that motivated this.

**Confirm the number before writing.** `010` was free when
`docs/no-hats-sequence.md` was written and is taken by story 11.6. Check
`functions/sql/` first.


## Dev Agent Record

### Completion Notes

**Implemented 2026-08-23.** All eight acceptance criteria met in code. One thing
outstanding and stated plainly: **`011` has not been applied.** Migrations here
are hand-applied through psql and this one is no different. Until it runs,
`check:migrations` reports "No database reachable" and exits 0.

**The unverified category was not in the acceptance criteria and had to exist.**
AC3 says the backfill must not claim a migration ran that did not. Ten rows
assert history nothing can verify, so their checksum is NULL. Treating NULL as
agreement would let the ledger claim more than it knows; treating it as a
mismatch would make the check red on the day it ships for ten migrations that
are genuinely applied — and a check that is red on arrival gets muted. It is its
own reported category and does not fail the run.

**Read-only, deliberately.** A runner that applies what is missing is the
obvious next step. Not in this story: there is no staging environment, these
files go straight at production, and a runner that guesses wrong is worse than a
human with a trustworthy list. Automating the apply is a separate decision with
a separate blast radius.

**AC6 is the one worth flagging.** `npm run check:functions` existed and was run
by hand only, so nothing functions-side was verified before a deploy — the root
build is `next build`, which never compiles `functions/src`. That is the plan's
§10 critical finding, and it is why the fixture enforcing the grant-ordering fix
was running in no gate. It now runs in `cloudbuild.yaml` before the image is
built. Expect the first build to be slower by an `npm ci` in `functions/`.

**Migration number.** The re-cut predicted `011` and the story said to confirm
rather than trust it. Confirmed: `010` was taken by story 11.6 while the re-cut
was being written.
