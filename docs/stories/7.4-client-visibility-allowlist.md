# Story 7.4 — Client-visibility allowlist at the query layer

**Epic:** 7 — Command surface and configurability
**Status:** In progress — allowlist, catalog and picker landed; fetcher adoption waits on the
metric registry having fetchers in it

## Story

As TAG, I want client-facing surfaces to render from an explicit permit list, so that our own
margin cannot reach a client's screen through a forgotten conditional.

## Context

`docs/epics.md` states this is not optional and must not be deferred behind 7.3, and
`docs/client-fields.md` §2 gives the reasoning verbatim: *"A blocklist someone forgets to
update is how your management-fee margin lands on a client's screen. Enforce at the query
layer — a component that forgets a conditional is a bug; a query that cannot return the column
is not."*

This is the column-level twin of **Story 7.6** (data scope — whose rows). Same failure shape,
same remedy: make the unsafe call unrepresentable rather than discouraged. 7.6 brands
`ScopeFilter`; this brands `FieldAllowlist`.

**The catalog is parsed from the doc, never retyped.** 100 fields × 12 role columns is exactly
the transcription task where one mistyped dash is the leak. `scripts/parse-field-catalog.mjs`
reads the markdown tables, `scripts/gen-field-catalog.mjs` writes the TypeScript, and
`test/field-catalog-drift.test.ts` re-parses the doc on every CI run so the two cannot diverge.

## Acceptance criteria

1. Visibility comes from `docs/client-fields.md`, which stays the source of truth.
2. The allowlist cannot be constructed anywhere but `resolveFields`.
3. A field absent from a role's map is denied — the default is "no", never "yes".
4. A field id absent from the catalog entirely is denied.
5. `columnsFor` intersects requested fields with permitted ones; it never unions.
6. A forbidden field is dropped silently, not raised — an error would confirm the field exists.
7. `contract.mrr` and `econ.feeToSpendRatio` are unreachable by every client role.
8. Doc and generated catalog diverging fails CI.

## Dev notes

**The header count was stale because the parser was wrong.** The doc's header said "68
fields across 13 categories" and "41 of 68 ship without Story 4.1"; the section headings
summed to 91; the true figure is 100. The gap was a parse defect, not a doc defect. Column
positions were a fixed offset, which held for thirteen of the fourteen tables and silently
dropped all nine rows of §8, whose header carries an extra `Definition` column. Those rows
failed the mark lookup and hit a `continue`, so the catalog simply lacked them.

**The drift test could not have caught it.** It compares the generated catalog to the parser
that produced it, so the two agreed while both were short. The section headings are the only
counts a human wrote, so they are the only ones that can contradict the parser:
`assertSectionCounts` compares parsed-per-section to heading-declared-per-section, the
generator refuses to write when they disagree, and the drift test asserts the same. A row
that looks like a field row and does not parse now throws with a line number instead of
being skipped. In an allowlist, a quietly missing field is a blank dashboard nobody can
explain.

**Counts now consolidated, and now checked.** `docs/client-fields.md` reads 100 fields across
14 categories, 63 shipping against live integrations, 32 waiting on Story 4.1 and 5 on the
§7b Slack work. `docs/epics.md` carried the same stale pair and was corrected with it.

Correcting those numbers by hand would have left them free to rot again, which is how they
got 32 fields out of date in the first place. `assertHeaderTotals` parses the four totals out
of the doc's own prose and compares each to the tables: total fields, category count, fields
shipping today, and the split of the blocked remainder between Story 4.1 and §7b. The parser
now reads the `NOW` column and each section's number to do it. Both the generator and the
drift test run the check, so a stale total fails the build and CI, not a later reader.

A claim that has been reworded past recognition throws too. An unfindable claim and a
satisfied one are not the same result, and treating them alike is the failure this whole fix
exists to remove. Confirmed against three tampered copies of the doc: a wrong ship count, a
reworded header, and a wrong §7b split each fail with the specific number named.

**The picker consulted role and not fields, and the two disagreed.** `getAvailableWidgets`
filtered `WIDGET_REGISTRY` on `availableFor` alone, so a widget could be offered to a hat the
field catalog denies. It already was: `kpi_summary` renders `spend.actual`, `econ.roas` and
`funnel.cpl`, and the doc marks all three `never` for `client_manager` — only the owner sees
what the work costs. That widget is now offered to owner, exec and CSM.

Widgets therefore declare what they render. `WidgetDefinition.fields` is required rather than
optional, because an optional list makes "forgot to declare" mean "offered to everyone", which
is the forgotten-conditional failure this story exists to remove. `isOfferable` is the rule
(role owns the widget *and* the allowlist permits every declared field) and there is no
exported way to get the role-only list: a caller who wanted one is the caller about to hand a
client TAG's margin.

**A widget is dropped whole, never trimmed.** `client_manager` can see one of `kpi_summary`'s
four fields. Offering a KPI summary that is only booking rate would be worse than not offering
it, and partial offering is also how a field creeps back in later.

**Five roles had no column at all, and the picker is what exposed it.** `resolveFields`
returns an *empty* allowlist for a role absent from the doc, because AC3 makes absence mean
denial. That was invisible while nothing consulted it. `tag_csd` had three widgets, one of
them CSD-only, so a CS Director's dashboard would have emptied the moment the picker started
asking. `docs/client-fields.md` now carries `TCD`, `TSM`, `TST`, `CSM` and `CST` across all
100 rows.

The marks were seeded by mirroring the nearest existing role — TCD from CS, TSM from SM, TST
from SL, CSM from CM, CST from CL — which is an assumption about what those hats should see,
not a derivation. It is one column edit away from being changed, and the drift test will keep
it honest either way. `admin` deliberately has no column: it is Hub administration rather than
a client-data hat, and it reads through whichever hat it is wearing.

**The registry-driven tests could not prove the rule.** Once the four conflicts were fixed the
registry was internally consistent, so deleting the field check from `isOfferable` broke
nothing any test over `WIDGET_REGISTRY` could see. The cases that matter are the ones written
against a widget that does not exist: a margin widget marked available to an owner, and a
widget naming a field id nobody classified. Both are refused, and both fail when the check is
removed — confirmed by removing it.

**Two layers, deliberately.** `columnsFor` keeps forbidden columns out of the query;
`project` keeps them out of the response if a fetcher ever returns more than it asked for — a
join, a `SELECT *`, a Firestore document read whole. The epic argues for the query layer and
is right, but the projection costs nothing and covers the read-whole case that a column list
cannot.

**Silent drop, not throw** (AC6). Raising on a forbidden field turns any client-facing endpoint
into an oracle for which fields exist. Dropping is quieter and leaks nothing.

`unsafeAllowlistForTests` mirrors `unsafeScopeForTests` in scope.ts, named so it cannot be
mistaken for legitimate application code.
