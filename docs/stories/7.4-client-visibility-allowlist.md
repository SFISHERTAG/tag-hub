# Story 7.4 — Client-visibility allowlist at the query layer

**Epic:** 7 — Command surface and configurability
**Status:** In progress — allowlist and catalog landed, fetcher adoption outstanding

## Story

As TAG, I want client-facing surfaces to render from an explicit permit list, so that our own
margin cannot reach a client's screen through a forgotten conditional.

## Context

`docs/epics.md` states this is not optional and must not be deferred behind 7.3, and
`docs/client-fields.md` §2 gives the reasoning verbatim: *"A blocklist someone forgets to
update is how your management-fee margin lands on a client's screen. Enforce at the query
layer — a component that forgets a conditional is a bug; a query that cannot return the column
is not."*

This is the column-level twin of **Story 7.6** (data scope — whose rows). Same failure shape,
same remedy: make the unsafe call unrepresentable rather than discouraged. 7.6 brands
`ScopeFilter`; this brands `FieldAllowlist`.

**The catalog is parsed from the doc, never retyped.** 100 fields × 7 role columns is exactly
the transcription task where one mistyped dash is the leak. `scripts/parse-field-catalog.mjs`
reads the markdown tables, `scripts/gen-field-catalog.mjs` writes the TypeScript, and
`test/field-catalog-drift.test.ts` re-parses the doc on every CI run so the two cannot diverge.

## Acceptance criteria

1. Visibility comes from `docs/client-fields.md`, which stays the source of truth.
2. The allowlist cannot be constructed anywhere but `resolveFields`.
3. A field absent from a role's map is denied — the default is "no", never "yes".
4. A field id absent from the catalog entirely is denied.
5. `columnsFor` intersects requested fields with permitted ones; it never unions.
6. A forbidden field is dropped silently, not raised — an error would confirm the field exists.
7. `contract.mrr` and `econ.feeToSpendRatio` are unreachable by every client role.
8. Doc and generated catalog diverging fails CI.

## Dev notes

**The header count was stale because the parser was wrong.** The doc's header said "68
fields across 13 categories" and "41 of 68 ship without Story 4.1"; the section headings
summed to 91; the true figure is 100. The gap was a parse defect, not a doc defect. Column
positions were a fixed offset, which held for thirteen of the fourteen tables and silently
dropped all nine rows of §8, whose header carries an extra `Definition` column. Those rows
failed the mark lookup and hit a `continue`, so the catalog simply lacked them.

**The drift test could not have caught it.** It compares the generated catalog to the parser
that produced it, so the two agreed while both were short. The section headings are the only
counts a human wrote, so they are the only ones that can contradict the parser:
`assertSectionCounts` compares parsed-per-section to heading-declared-per-section, the
generator refuses to write when they disagree, and the drift test asserts the same. A row
that looks like a field row and does not parse now throws with a line number instead of
being skipped. In an allowlist, a quietly missing field is a blank dashboard nobody can
explain.

**Counts now consolidated.** `docs/client-fields.md` reads 100 fields across 14 categories,
63 shipping against live integrations, 32 waiting on Story 4.1 and 5 on the §7b Slack work.
`docs/epics.md` carried the same stale pair and was corrected with it.

**Two layers, deliberately.** `columnsFor` keeps forbidden columns out of the query;
`project` keeps them out of the response if a fetcher ever returns more than it asked for — a
join, a `SELECT *`, a Firestore document read whole. The epic argues for the query layer and
is right, but the projection costs nothing and covers the read-whole case that a column list
cannot.

**Silent drop, not throw** (AC6). Raising on a forbidden field turns any client-facing endpoint
into an oracle for which fields exist. Dropping is quieter and leaks nothing.

`unsafeAllowlistForTests` mirrors `unsafeScopeForTests` in scope.ts, named so it cannot be
mistaken for legitimate application code.
