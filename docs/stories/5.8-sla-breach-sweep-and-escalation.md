## Story

As a CSM lead, I want breached onboarding SLAs to raise their own hand on a
schedule, so that a stuck client surfaces without someone remembering to look.

## Context

Story 5.7 makes a breach computable. It only computes on read: if nobody opens
the checklist, nobody learns. This story adds the sweep that runs whether or not
anyone is looking, the record that stops it alerting on the same breach every
hour, and the wiring into the escalation surface that already exists.

**No inbound webhook.** The obvious design is a GHL workflow firing a webhook on
stage change. This story deliberately does not do that, for two reasons. Inbound
GHL webhook authentication is an open design decision carried over from the
resweep and is not settled; standing up an unauthenticated endpoint that writes
client state would be the wrong way to settle it. And a poll already has
everything it needs, because the Fulfillment opportunity carries
`lastStageChangeAt` and the sweep reads it directly. A webhook would make
detection faster and would not make it more correct. If sub-hourly detection
later matters, add the webhook then, as an optimisation on a working loop, once
the auth question has an answer.

**What persists, and why it does not conflict with the data model.**
`docs/data-model.md` is explicit that Firestore is the primary system of record
and Postgres is for computed views and logs. A breach record is a log: an
immutable observation that at time T, location L had been in stage S past its
deadline. It is not a second copy of stage state, which stays in GHL. The sweep
recomputes truth from GHL on every run and never reads its own table to decide
whether something is breached, only to decide whether it has already said so.

**Resolution is observed, not reported.** A breach is resolved when a later
sweep sees the milestone that ends that stage or track has been stamped. Nothing
has to tell us; the next poll notices. This is cleaner than it was under the old
stage model, because a dated field is a permanent fact rather than a value that
moves on.

**Tracks are swept alongside stages.** A2P is the case that justifies the whole
story: it starts at PR1, gates AP3, and can sit untouched for a month while the
stage clock reads green the entire time. A sweep that only watched stages would
be blind to precisely the stall it was built to catch.

## Acceptance criteria

1. Migration `functions/sql/008_sla_breaches.sql` creates `sla_breaches`:
   location id, fulfillment opportunity id, `subject_kind` (`stage` | `track`),
   `subject_key` (the stage code or track key), the start timestamp the breach
   was computed against, `due_at`, `first_observed_at`, `resolved_at`
   (nullable), and `notified_at` (nullable). A partial unique index on
   (location, opportunity, subject_kind, subject_key) where
   `resolved_at IS NULL`, so a re-run cannot open a duplicate and a stage and a
   track of the same name cannot collide.
2. `docs/data-model.md` is updated in the same commit with the new table, its
   source, and why it exists (log, not source of truth). Required by CLAUDE.md;
   the pre-commit hook enforces it.
3. `POST /api/cron/sla-sweep` authenticates with the `CRON_SECRET` bearer,
   mirroring `app/api/cron/meta-retry/route.ts` exactly. No user session, since
   Cloud Scheduler has none.
4. Each run: for every tenant in the registry, resolve the Fulfillment
   opportunity and its custom fields, compute stage and track deadlines via 5.7,
   then (a) open a breach row for any newly breached stage or track,
   (b) resolve any open row whose completing milestone is now stamped,
   (c) leave already-open, still-breached rows untouched.
5. The run is idempotent. Invoking it twice in succession produces the same
   table state as invoking it once, and sends no second notification.
6. A newly opened breach fires one notification via the existing Slack path used
   by 6.5's dead-letter escalation, and stamps `notified_at`. Notification
   failure must not roll back or block the sweep; it logs and continues.
7. A tenant with no custom field folder yet is skipped, counted, and not
   breached. Mid-migration accounts must not generate alerts for milestones that
   have nowhere to be recorded.
8. Per-tenant failure is isolated. One tenant whose GHL fetch fails does not
   abort the run for the other 39. The run returns a summary
   `{ scanned, skipped, opened, resolved, failed }`, and a non-empty `failed` is reported,
   never swallowed. All calls go through the error-handling contract in
   `lib/api/errorInterceptor.ts`: no catch-to-empty.
9. Open breaches feed the existing At Risk bucket in story 3.6 via
   `lib/rules/configs/escalation.config.ts`. No new escalation screen is built.
   3.6's Known Gaps list is updated, since this closes part of AC3's
   "under-flag, never over-flag" caveat.
10. No new role string. Reads reuse the portfolio/CSM permission path through
   `PermissionService`. `lib/auth/roles.ts` is unchanged.

## Dev notes

**Cadence.** Hourly, matching meta-retry. Onboarding SLAs are measured in days;
hourly detection is far finer than the thing being measured, and a tighter loop
buys nothing but GHL rate limit pressure across 40 tenants.

**Rate limits.** One Fulfillment opportunity fetch per tenant per run. At 40
tenants that is fine hourly. If the tenant count grows past a few hundred this
needs batching, and the summary counters are what will show it.

**Do not alert on migration.** Two populations make this acute. Accounts arriving
from the GHL consolidation (`docs/ghl-account-migration-checklist.md`) carry no
milestone history at all. And the existing 23 are being backfilled by a manual
pass, so their fields appear in whatever order a human works through them. Either
could open a wall of breaches for clients who are not stuck. Stamp the tenant's
registration time and suppress notification for breaches first observed inside
that window, while still opening the row. Combined with the observe-only rollout
in 5.7's notes, nothing should alert until the backfill is complete and the
numbers have been re-set from real data.

**Why the table is not in Firestore.** It is queried by ranges over time and
joined against client summaries for reporting. That is the stated reason
Postgres exists here. It is also append-mostly and non-authoritative, so losing
it costs one sweep interval of memory and nothing else.
