# Story 22.1 — Repo hygiene as an exit code

**Epic:** 22 — The guard suite
**Status:** Review — both rules validated red-then-green; not yet merged or armed in any clone
**Depends on:** none. 22.2 covers arming, which this story does not solve.

## Story

As whoever opens this repository next, I want the shape of the tree judged by a
program rather than by whoever happens to look, so that untidiness fails
automatically instead of accumulating until someone important notices.

## Context

`.DS_Store` was tracked on `main` while `.gitignore:29` ignored it. Nobody was
careless. Hygiene was the one property here with no durable owner: thirteen
guards, and not one looked at the shape of the tree.

**Why a person cannot own this.** In a corporate shop, hygiene is split three
ways — an engineering manager accountable for the standard existing, every
engineer responsible at review time via `CODEOWNERS`, and a platform team owning
the tooling that makes untidiness fail. All three assume durable humans.
**Sessions here are consumable by design**, and this repository has already
recorded four separate sessions agreeing to a rule and then breaking it,
including the session enforcing it. Standing order 8 is the conclusion: prefer a
mechanism to a norm, because norms degrade across session replacement.

## Acceptance criteria

**AC1 — a tracked file matching a `.gitignore` pattern fails the check.** Met.
`git ls-files --cached --ignored --exclude-standard` cannot report a merely
untracked file, so a hit is always real.

**AC2 — an undeclared top-level entry fails the check.** Met, via an explicit
`ROOT_ALLOWLIST` in the script. Adding a line is the intended cost.

**AC3 — the check reads the index, not the last commit.** Met, and it did not
start that way. See Dev notes.

**AC4 — each rule is observed failing on a case only it can catch.** Met. Rule 1
red on `main` naming `.DS_Store`, green after the untrack. Rule 2 red on a
planted root file, green on its removal.

**AC5 — the check is invoked from `package.json`, the pre-commit source, and
CI, in the same commit as the script.** Met. A guard wired into only some of
those is the inert-guard failure this repo hit two days running.

**AC6 — no rule makes an aesthetic judgement.** Met, deliberately. See the
omission below.

**AC7 — the guard is observed failing through the CI invocation path, not only
locally.** Met, and it was not met when this story was first written. Trap 5:
`main` already carries a scar where a guard passed seven tests and did not fire
in the hook, because the tests called it directly and `MERGE_HEAD` does not
exist there. Evidence, from the Contracts job log of run `33407636358` on
`b8f82bf`:

```
Contracts  Repo hygiene  ✗ 1 undeclared top-level entry:
Contracts  Repo hygiene      CI_PLANT_PROBE.md
Contracts  Repo hygiene  ##[error]Process completed with exit code 1.
```

The probe file was committed deliberately and removed in the following commit.

**That probe demonstrated story 22.2 by accident, which is the finding worth
more than the proof.** The probe commit passed the local pre-commit hook
untouched. `.githooks/pre-commit` carries `check:repo-hygiene`; the installed
`.git/hooks/pre-commit` did not, because arming is a manual per-clone `npm run
hooks:install` that had not been re-run since the check was added. **A guard can
be correct, wired, green in CI, and simply not running for the person
committing.** CI caught what the hook missed, which is the argument for putting
guards in CI rather than trusting pre-commit.

## Dev notes

**The plant found a defect before it shipped, which is the whole argument for
planting.** Rule 2 originally read `git ls-tree --name-only HEAD` — the last
*commit*. A newly staged root file was therefore invisible to it until after it
had landed: a guard that cannot see the change it exists to refuse. It was caught
by staging a scratch file at root and watching the rule stay green, not by
re-reading the code, which had looked correct.

**This is the same index-versus-tree defect already recorded against
`check-story-status`**, rediscovered independently in a new script the same week.
That is a pattern worth naming rather than a coincidence: a check written against
the repository will reach for `HEAD` because that is what a repository *is*,
while the thing being judged lives in the index.

**One rule was designed and dropped.** A third rule would have flagged a
directory holding a single file beside a sibling holding the rest, aimed at
`sql/flow-schema.sql` against eleven migrations in `functions/sql/`. It is a
heuristic. A heuristic in a blocking guard produces false positives, a guard with
false positives gets bypassed, and the habit of bypassing is then carried to the
guard that mattered. That singleton is a human judgement, made once, and it is
still unmade.

## Review findings, 2026-08-31

An independent session reviewed this before it merged, per standing order 9. It
was the first guard here whose author was also its only reviewer, and Sam
stopped the merge for that reason. Three of its four findings changed the code.

**REQUIRED — rule 1 was machine-local, and its advice deleted real files.**
`--exclude-standard` reads three sources: `.gitignore`, the untracked
`.git/info/exclude`, and the committer's global `core.excludesFile`. **Two of
those are machine-local**, so the guard was not the same guard on two machines —
a personal global ignore entry became a repo rule for one person, red on their
laptop and green in CI. Worse, the failure text asserted "matched by
`.gitignore`" and advised `git rm --cached`; under the wrong source that sentence
was false and the advice **untracked a file that legitimately belonged in the
repo**, after which the guard went green because the content was gone. Verified
independently before the fix: a tracked `keep.ts` placed in `.git/info/exclude`
produced a hit against a `.gitignore` that said nothing about it. Replaced with
`--exclude-per-directory=.gitignore` and `core.excludesFile=/dev/null`; verified
that both leaks close and a force-added `node_modules/` path still fails.

**Rule 2 was scoped to the working directory.** `execFileSync` inherits the
process cwd, so running the script from `docs/` reported the contents of `docs/`
as undeclared *root* entries — a confident, specific, fabricated failure list.
Neither real invocation path was affected (git runs hooks at the top level,
Actions runs at the repo root), but a session diagnosing by hand was. Both git
calls now run at `git rev-parse --show-toplevel`.

**A non-ASCII root name printed as escaped octal.** The rule was right and the
message unreadable at the moment someone needed it. `core.quotepath=false`.

**The green-should-fail case, demonstrated rather than argued.** Stage a stray
root file and add its name to `ROOT_ALLOWLIST` in the same commit: exit 0. The
reviewer's judgement was that this is a review-surface problem rather than a
logic bug, and that the fix is to make the amendment loud rather than to change
the rule — a guard cannot tell a legitimate new root entry from an illegitimate
one, which is the judgement the allowlist exists to force. Named explicitly in
the script's header so a reviewer has a word for it.

**One attack the reviewer withdrew against its own line.** The comparison to
`check-story-status-parity`'s hardcoded vocabulary does not hold: that list
drifted because the truth lived elsewhere, and here the list *is* the
declaration. It also checked, rather than assumed, that the allowlist has no dead
entries — at `05c17eb` the tracked root is exactly the allowlist plus
`.DS_Store`, which this branch untracks.

## Second review, 2026-08-31 — refused, and the refusal was right

A second independent session refused the first fix. It reproduced two cases that
reintroduced the original defect; both reproduced again here before anything
changed.

**`--exclude-per-directory=.gitignore` reads the working tree, not committed
state.** It closed the machine-local config sources and opened two more:

- **F.** An *untracked* `feat/.gitignore` containing `thing.ts` → `feat/thing.ts`
  reported as ignored. Exists on one machine.
- **G.** A *tracked* `.gitignore` with uncommitted edits adding `keep.ts` →
  `keep.ts` reported. Fires inside a pre-commit run, before the rule it is
  reading has landed.

Under both, the message still said "matched by `.gitignore`" — technically true,
materially false — and still advised `git rm --cached`, which untracks real work
and then goes green because the content is gone. **Verbatim the failure the
previous commit claimed to have eliminated, through a path it did not consider.**

**The lesson is the shape, not the flag.** Two attempts to reach "ignored by
committed repo state" by *enumerating ignore sources* both failed, and the second
failed dangerously. The rule now **attributes** instead: `git check-ignore -v
--no-index` names the file and line that ignored the path, and a hit counts only
if that source is itself tracked and unmodified. **Source-agnostic by
construction** — a source nobody has thought of still has to be committed to
count, so the enumeration cannot be incomplete again.

Hits from uncommitted sources are reported under a separate heading with the
**opposite** remediation: fix your local ignore rule, and explicitly do not run
`git rm --cached`.

**`--no-index` is required and its absence was silent.** `check-ignore` skips
tracked paths by default, and every candidate here is tracked, so without it the
command exits 1 on all of them and the `catch` reclassified every genuine hit as
"unreadable source". Found by testing a tracked nested `.gitignore` that should
have been a committed hit and came back local-only — **a case that would have
looked like the guard working**.

Verified after the rewrite, all four in a synthetic repo: tracked nested
`.gitignore` → committed hit; `.git/info/exclude`, untracked `feat/.gitignore`
and dirty `.gitignore` → local-only, safe advice.

**Outside a repository** the script died with git's fatal plus a Node stack. It
failed closed, so CI was never at risk, but a guard arguing that its output is
trustworthy should not answer with a stack trace. One line and exit 1 now.

## The failure mode of this rule, named after four rounds

**Four review passes, four defects, and every one ran the same direction: a
genuinely committed hit quietly reclassified as somebody's local problem, filed
under a heading whose remediation argues against fixing it.**

- Pass 1: `--exclude-standard` read machine-local config, so the message lied and
  `git rm --cached` would have deleted real work.
- Pass 2: `--exclude-per-directory` read the working tree, so an untracked or
  dirty `.gitignore` did the same.
- Pass 3: `check-ignore -v` output parsed by splitting on `:`, so a directory
  named `we:ird` made the source unresolvable and the hit local-only.
- Pass 4: a leading `:` is pathspec magic, so `:magic/` made check-ignore exit 1
  with **empty stdout and empty stderr** — identical to "not ignored" — and the
  catch took the safe direction.

**This rule's failure mode is not false alarms. It is silent forgiveness.** Every
defect was found by asking *what would the guard say about a file it should have
flagged*, never by checking that it leaves good files alone. **That is the
question to ask of the next guard**, and it is the opposite of the instinct a
blocking check invites, which is to worry about false positives.

The fix in each case was one line. **The pattern is the finding.**
