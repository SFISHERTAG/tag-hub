# Story 10.9 — User menu and sign-out

**Epic:** 10 — Angular migration
**Status:** Review — implemented 2026-08-23.

## Story

As a signed-in user, I want a menu on my account, so that I can sign out —
which is currently impossible from inside the product.

## Context

**There is no way to sign out.** `AuthService.signOut()` exists and posts to
`/api/auth/signout`; nothing calls it. No button, no menu, no link. The only
exits are clearing cookies by hand or a `fetch` from a console. This is not the
minimalism pattern of hiding an affordance at opacity 0 — the affordance was
never built.

It matters more than it looks. Custom claims are baked into the session cookie
when it is minted, so a grant change is invisible until the user signs out and
back in. Without sign-out, an admin can change someone's access and the person
has no way to pick it up.

**Report a bug moves here.** `nav-items.ts` already says so: *"Last on purpose.
It is a utility rather than a destination, and it is the obvious first candidate
to move into a bottom-nav overflow sheet when one lands."* A menu is that
overflow, and it shortens a nav bar that runs to ten entries for a `tag_exec`.

**Settings needs somewhere to go.** There is no `/settings` route. `nav-items.ts`
is explicit that shipping a link its guard refuses "sends people into a
redirect", so this story builds a minimal page rather than an inert item: the
signed-in address and the roles actually granted. That second part is not
padding — the roles a session holds were unreadable from inside the product, and
not knowing them cost real time this week.

**A hat switcher, deliberately temporary.** Reversed 2026-08-23 at Sam's
request, and the reversal is sound: he holds thirteen grants, lands on `admin`
which has no widgets by design, and a console `fetch` is not a way to walk a
product. The switcher makes the smoke walk possible now.

It is throwaway and is labelled as such in the code. Epic 15 removes the
active-role concept, and 15.D deletes `switchRole`, `POST /api/session/role` and
this control together. Building it means one more thing for 15.D to remove, and
that is the accepted cost — 15.D already carries that deletion because 15.A
deferred it.

## Acceptance criteria

1. An account control in the toolbar opens a menu, on both the wide and narrow
   layouts. One shell, one control, no second implementation.
2. The menu shows the signed-in email address as a non-interactive header.
3. Items: the hat switcher, Settings, Report a bug, Log out. Log out is
   separated from the rest, since it is the destructive one.
3a. The switcher lists only roles in `session.availableRoles`, marks the current
   one, and switches through the existing `RbacService.switchRole`. It carries a
   comment naming 15.D as the story that deletes it. It renders nothing when the
   user holds a single grant, which is every real user today.
4. Log out calls `AuthService.signOut()` and lands on `/signin`. A failed
   sign-out surfaces an error rather than pretending it worked; a user who
   believes they signed out and did not is the worst outcome here.
5. Report a bug routes to `/bug-reports` and is **removed** from `NAV_ITEMS`, so
   it appears in exactly one place.
6. `/settings` exists, is guarded like any other route, and shows the address
   and the granted roles.
7. Angular Material only. `mat-menu`, `mat-icon-button`. Colour from M3 tokens;
   no raw hex in any component `.scss`, no `!important`, no `::ng-deep`.
8. Standalone, `OnPush`, `inject()`, new control flow.
9. Keyboard reachable and screen-reader labelled. A menu that only opens on a
   mouse is not a replacement for a missing button.

## Dev notes

**Sign-out must not fail silently.** `POST /api/auth/signout` needs the Origin
header, which `fetch` sends automatically from the page — but the CSRF guard
refuses anything else with a 403, and that 403 is easy to swallow. If the call
fails the menu says so and the user stays where they are.

**The hat switcher is temporary and must stay easy to delete.** Keep it in its
own block in the template and its own method on the component, so 15.D removes a
contiguous piece rather than untangling it. It is the one part of this story
with a known expiry.


## Dev Agent Record

### Completion Notes

**Implemented 2026-08-23.** The product can be signed out of for the first time.

**The architecture boundary changed the design, correctly.** The obvious build
was `UserMenu` injecting `AuthService.signOut()`. eslint refused it:
`layout/` must not import `features/`, per CLAUDE.md's isolation rule and the
`no-restricted-imports` zones. That is not an obstacle to work around — signing
out is a *session* operation, and `RbacService` in `core/` is already the
session authority the layout injects. `signOut()` moved onto that contract and
its three implementations. Better placement than the one I started with, found
by the linter rather than by me.

**Sign-out fails loudly.** `POST /api/auth/signout` sits behind the CSRF origin
guard, which answers 403 to anything without a matching Origin. The
implementation clears the local session only after the server accepts, and the
menu surfaces the failure without navigating. Someone shown a signed-out screen
while their cookie is intact is the worst outcome available here.

**Report a bug moved, it did not get duplicated.** `nav-items.ts` had already
predicted this: "the obvious first candidate to move into a bottom-nav overflow
sheet when one lands". The route and guard are untouched. Its own doc comment
counted `tag_csd`'s entries as six, so that is now five.

**Settings is thin but not fake.** `nav-items.ts` is explicit that a link its
guard refuses "sends people into a redirect", so Settings needed a real
destination. It shows the address and the granted roles — and the roles half
earns its place: what a session actually holds was unreadable from inside the
product, and finding out required the Admin SDK. That cost real time twice this
week.

**The hat switcher is temporary and marked as such** in the component, the
template, the spec and this story — 15.D deletes it with `switchRole` and
`POST /api/session/role`. It renders nothing for a single-grant user, which is
every real user today. Reversed into scope at Sam's request after being decided
against; the reversal is right, because a console `fetch` is not a way to walk a
product.
