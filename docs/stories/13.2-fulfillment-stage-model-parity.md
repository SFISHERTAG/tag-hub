# Story 13.2 — Fulfillment stage model parity

**Epic:** 13 — Lifecycle handoff and churn prevention
**Status:** Draft — original premise superseded, scope reduced 2026-08-22
**Depends on:** none

## Story

As a client in onboarding, I want every stage of the real pipeline to be a stage
the app understands, so that my checklist does not silently disappear.

## What changed, and why this story shrank

The original version of this story described an 11-stage pipeline containing
`New Client`, `Onboarding Call`, `PR 3 - VSL Creatives` and
`PR 4 - Creative Edits`, and asked for `FULFILLMENT_STAGE_ORDER` to be extended
to match. That was accurate when it was written on 2026-08-21.

GHL rebuilt the Fulfillment pipeline on 2026-08-22 at 11:29. None of those
stages exist. Acting on the original acceptance criteria would now add eleven
dead stages to working code.

Verified on the board 2026-08-22, the live pipeline is 12 stages:
`Onboarding Booked · Onboarding Complete · Tech Stack Provisioned ·
Intake Complete · Creative Copy Complete · Creatives Compete · Editing Complete ·
Campaign Launched · First Appointment Booked · 1st Deal Closed · Ascension ·
Offboarded`.

The parity work itself has already landed:

- Commit `2787e21` mapped all 12 live stages, kept the old PR/AP codes for
  existing data, and updated `AP2_STAGE_NAME` to `"Campaign Launched"`.
- `lib/onboarding/stage-tasks.test.ts` pins the live stage list verbatim,
  GHL's `Creatives Compete` typo included, so the next rename fails a test
  rather than a client's checklist. Confirmed to bite: reverting the parser to
  its pre-fix form turns 14 of those assertions red.

Two of the original acceptance criteria were **not** covered by that fix, and
they are what remains of this story.

## Acceptance criteria

1. "No tasks defined for this stage" and "I do not recognise this stage" are
   distinguishable at every call site. Today both surface as an empty checklist,
   which is why the original defect went unreported: a client at an unmodelled
   stage looked identical to a client with nothing to do.
2. Stage ordering derives from GHL's `position`, not from the stage code. The
   old pipeline interleaved `AP 1` between `PR 1` and `PR 2`, so any code
   inferring order from the code prefix was already wrong, and nothing prevents
   the new pipeline being reordered tomorrow.
3. `FULFILLMENT_STAGE_ORDER` stays in board order and the test that pins it
   stays green.
4. Task lists exist, or are recorded as intentionally empty, for the stages that
   currently have none. An intentionally empty list is a decision; a missing one
   is a bug, and AC1 depends on being able to tell them apart.

## Tasks

- [ ] Separate "no tasks" from "unrecognized stage" at the call sites
- [ ] Derive ordering from GHL `position` rather than the stage code
- [ ] Define or explicitly empty the task lists for the stages that have none
- [ ] Extend `lib/onboarding/stage-tasks.test.ts` for the two new distinctions
- [ ] Gate: `npm run test`, `npm run lint`, `tsc --noEmit`
