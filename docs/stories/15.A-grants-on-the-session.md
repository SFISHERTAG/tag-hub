# Story 15.A — Grants on the session

**Epic:** 15 — No hats
**Status:** Review — implemented 2026-08-23. AC5 and AC6 deferred to 15.D with reasons recorded inline.
**Depends on:** 15.0
**Blocks:** 15.A2, 15.C, 15.F
**Plan:** `docs/ROLES_AND_GRANTS_PLAN.md` · sequence `docs/no-hats-sequence.md`

## Story

As the codebase, I want the full set of a person's grants on the session, so
that later stories can stop asking which single hat they are wearing.

## Context

This is deliberately the boring story. It is **additive**: `currentRole`,
`availableRoles` and `locations` all stay exactly as they are, and every existing
reader keeps working. Nothing observable changes for a signed-in user.

That is the plan's own sequencing rule, and it is there because the alternative
failed review:

> `currentRole` is deleted last, not first. Story A adds `grants` beside it;
> each story removes readers; by the end its deletion is a pure removal.
> Deleting it first is a ~30-site rewrite and is the shape that failed review.

Three things this story does.

**1. `Session.grants`.** `parseRoleGrants` already builds the full array and
`resolveSession` already throws all but one entry away. The array is simply kept.

**2. `GLOBAL_ROLES` in one place.** `[TAG_EXEC, TAG_CSD, ADMIN]` is currently
written out three times: `session.ts:205-207`, `session.ts:296-298`, and
`api-session.ts:78-80`. Byte-equivalent, and three chances to add a fourth global
role in two of them. This is also the constant that makes §4's "global reach
comes from the role, not the claim" enforceable, so it has to exist before 15.F
can reject a blank locations list.

**3. Delete the dead switcher.** `switchRole` lives in the `RbacService`
interface, its three implementations and their specs, plus
`POST /api/session/role` — and is called by **no component**. Verified again
2026-08-23: `web/src/app/layout/shell/` has no reference. It is not a feature
that is switched off, it is a feature that was never wired up, and leaving it
implies an escape hatch that does not exist. Its presence is why the live bug
reads as a UI gap rather than a model problem.

**Reduced `SessionPayload`.** The payload crossing to the browser drops
`availableRoles`. Nothing renders it — there is no picker — and shipping a list
of roles the user cannot select is a claim the UI cannot honour.

## Acceptance criteria

1. `Session` carries `grants: RoleGrant[]`, the full parsed array, alongside the
   existing `currentRole`, `availableRoles`, `locations` and `scope`.
2. Every existing field keeps its current meaning and value. This story changes
   no authorization decision; a diff of resolved sessions before and after is
   identical but for the added field.
3. `GLOBAL_ROLES` is exported from `lib/auth/grants.ts` and the three hardcoded
   triples reference it. No behaviour change: the constant is byte-equivalent to
   what each site spells out today.
4. `isGlobalRole(role)` is the only way the check is written afterwards. A grep
   for `TAG_EXEC ||` finds nothing outside `grants.ts`.
5. ~~`switchRole` is deleted from the `RbacService` interface, all three
   implementations, and their specs. `POST /api/session/role` and its route file
   are deleted.~~ **Deferred to 15.D, 2026-08-23.**

   The plan calls the switcher dead, and it is — from the UI. It is not dead
   from a console, and that is currently the only way anyone can change hat.
   Sam is pinned to `admin`, which is deliberately without widgets, and
   `POST /api/session/role` is the escape. Deleting it in this story would
   remove the workaround four stories before 15.D removes the need for one.

   It goes in 15.D, where the live bug is fixed and there is nothing left to
   escape from. Recording the deviation rather than quietly reordering: the plan
   put this in A on the reasoning that it has no caller, and that reasoning was
   correct about components and wrong about people.
6. ~~`SessionPayload` no longer carries `availableRoles`.~~ **Deferred to 15.D
   with AC5.** It is the same change: `switchRole` validates against
   `availableRoles`, so dropping the field while keeping the switcher breaks the
   mock and the endpoint's own check. The two move together or not at all.

   The upside is that 15.A ends up exactly as the plan described it — purely
   additive, no reader changed, nothing observable.
7. No new error type. `GrantValidationError` already exists in `lib/auth/grants.ts`
   and is the one used, per the plan's finding that the admin work must not
   invent a second.
8. A signed-in user notices nothing. Verified by signing in against the deployed
   revision after merge, not by reasoning about it.

## Dev notes

**The live bug is not fixed here and must not be.** A founder still reaches one
of five grants after this story. That is 15.D. Fixing reachability now, before
15.B has made every tenant-scoped gate location-aware, is precisely the ordering
the plan warns produced a cross-tenant write escalation in an earlier attempt.

**Deleting the switcher looks like removing the fix.** It is the opposite. There
is no picker, so the endpoint is unreachable; the model this epic moves to has no
active role for a picker to set. Anything needing a temporary way to change hats
should use the endpoint before this story lands, not after.

**Do not touch the claim shape.** §4 of the plan: retyping `locations` makes
`parseRoleGrants` drop every entry, `resolveSession` returns null, and every gate
reads that as signed out. A rollback would sign out every migrated user. Same
keys, same types.


## Dev Agent Record

### Completion Notes

**Implemented 2026-08-23.** Purely additive, as intended: no authorization
decision changes, and a resolved session differs only by the new `grants` field.

**The plan undercounted the inline triples.** It named three —
`session.ts:205`, `session.ts:296`, `api-session.ts:78`. There were four: the
Angular `location-access.guard.ts` carries its own copy, with a comment saying
it mirrors the server and the two must change together. The plan missed it
because it searched server-side. The Angular half cannot import
`lib/auth/grants.ts`, so `GLOBAL_ROLES` and `isGlobalRole` are mirrored in
`web/src/app/core/models/role.model.ts`, and both now say so in a comment.

**The equivalence test compares against the old predicate, not the new list.**
Re-listing the same three names would agree with a typo. `asWrittenBefore()` is
the check exactly as the call sites wrote it, run against all 13 roles.

**Two acceptance criteria deferred, and the reason matters more than the
deferral.** AC5 deletes the hat switcher on the grounds that no component calls
it. That is true and incomplete: it is reachable from a console, and right now
it is the only way anyone can change hat. Sam is pinned to `admin`, which is
deliberately without widgets. Deleting it here removes the workaround four
stories before 15.D removes the need for one. AC6 travels with it, since
`switchRole` validates against `availableRoles`.

Both move to 15.D. The side effect is that 15.A is now exactly what the plan
described — additive, no reader changed, nothing observable.

**Still outstanding:** a real sign-in against a deployed revision. The auth path
has broken twice today from things a green suite did not catch, so that check is
not optional; it just needs a deploy first.
