# Story 15.A — Grants on the session

**Epic:** 15 — No hats
**Status:** Review — implemented 2026-08-23. AC5 and AC6 deferred to 15.D with reasons recorded inline.
**Depends on:** 15.0
**Blocks:** 15.A2, 15.C, 15.F
**Plan:** `docs/ROLES_AND_GRANTS_PLAN.md` · sequence `docs/no-hats-sequence.md`

## Story

As the codebase, I want the full set of a person's grants on the session, so
that later stories can stop asking which single hat they are wearing.

## Context

This is deliberately the boring story. It is **additive**: `currentRole`,
`availableRoles` and `locations` all stay exactly as they are, and every existing
reader keeps working. Nothing observable changes for a signed-in user.

That is the plan's own sequencing rule, and it is there because the alternative
failed review:

> `currentRole` is deleted last, not first. Story A adds `grants` beside it;
> each story removes readers; by the end its deletion is a pure removal.
> Deleting it first is a ~30-site rewrite and is the shape that failed review.

Three things this story does.

**1. `Session.grants`.** `parseRoleGrants` already builds the full array and
`resolveSession` already throws all but one entry away. The array is simply kept.

**2. `GLOBAL_ROLES` in one place.** `[TAG_EXEC, TAG_CSD, ADMIN]` is currently
written out three times: `session.ts:205-207`, `session.ts:296-298`, and
`api-session.ts:78-80`. Byte-equivalent, and three chances to add a fourth global
role in two of them. This is also the constant that makes §4's "global reach
comes from the role, not the claim" enforceable, so it has to exist before 15.F
can reject a blank locations list.

**3. Delete the dead switcher.** `switchRole` lives in the `RbacService`
interface, its three implementations and their specs, plus
`POST /api/session/role` — and is called by **no component**. Verified again
2026-08-23: `web/src/app/layout/shell/` has no reference. It is not a feature
that is switched off, it is a feature that was never wired up, and leaving it
implies an escape hatch that does not exist. Its presence is why the reachability
defect reads as a UI gap rather than a model problem.

**Reduced `SessionPayload`.** The payload crossing to the browser drops
`availableRoles`. Nothing renders it — there is no picker — and shipping a list
of roles the user cannot select is a claim the UI cannot honour.

   what each site spells out today.
4. `isGlobalRole(role)` is the only way the check is written afterwards. A grep
   for `TAG_EXEC ||` finds nothing outside `grants.ts`.
5. ~~`switchRole` is deleted from the `RbacService` interface, all three
   implementations, and their specs. `POST /api/session/role` and its route file

   invent a second.
8. A signed-in user notices nothing. Verified by signing in against the deployed
   revision after merge, not by reasoning about it.

## Dev notes

**The reachability defect is not fixed here and must not be.** A founder still
reaches one of five grants after this story. That is 15.D. Fixing reachability
now, before 15.B has made every tenant-scoped gate location-aware, is precisely
the ordering the plan warns produced a cross-tenant write escalation in an
earlier attempt.

**Corrected 2026-08-26: it is latent, not live.** This story called it "the live
bug" three times, and Epic 15's own text described the founders as being "in
production". Sam confirmed those client-founder accounts were created for setup
and testing, have never signed in, and are not in use. The code defect is real
and unfixed and becomes live with no code change the moment a founder signs in.
What was wrong is the word, and the word was doing work: **this story uses it to
justify sequencing**, so a reader arriving here inherits an urgency ranking built
on an outage nobody is having. The ordering argument above survives on its own
merits, which is why the sequencing is unchanged and only the framing is
corrected. Full note in `docs/epics.md` under Epic 15; four other documents still
carry the old framing and are named there.

**Deleting the switcher looks like removing the fix.** It is the opposite. There
is no picker, so the endpoint is unreachable; the model this epic moves to has no
active role for a picker to set. Anything needing a temporary way to change hats
should use the endpoint before this story lands, not after.

**Do not touch the claim shape.** Still the right instruction, but as of
2026-08-26 for two reasons rather than the one written here. Retyping `locations`
makes `parseRoleGrants` drop every entry, `resolveSession` returns null, and
every gate reads that as signed out — however that rollback cost is currently
**zero**, because nobody is signed in, and it re-arms at the first real sign-in
after any shape change. The two reasons that bind regardless are §4's fail-closed
rule (`locations: []` means none, never all, because a blank admin textarea
yields `[]`) and §4's size budget (900 bytes measured against the current shape,
with an overflow path that truncates to a **prefix** and therefore needs a flat
array). Same keys, same types — but know which of the three arguments you are
relying on. Full note in `docs/epics.md` under Epic 15.

## Touched by the 2026-08-22 review streams (landed 2026-08-26)

Status unchanged. This story's acceptance criteria are unaffected; the note is
here because the review-stream commits modified two files this story references
and the pre-commit check correctly required saying why.

The commits were written on 2026-08-22 against the branch that produced 7.6-7.8,
were left behind when that branch was rebased, and are being landed four days
later. They predate this story rather than responding to it.

`lib/auth/grants.ts` — `assertTeamUidsExist`'s injected resolver changed shape,
from a per-uid `userExists: (uid) => Promise<boolean>` to a batched
`missingOf: (uids) => Promise<readonly string[]>`. The reason is a correctness
one and not a performance one: the per-uid version was called with a bare
`catch { return false }` in `lib/auth/admin.ts`, so a transient Firebase Auth
failure was indistinguishable from "this user does not exist", and because the
assertion is deliberately all-or-nothing an outage rejected the whole write
while naming real people as missing.

**15.A's own exports are untouched.** `GLOBAL_ROLES` and `isGlobalRole` are not
modified, added to, or referenced by these commits — verified by diffing them
against `lib/auth/grants.ts` and `lib/auth/session.ts` directly. The claim shape
is unchanged, so the byte-compatibility requirement in `ROLES_AND_GRANTS_PLAN.md`
§4 still holds and `parseRoleGrants` behaviour on a rollback is unaffected.

`lib/auth/session.ts` — comment only on the parser's export contract, recording
that `lib/auth/user-directory.ts` now reads claims through the same function
instead of hand-copying the parsing. No logic change.

`lib/auth/api-session.ts` and `web/src/app/core/models/role.model.ts`, the other
two files this story lists, are not touched at all.
