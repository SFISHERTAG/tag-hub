# Story 4.9 — Two client roles are offered no widgets at all

**Status:** Draft — not started, 2026-08-27

## Story

As a `client_setter` or `client_setter_manager` signing in, I need my dashboard
to offer me something, so that the product does not present an empty page as a
finished state.

## The defect

`ROLES.CLIENT_SETTER` and `ROLES.CLIENT_SETTER_MANAGER` appear in **zero**
`availableFor` lists in `lib/dashboard/widget-definitions.ts`. Counted at
`8bbce5a`:

```
CLIENT_OWNER            4
CLIENT_MANAGER          3
CLIENT_CLOSER           2
CLIENT_SETTER_MANAGER   0
CLIENT_SETTER           0
```

Both roles are real. `lib/auth/roles.ts` defines them, and `lib/dashboard/scope.ts`
gives each a scope: `client_setter_manager: "team"` at `:62`,
`client_setter: "self"` at `:64`. Nothing about them is a stub.

## Why this is not story 4.8

**4.8 is ids with no loader. This is roles with no ids**, and the difference is
what makes this one worse to find.

Under 4.8 the registry offers a widget, `widget-loaders.ts:21` finds no loader,
and the tile renders as "not built yet". The failure announces itself: a person
sees a placeholder and can report it, and a session grepping for unregistered ids
finds it.

Here `getAvailableWidgets(role)` filters `WIDGET_REGISTRY` by `availableFor` and
returns an empty array. There is no placeholder, no id, no error and nothing to
grep for. **A client setter signs in to an empty dashboard and the product
behaves exactly as though that were correct.**

That is the same shape as the finding this repository already paid for: the tile
asserting a negative. A dashboard with nothing on it and no complaint reads as
"nothing to see" rather than "nothing was built".

## What is not yet known, and must not be guessed

**Whether these roles should have a dashboard at all is a product question and it
is Sam's.** A setter may legitimately live entirely in the pipeline and day-view
surfaces and never open a dashboard, in which case the correct fix is an explicit
redirect or an honest empty state, not widgets. Inventing a widget set here would
be exactly the "status invented to fill a gap" that `AGENT_COORDINATION` §11 says
is worse than an admitted gap.

So this story is filed to record the state, not to specify the build. Its first
acceptance criterion is a decision, not code.

## Acceptance criteria

1. [ ] Sam decides whether `client_setter` and `client_setter_manager` get a
       dashboard, a redirect to a surface they do have, or a deliberate empty
       state. Recorded here with the reason.
2. [ ] Whichever is chosen, a session signing in as each of those two roles
       reaches a screen that is intentional rather than incidental.
3. [ ] If the answer is "no dashboard", `getAvailableWidgets` returning empty for
       them is asserted in a test, so the next reader finds the decision rather
       than rediscovering the gap.
4. [ ] No role string is inlined. Any check goes through `ROLES.*` or
       `PermissionService`, per the CLAUDE.md security contract.
