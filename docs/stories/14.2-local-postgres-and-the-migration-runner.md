# Story 14.2 — Local Postgres and the migration runner

**Epic:** 14 — Off Firestore
**Status:** Review — implemented 2026-08-23
**Depends on:** 15.0 (the ledger)

## Story

As anyone working on this repo, I want a local database that matches production
and a safe way to bring it up to date, so that "works locally" means something.

## Context

Local development was one of Sam's three stated reasons for leaving Firestore.
It was also broken, quietly: **the local `tag_automation` had 4 tables and
production has 27.** Local was stuck around migration 002 — no `clients`, no
`appointments`, no `courses`, no ledger. Anything touching those tables could
only be tested against production.

Nobody had noticed because nothing reports it. The eleven migrations are applied
by hand, and a database that is behind looks identical to one that is current
until a query fails.

**Why a runner now, when 15.0 refused to build one.** 15.0's reasoning was
right and is unchanged: no staging environment, migrations hand-applied straight
at production, and a runner that guesses wrong is worse than a human with a
trustworthy list. What this story changes is only that a local database now
exists to be wrong against. Production is still applied by a human. The runner
refuses a non-local target unless the operator says `--force` in as many words.

## Acceptance criteria

1. `npm run migrate:local` applies pending migrations in filename order.
2. `--dry` plans without touching anything.
3. Every decision is in a pure module, provable without a database.
4. Refuses a non-local target unless `--force`.
5. Refuses when a migration was edited after being applied, and `--force` does
   **not** override that.
6. Refuses a gap — an earlier migration unapplied while a later one has run.
7. Each migration applies in its own transaction with its ledger row written
   inside it.
8. Idempotent: a second run applies nothing.
9. Migrations connect as a role that can do DDL, separately from the app user.

## Dev Agent Record

### Completion notes

**Docker was the wrong instinct and checking saved it.** The obvious build is a
`docker-compose.yml`. Docker is not installed on this machine — but Homebrew
`postgresql@18` is, running on 5432, with a `tag_automation` database and a
`tag_app_user` role already present. So the story is not "stand up a local
Postgres". It is "the local Postgres is nine migrations behind and nothing says
so".

**Three defects found by running it, none of which a test would have caught.**

*The app user cannot migrate.* Applying as `DB_USER` fails with `permission
denied for schema public`. `tag_app_user` holds SELECT/INSERT/UPDATE/DELETE and
no DDL rights, which is correct for an application and useless for a migration.
Hence `DB_MIGRATION_USER`, falling back to `DB_USER`. **This is the same defect
as production's 010 blocker** — `CREATE INDEX` on `course_progress` needs the
owner — so the local environment reproduced the production problem within
minutes of existing, which is the entire argument for having one.

*The ledger cannot record its own creation.* `schema_migrations` is created by
011, so recording 001 into it fails on any database predating 011 — which is
every fresh one. The runner now creates it up front, idempotently and with a
definition deliberately identical to 011's.

*The gap check fired on production and was right.* Run against production as a
dry run, it refused: 010 unapplied while 011 has run. That is a true statement
about the live database and the refusal is correct.

**What running it revealed, and it matters more than the runner.** Migration 003
creates **17 tables**, and eight of them mirror Firestore collections with
**zero references anywhere in application code**: `users`, `tenants`,
`auth_codes`, `audit_log`, `bug_reports`, `ghl_agency_token`,
`ghl_location_tokens`, `groups`.

That is the `course_progress` condition from story 11.6 — an empty Postgres
schema beside a live Firestore collection — repeated eight more times, already
in the tree. Epic 14 was scoped as "create the table, backfill, cut over". For
much of it the table exists and has done since 003. Whether those schemas are
usable or were abandoned mid-design is not established here, and it changes
14.4 through 14.9. Raised with the session holding 14.1.

**Not done, deliberately.** No auto-apply to production. No CI step. `010`
remains outstanding: it needs owner privileges `tag_app_user` lacks, which is a
credentials decision rather than something a runner should paper over.
