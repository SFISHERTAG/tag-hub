# Story 11.3 — Verified doc claims: checks over prose

**Epic:** 11 — Migration readiness
**Status:** In Progress

## Story

As anyone reading this repo's documentation, human or agent, I want a claim in a
doc to be something a check enforces, so that reading it is not a guess about
when it was last true.

## Context

Epic 10 is planned out of `docs/epics.md`, `docs/architecture.md`,
`docs/prd.md`, `docs/frontend-file-tree.md` and forty-odd story files. Every one
of those is an input a session will act on without re-deriving it. That makes a
stale sentence in a doc more expensive here than a stale comment in code,
because nothing compiles a doc.

The failure is not hypothetical in this repo:

- The epic tables marked the auth/roles subsystem, the CSM portfolio and the
  client dashboard "not started" or "decided, not built" while all three were
  implemented and live.
- `docs/epics.md` described `MockRbacService` as provided unconditionally and
  both route guards as failing open in production. That had been true and was
  not any more. It was read as current and repeated as a live vulnerability.
- Impersonation audit storage was documented three contradictory ways across
  two docs and a dead migration, none of them the location the code writes to.
- The architecture doc pointed at a client-dashboard route nothing links to,
  while the real one went undocumented.
- A story's own status said Done while its only action had zero call sites.

The pattern is the same each time: prose describing an intention that code later
moved past, with nothing to notice the divergence.

Several checks already exist and are the shape this story is arguing for:
`check-story-status.mjs` (status against its own task list, and against the
files a story claims), `check-role-parity.mjs` (13 roles consistent across three
definitions), `check-secret-scan.mjs`, `check-agent-isolation.mjs`,
`check-branch-freshness.mjs`, and the tracked `scripts/hooks/pre-commit` that
runs them. `web/src/app/app.config.spec.ts` pins the RBAC provider so the
property is enforced rather than described.

This story is the remaining conversions, and the rule going forward.

## Acceptance criteria

1. A doc claim that can be checked is checked, and the doc names the check.
2. A claim that cannot be checked is marked as judgement, so a reader can tell
   the two apart.
3. The data-model doc-guard watches every file that declares a store, including
   the Cloud Functions side and `lib/webhooks/**`, not only the four paths it
   started with.
4. Epic and story status tables agree with the story files, and both agree with
   the code. Where they cannot, the doc says which is authoritative.
5. Documented routes exist and reachable routes are documented.
6. A single audit-log storage location is documented, matching where the code
   actually writes.
7. Every check announces what it checked, so a skipped check is visible.

## Dev notes, what a check cannot do

Some claims are genuinely judgement: why a boundary exists, what a trade-off
bought, which of two designs was preferred and why. Those are the most valuable
prose in the repo and none of it is mechanically checkable.

The goal is not to delete them. It is that a reader can tell instantly which
kind of sentence they are reading, so that "the guards are default-deny" is
known to be enforced while "we chose Slack over an in-app inbox because clients
already live there" is known to be reasoning. Conflating the two is what let a
corrected security claim be re-reported as live.

## Dev notes, the cheapest high-value conversion left

The data-model guard's blind spot. It watches four paths and misses the Cloud
Functions side entirely, which is how at least five real collections ended up
undocumented in the file CLAUDE.md calls the mandatory single source of truth.
Widening a watched-file list is a one-line change with a large blast radius, and
it fails loudly the moment it finds something.
