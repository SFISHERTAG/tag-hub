# Story 8.7 — Escalate a config fault instead of silently serving fixtures

**Epic:** 8 — Operational instrumentation
**Status:** Done. Implemented 2026-08-25; corrected 2026-08-27 (see Correction), gate green

## Story

As whoever operates the Hub, when a deployment cannot read its own
configuration, I need to be told, rather than having every dashboard quietly
substitute fabricated numbers that look exactly like real ones.

## The defect

`resolveDashboardLocation` (`app/api/dashboard/_lib/access.ts`) was:

```ts
try { return getLocationForDashboard(session) || null; }
catch { return null; }
```

Two different conditions arrived at that `catch` and both became the same
`null`:

| Condition | What it means | Right response |
| --- | --- | --- |
| A client role holds no location | A data state a client can legitimately be in | Sample data is a fair answer |
| `GHL_LOCATION_ID_TAG_GROWTH` is unset | A **deploy fault** | Someone should be paged |

Four routes then read that `null` and substitute fixtures:
`leads-funnel`, `spend-roas`, `pipeline-board`, `kpi-summary`. So one missing
environment variable converts every internal user's live funnel into
`MOCK_METRICS`, and the only signal is a disclosure shown to the *viewer*.

**The viewer was told. Nobody operating the system was.** That asymmetry is the
whole bug: the tiles carry `source: "sample"` and a `kpiDisclosure`, so nothing
looks broken from outside, and the condition can persist indefinitely because
its only reader is the person least able to act on it.

It also breaks this project's own error contract, stated in `CLAUDE.md`: catch
only to enrich context, then re-throw or log and return a typed error. This
caught to a value with no logging at all.

## Decisions

1. **A typed error, not a message match.** `DashboardLocationError` carries a
   `kind` of `"config"` or `"unassigned"`. Matching on the message string would
   work and would break the first time someone reworded it.
2. **Only the deploy fault escalates.** `"unassigned"` returns `null` quietly,
   because sample data genuinely is the right answer for a client with no
   location. Alerting on it would be noise that buries the real signal.
3. **An unknown error escalates too.** Anything that is not a
   `DashboardLocationError` is by definition unanticipated, and the failure mode
   this story exists to fix is precisely "an unanticipated condition became a
   silent fixture".
4. **Throttled to one alert per fault kind per 15 minutes.** A config fault
   fires on every dashboard request from every internal user across four routes.
   Per-occurrence alerting would post hundreds of identical messages and teach
   everyone to mute the channel, which is a worse outcome than not alerting.
5. **In-process throttle, not persisted.** A restart re-alerting once is correct:
   a restart is exactly when a config fault is introduced or fixed.
6. **Alerting can never fail the request.** `void postAlert(...).catch(() => {})`,
   matching the pattern established in `app/api/onboarding/intake-submit/route.ts`
   at commit `a051722`. A dashboard must not go down because Slack is unreachable.
7. **Reuses `postAlert`, does not invent a channel.** `lib/slack.ts:221` already
   posts to `SLACK_OPS_CHANNEL_ID`, an internal channel deliberately separate
   from the per-client channels a `client_owner` guest can see. Story 6.5
   established it.

## Dev notes

**This story does not make the dashboard show real data.** It makes the
*absence* of real data audible to TAG. The four widget routes still serve
fixtures when no location resolves, and the health widgets remain fabricated for
a different reason entirely: `lib/dashboard/csm-clients.ts:81` calls
`getMockMetrics(clientId)`, which discards its argument and returns
`{ roas: 95, spend: 102, leads: 88, sla: 97 }` for every client in the system.
That is a separate and larger problem, found in the same audit, and it has no
story yet.

**One deployment step remains and it is not code.** `SLACK_OPS_CHANNEL_ID` is
present in `.env.example:129` and unset on the Cloud Run service, so today this
escalation logs to `console.error` and posts nowhere. Setting it, and inviting
the bot to that channel, are the two actions that make this story's alert
actually arrive. Until then AC1 is satisfied in code and inert in production,
which is exactly the shape of gap this epic exists to close, so it is recorded
here rather than left implied.

## Correction, 2026-08-27: the alert reached seven roles out of thirteen

This story was marked Done, its gate was green, and AC1 was false for six of the
thirteen roles in `ROLES`.

`getLocationForDashboard` routed on two lists local to
`lib/dashboard/location-selection.ts`: `AGENCY_DASHBOARD_ROLES` (four TAG-side
roles) and `CLIENT_DASHBOARD_ROLES` (three client roles). Seven of thirteen.
The remaining six matched neither and reached a third exit that **returned**
instead of throwing:

```ts
// Fallback
return locations[0] || process.env.GHL_LOCATION_ID || "";
```

So `admin`, `tag_csd`, `tag_setter_manager`, `tag_setter`,
`client_setter_manager` and `client_setter` never produced a
`DashboardLocationError`, never reached `resolveDashboardLocation`'s catch, and
never escalated. For those roles the story's own defect survived the story: an
unset `GHL_LOCATION_ID_TAG_GROWTH` resolved silently to the legacy single tenant
named in `GHL_LOCATION_ID`, which **is** set in production
(`cloudbuild.yaml`), or to the empty string when it is not.

An `admin` is the role most likely to be looking at the dashboard when a deploy
fault is introduced, and was one of the six.

**Why the lists were not simply widened.** `isClientUser` names three of the five
client roles deliberately. `lib/auth/session.ts` says so in a comment, and
`test/internal-role.test.ts` asserts it: adding `client_setter` and
`client_setter_manager` there flips `readOnly` in
`app/api/onboarding/checklist/route.ts` and `legacy/onboarding/`, which is a
permission change in an unrelated feature and would fail that test. The fix
routes on `isInternalRole` (`lib/auth/session.ts`) instead, which already
partitions all thirteen and is already guarded against a new role being left
unclassified.

**Why the fallback was deleted rather than made to throw.** `GHL_LOCATION_ID`
names the sub-account the PIT belongs to (`lib/ghl/tokens.ts`). Stories 1.3 and
1.5 both state it must no longer determine what a signed-in user sees. Reading
it here was the last place it still did.

**How this was missed.** The five original tests all drive `TAG_CSM` or
`CLIENT_OWNER`, one role from each list. Every one passes against code that
handles seven roles, because no test names the other six. The gate was green and
measured half the taxonomy.

Found by adversarial review of PR #9 on 2026-08-27, re-derived from
`lib/dashboard/location-selection.ts` at `5f43a8d` rather than from the PR body.
