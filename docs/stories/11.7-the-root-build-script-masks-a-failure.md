# Story 11.7 — The root build script masks a failure

**Epic:** 11 — Migration readiness
**Status:** Draft
**Depends on:** none

## Story

As anyone trusting the gate, I want `npm run build` to fail when the build
fails, so that a green result means something.

## Context

Found 2026-08-22. `npm run build` returned **exit 0** while the Angular step had
already failed with `ng: command not found`. The Next build never ran either.
Nothing in the output said the gate had not executed.

Reproduced directly: `npm run web:build` alone exits **127**. The failure is real
and the exit code is real; the composite script is losing it.

```
npm run build  ->  exit 0    (ng: command not found, next build never reached)
npm run web:build -> exit 127
```

This is the same class of problem CLAUDE.md already calls out for this script:
"The root `npm run build` is `next build`, which never compiles `functions/src`.
A green root gate therefore proves nothing about functions-side code." That note
warns the gate is *narrow*. This story is about it being *false*, which is worse.
A narrow gate that reports honestly can be worked around. A gate that reports
success when it did not run cannot.

The immediate trigger was a worktree without its own `node_modules`, so `ng` and
`next` did not resolve. That is a local condition and not itself the bug. The bug
is that the condition produced a pass.

**Why this matters more than it looks.** CLAUDE.md's definition of done is built
on this command, and its own standard is "Do not report progress based on reading
the code. Only green output counts." A script that emits green without running is
the one failure mode that standard cannot defend against.

## Acceptance criteria

1. `npm run build` exits non-zero when any step in it fails, including a missing
   binary.
2. A missing `node_modules`, in the root or in `web/`, fails loudly and says
   which, rather than skipping the step.
3. The same audit is applied to the other composite scripts: `web:gate`,
   `check:functions`, and anything else chaining steps with `&&`. Fix whatever
   shares the defect rather than only the one that was caught.
4. A test or CI check asserts that a deliberately failing sub-step propagates a
   non-zero exit from the composite. Without it this regresses silently, which is
   exactly how it arrived.
5. If a worktree is expected to run gates, document how it gets dependencies. If
   it is not, the gate says so instead of passing.

## Tasks

- [ ] Reproduce the exit-0-on-failure case
- [ ] Fix propagation in `npm run build`
- [ ] Audit `web:gate`, `check:functions`, and other `&&` chains for the same defect
- [ ] Regression check that a failing sub-step fails the composite
- [ ] Document dependency setup for worktrees, or make gates refuse to run in one
- [ ] Gate: run the fixed script and show it failing when it should
