# Story 5.12 — Intake submission to seeded brief

**Epic:** 5 — Onboarding and campaign launch
**Status:** Not implemented — code exists, nothing runs it

## Story

As a client who has just filled in the intake form, I need my answers to become
a brief my CSM can work from, so onboarding continues without someone
transcribing my form by hand.

## Live state, verified 2026-08-23

**This does not run anywhere.** Three independent facts, each checked:

| | |
| --- | --- |
| Cloud Function | Not deployed. `gcloud functions list --gen2` is empty; the only services are `phase1-provisioning` and `tag-hub-git` |
| App route | `app/api/onboarding/intake-submit/route.ts` exists and authenticates, then forwards to `process.env.PHASE2_WEBHOOK_URL` |
| That variable | **Not set on the live service.** The secret `PHASE2_WEBHOOK_SECRET` is wired; the URL is not |

So a caller authenticates successfully, hits
`console.error("PHASE2_WEBHOOK_URL not configured")`, and gets a failure. A
client who submits the intake form gets nothing, and nothing says so.

**Nobody knew.** It was called "Phase 2", it had no story, and so it had no
Status to walk backwards and no hook that could fire.

## What the existing code does

`functions/src/webhooks/phase2-intake-submit.ts`, undeployed:

1. Validate the submission
2. Create a Google Doc in the client's Drive folder
3. Seed it with the intake answers (`formatIntakeForDoc`)
4. Generate copy with Gemini (`generateAllContent`)
5. Add an empty UVP tab for a human to complete
6. Share the doc with the client
7. Record completion, and trigger 5.13

## Acceptance criteria

1. [ ] A submitted intake form produces a seeded, shared Google Doc in the client's Drive folder
2. [ ] Gemini-generated copy is present, and the UVP tab is present and empty
3. [ ] The endpoint enforces its secret. **`checkWebhookSecret` must not be used** — it returns `void` and never blocks (see Risks)
4. [ ] Re-delivery does not create a second document
5. [ ] The endpoint is verified reachable and enforcing as part of done, not later
6. [ ] A submission that fails is visible to a human rather than only in logs

## Risks

**Do not redeploy this as it stands.** `phase2-intake-submit.ts:29` calls
`checkWebhookSecret`, which returns `void` and never refuses anything. The
deploy script `deploy:phase2` in `functions/package.json` carries
`--allow-unauthenticated`. Running it ships an open door into client
provisioning. There is no exposure today only because it is not deployed.

**Prefer implementing this in `app/api`** rather than redeploying the function.
The route already exists and already enforces via `authorizeOnboardingTrigger`.
That is story 14.A's substance, and doing it here would duplicate it.

**Gemini cost and failure are unbudgeted.** `generateAllContent` runs per
submission. Nothing here rate-limits it or handles a Gemini outage, and a
failure at step 4 currently loses steps 1 to 3.

## Dev notes

**Decide first whether this is wanted.** It has been dead long enough that
nobody noticed. Before rebuilding it, establish whether any client has submitted
an intake form during that window, because if so there is a person sitting in
the gap with no brief and no error.
