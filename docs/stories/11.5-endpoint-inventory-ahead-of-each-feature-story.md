# Story 11.5 — Endpoint inventory ahead of each feature story

**Epic:** 11 — Migration readiness
**Status:** Draft

## Story

As the person starting an Epic 10 feature story, I want to know exactly which
endpoints it needs before I write a component, so the endpoint layer is designed
once rather than discovered one screen at a time.

## Context

An Angular SPA cannot call a Server Action. Every data path a screen needs must
exist as an endpoint under `app/api/**` first. Measured on this branch:

| | Count |
|---|---|
| Files marked `"use server"` | 22 |
| Exported server actions in them | 41 |
| Existing `app/api/**` route files | 25 |
| `page.tsx` files importing `lib/` directly | 33 of 33 |

Every page reads `lib/` directly. Not most; all of them.

Those numbers matter less than the fact that they moved. `docs/epics.md`
records "39 exported Server Actions across 21 `use server` files" and "24 of 25
data-reading pages", measured earlier. Both grew while the migration was being
planned around them. An inventory taken once at the top of an epic is stale
before the epic's second story starts, which is why this is a per-story
discipline and not a one-off audit.

## Acceptance criteria

1. A script produces the inventory on demand: server actions by feature area,
   existing endpoints, and pages importing `lib/`, with counts and paths.
2. It can be scoped to one feature area, so a story can ask only about its own
   surface.
3. Each Epic 10 feature story carries its inventory, taken when the story
   starts, with the date and commit it was taken at.
4. The inventory distinguishes an action needing a new endpoint from one whose
   endpoint already exists.
5. Re-running it after a story closes shows the surface shrinking, and that
   delta is the migration's actual progress measure.

## Tasks

- [ ] Scope it by feature area

## Dev notes, why per-story rather than once

Designing all 41 endpoints up front is the other option and it is worse. It
front-loads guesses about screens nobody has built, and the endpoint shape a
screen actually wants is often not the shape its server action had — several
actions exist only because a component needed something awkward from a server
component, and disappear rather than becoming endpoints.

Per-story keeps the design close to the screen that consumes it, at the cost of
needing this inventory to be cheap to re-run. Hence a script.

## Dev notes, the number to watch

The useful progress metric for Epic 10 is not screens ported. It is the count of
`"use server"` files remaining, because that is what has to reach zero before
the Next rendering path can be deleted. Screens can look ported while their
actions live on, and that state is indistinguishable from done at a glance.
