# Story 6.2 — Conversion dispatch on showed

**Epic:** 6 — Acquisition loop
**Status:** Done

## Story

As TAG, I want to send a "showed" conversion to Meta when a prospect shows up to a call, so that Meta learns which ads are buying people who engage, not just form-submitters.

## Context

Meta's learning algorithm optimizes for conversions. If we only send closed-won conversions, the algo thinks "high-value prospects come from Form Submit" when really the value came from the closer's conversation.

Sending "showed" teaches it "calls that happen lead to closes more often than form submits alone."

Data: appointment marked "showed" (Story 2.2–2.3) → get contact → get utmAdId → send to Meta Conversions API with hashed email/phone and fbc/fbp.

## Acceptance criteria

1. Trigger: appointment marked "showed" (Story 2.3 outcome).
2. Fetch contact by contactId; extract utmAdId.
3. Call Meta Conversions API with:
   - event_name: "ViewContent" (showed = viewing the offer)
   - user_data: hashed email/phone, fbc, fbp
   - event_id: appointmentId (idempotency)
4. Log event to Firestore for audit (Story 3.5).
5. On error: log and alert (don't throw — showed marking must never fail).

## Implementation

`lib/meta/conversions.ts` — `dispatchShowed(locationId, appointmentId,
contactId)` fetches the contact, extracts `utmAdId` and `fbc`/`fbp` from
`lastAttributionSource` (falling back to `attributionSource`), hashes
email/phone with SHA-256, and POSTs a `ViewContent` event to
`graph.facebook.com/{version}/{META_PIXEL_ID}/events` with `event_id` set to
the appointmentId. Every exit path — missing config, missing contact, no
`utmAdId`, a failed or non-2xx Meta call, or any unexpected error — is caught
and written to `locations/{locationId}/metaConversionLog/showed_{appointmentId}`
in Firestore (Story 3.5's audit trail) instead of throwing.

`app/l/[locationId]/today/actions.ts`'s `markAppointment` schedules
`dispatchShowed` via Next's `after()` once the GHL status write and the
timing/audit-log write have already succeeded, only when `status === "showed"`
and a `contactId` is present — a fire-and-forget follow-on, never inline in
the outcome-save path. `contactId` was threaded through from
`app/l/[locationId]/today/page.tsx` → `StatusControls` → `markAppointment`.

`META_PIXEL_ID` added to `.env.example` alongside the other Meta vars.

Story 6.3 (closed-won → "Purchase") shares the hashing/user_data/POST helpers
in the same file via `dispatchClosedWon`.

## AC5 verification

`test/dispatch-showed.test.ts` deliberately fails the Meta API two ways — a
rejected `fetch` call (simulated outage) and a non-2xx response — and asserts
`dispatchShowed` still resolves without throwing, logging a `status: "error"`
entry to the fake Firestore in both cases. A third test verifies a successful
dispatch hashes email/phone (raw values never appear in the request body) and
sets `event_id` to the appointmentId. All three pass (`npx vitest run
test/dispatch-showed.test.ts`), confirming a Meta outage cannot fail the
outcome save that triggers it.

## Decision, 2026-08-25: one pixel per client, not one shared TAG pixel

Sam's call, and it settles the same question for 6.1 and 6.3.

**Resolve the tenant's own `metaPixelId`.** It is already captured at intake
(`functions/src/webhooks/phase2-intake-submit.ts:171`).

**This is more than wiring, and an earlier draft of this note said otherwise.**
The dispatch path does not have a pixel slot waiting to be filled: it reads a
single global, `const pixelId = process.env.META_PIXEL_ID!`
(`lib/meta/conversions.ts:157`), and `META_PIXEL_ID` is validated as required
config at `:119`. So going per client means replacing a global configuration
assumption with a per-tenant lookup, deciding what happens when a tenant has no
`metaPixelId` recorded, and removing a required env var that other things may
assume. Small, but architectural rather than clerical. Scope it accordingly.

**Why per client rather than shared.** Attribution stays isolated, each client's
conversion data belongs to them, and a mistake affects one account instead of the
whole book. A single TAG pixel would have been simpler to configure and would
have pooled every client's conversions into one signal.

**Not urgent, because of 6.1.** Dispatch is deliberately dark until the 23-client
audit runs, so this decision changes what gets built rather than what happens in
production today.
