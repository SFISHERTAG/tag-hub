# Story 8.5 — The rules engine behind health and escalation

**Epic:** 8 — Operational instrumentation
**Status:** Backlog — shipped without a story, real state unverified

## Why this is a backlog item for shipped code

`lib/rules/` is a live, generic rule evaluator with two configuration sets, and
**no epic mentions it**. It has unit tests and it is on the read path of the CSM
dashboard and the portfolio view. Nothing in the planning system records that it
exists.

Written under `AGENT_COORDINATION.md` §11.

## What is shipped

- `lib/rules/engine.ts` — `evaluateRules`, a config-driven evaluator, with tests
- `lib/rules/types.ts` — the rule and condition shapes
- `lib/rules/configs/escalation.config.ts` — decides a client's escalation bucket
- `lib/rules/configs/clientHealth.config.ts` — feeds the health signal

Consumed by `lib/dashboard/csm-clients.ts` and `lib/ghl/portfolio.ts`.

## Why it matters more than its size suggests

These configs decide **what a CSM is told to worry about**. `escalation.config.ts`
produces the bucket and the reason shown on the escalations desk, and
`computeEscalation` feeds it `daysSinceLastCheckIn` from the audit log.

Story 14.1 found a real defect on that exact path: a client with no
`ghl_location_id` produced the Firestore path `locations/undefined/auditLog`,
which is a *valid* path matching nothing, so "no location" arrived at these
rules as "never checked in" and they acted on it. That is fixed. It is also
evidence that the inputs to these rules were never specified anywhere.

## Acceptance criteria

1. [ ] Record what each config actually decides, in business terms, so a CSM
   could confirm the rules match what they are supposed to mean
2. [ ] State every input each rule depends on and what an **absent** input means
   — the `undefined` location bug existed because that question had no answer
3. [ ] Confirm the thresholds are current and owned by a person, not inherited
4. [ ] Decide whether these configs belong in code or in the tenant
   configuration surface Epic 7 describes
5. [ ] Reconciled with Epic 13's escalation work (13.6 Escalations desk), which
   consumes this and may supersede parts of it

## Verification

**Unverified.** The engine has unit tests; the *configs* have never been checked
against anyone's intent. That distinction is the point of this story.

## Decision, 2026-08-25: thresholds in code now, Epic 7's config surface later

Sam's call. Health and escalation thresholds are written in code, with Epic 7
absorbing them once the numbers stop moving.

**Why code first.** The right thresholds are not known yet. While they are still
being learned, versioned and reviewable beats changeable-at-2am: every change
carries a diff, an author and a reason. A configuration surface makes a bad
threshold a five-second edit with no review, which is the wrong trade while
nobody is confident what "at risk" should mean.

**Why not code forever.** Once the numbers settle, requiring a deploy to change a
number that the person who owns the standard understands better than the person
who can deploy is its own failure. Epic 7 is the home for that, and this is a
deferral with a stated condition rather than a rejection.

**The condition, so this is checkable:** thresholds move to Epic 7's surface when
they have stopped changing, not when Epic 7 is ready.
