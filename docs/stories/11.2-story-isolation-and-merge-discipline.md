# Story 11.2 — Story isolation and merge discipline

**Epic:** 11 — Migration readiness
**Status:** Draft

## Story

As any session working this repo, I want to know before I start that the work I
am about to do is not already done, and that landing it will not silently drop a
commit it depends on.

## Context

Epic 10 is seven feature stories that will be worked concurrently by multiple
sessions across worktrees sharing one `.git`. The coordination failures that
costs shows up as are not hypothetical; each of the following has already
happened in this repo.

**Duplicate work, discovered after the fact.** Two sessions independently fixed
the same fourteen critical findings, in different shapes, hours apart. One
branch's implementation reached `main`; the other was fifteen commits of
superseded work that had to be triaged commit by commit to find the eight that
were genuinely new. Nothing warned either session.

**A cherry-pick that dropped its prerequisite.** A commit adding
`lib/api/webhook-auth.ts` was picked onto another branch without the commit that
added `isInternalRole` to `lib/auth/session.ts`. `main` stopped typechecking. The
break was reported by a third session as a mystery defect.

**A checkout inside another session's worktree.** One session ran
`git checkout --detach` in a worktree it did not own and deleted a committed
file from another session's disk.

**Stale reports treated as current.** Two handoff messages relayed five findings
as verified; four were already resolved. Re-verifying against `HEAD` caught all
of them, which is the whole lesson.

`docs/AGENT_COORDINATION.md` already writes the rules down. This story is about
making the ones that can be checked, checked. A rule that lives only in prose is
a rule that is followed until the session is busy.

## Acceptance criteria

1. A pre-commit or pre-push check refuses a commit whose branch is behind its
   base by more than a stated threshold, naming what it is behind.
2. A check detects a staged change to a file another live branch has also
   modified since the merge base, and names the branch.
3. A cherry-pick or partial port that references a symbol absent from the target
   branch fails a check rather than reaching review. Typechecking the target
   branch is the cheapest form of this.
4. The worktree ownership rule is enforced, not just documented: a session
   cannot check out or detach in a worktree it did not create.
5. Every check states what it checked and what it did not, so a skipped check is
   visible rather than silent.
6. The rules and the checks agree, and `docs/AGENT_COORDINATION.md` points at
   the check that enforces each one.

## Tasks

- [ ] Branch-freshness check: refuse work on a branch too far behind its base
- [ ] Overlap check: warn when staged files are also modified on another live

- [ ] Worktree-ownership guard for checkout and detach operations
- [ ] Make every check announce itself, including when it passes
- [ ] Cross-reference the doc against the checks, in both directions

## Dev notes, why detection beats prevention here

Stopping two sessions from working the same file is not achievable and probably
not desirable; parallel work is the point of worktrees. What is achievable is
that neither session finishes in ignorance. A warning naming the other branch at
the moment of staging costs seconds. Finding out after fifteen commits costs the
triage that produced this story.

## Dev notes, the check that would have caught the most

Of the four incidents, the cherry-pick that dropped its prerequisite is the one a
check catches most cleanly and most cheaply: run the target branch's typecheck
after the pick, before the push. It needs no new infrastructure and it converts a
mystery into an error message naming the missing symbol.

The duplicate-work incident is the expensive one and the hardest to catch. An
overlap warning at staging time is a partial answer. A better one may be social
rather than technical, and this story should say so rather than pretend a hook
solves it.
