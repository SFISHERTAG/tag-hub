# Story 2.5 — Move a deal between stages

**Epic:** 2 — Closer workspace
**Status:** Ready

## Story

As a closer or TAG sales rep, I want to move a deal to a different pipeline
stage from the board, so that the board reflects where work actually stands
without opening GoHighLevel.

## Context

`app/l/[locationId]/pipeline/page.tsx` renders the board as a read-only server
component today. `lib/ghl/opportunities.ts` only exports a read
(`getOpportunities`); there is no opportunity write path anywhere in the Hub
yet. This is the first client interactivity on the board, and the pattern to
follow already exists on `/l/[locationId]/today`: a server action plus a
"use client" control with optimistic update and rollback (see
`app/l/[locationId]/today/actions.ts` and
`app/l/[locationId]/today/status-controls.tsx`, Story 2.3).

## Acceptance criteria

1. A deal can be moved to any other stage in its own pipeline directly from
   the board, without leaving `/`.
2. The move calls a new write in `lib/ghl/opportunities.ts` that updates
   `pipelineStageId` on the opportunity. GHL stays the system of record; the
   Hub does not cache stage locally.
3. The card updates optimistically and rolls back with a visible inline
   error if the GHL write fails, matching the pattern in
   `status-controls.tsx`.
4. A deal cannot be moved into a stage belonging to a different pipeline;
   the control only offers stages from the deal's own pipeline.
5. After a successful move, the page reflects the server's
   `lastStageChangeAt` rather than trusting a client-side guess, since the
   staleness indicator (Story 2.1, AC 5) depends on it being real.

## Tasks

- [ ] Add a stage-update function to `lib/ghl/opportunities.ts`
      (`PUT /opportunities/{id}` with `pipelineStageId`)
- [ ] Server action (new `app/actions.ts`, or extend an existing one)
      calling it and `revalidatePath("/")`
- [ ] Client control on `Card` for choosing a destination stage, scoped to
      the deal's own pipeline
- [ ] Optimistic update, rollback, and inline error on failure
- [ ] Confirm GHL's actual rejection behavior for a cross-pipeline stage id
      and surface it as a clear error rather than a generic one

## Dev notes

A stage `<select>` per card is the smaller correct increment. Drag-and-drop
is a polish pass, not a functional requirement; don't block this story on
it.

Keep `locationId` as the write function's first argument, matching every
other function in `lib/ghl/`. There is deliberately no ambient current
location anywhere in this codebase.
