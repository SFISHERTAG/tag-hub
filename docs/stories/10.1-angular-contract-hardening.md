# Story 10.1 — Angular contract hardening and boundary enforcement

**Epic:** 10 — Angular migration
**Status:** Done

## Story

As the engineer porting this frontend to Angular, I want every CLAUDE.md
constraint to be machine-checked before the first feature module exists, so that
the contract is enforced by the build rather than by memory across fifteen
features and three months.

## Context

Phase 2 landed the Angular skeleton at `web/` and its gate is green. The audit
of 19 Aug 2026 found the green gate was not yet evidence of the contract: several
rules CLAUDE.md states as non-negotiable had nothing enforcing them, and the
cheapest moment to fix that is now, while `web/src/app/` holds twelve files
instead of two hundred.

Specifically, all of the following were true at the start of this story:

- `strict` and `strictTemplates` were absent from `web/tsconfig.json`.
- `@typescript-eslint/no-non-null-assertion` was not enabled, and `strict` does
  not imply it — the rule ships in typescript-eslint's `strict` config, while
  `web/eslint.config.js` extends `recommended` and `stylistic` only.
- CLAUDE.md prescribes `ROLES.ADMIN` and `hasRole(...)`. Neither existed: `ROLES`
  was a readonly array on both sides, so `ROLES.ADMIN` had no referent.
- `scripts/check-story-status.mjs` parsed that array inside a `try`/`catch` that
  fell back to a stale hardcoded role list on any failure, silently.
- `scripts/create-user.mjs` carried a third, divergent copy of the role list,
  missing six roles including `admin`, `tag_csd` and every setter role.
- The root `tsconfig.json` and `eslint.config.mjs` both swept in `_archive/**`
  and `web/**`, so `tsc --noEmit` and `npm run lint` reported over a thousand
  problems from dead code and from a workspace that has its own gate.
- `web/package.json` had no `engines` field and there was no `.nvmrc`, while the
  machine default Node is below the Angular CLI's floor.
- The Angular gate was not reachable from the repo root.

## Acceptance criteria

1. `strict` and `strictTemplates` are on in `web/tsconfig.json`, and the gate is
   green with them on.
2. Non-null assertions fail `npm run web:lint`.
3. `ROLES` is a keyed `as const` object on both sides, with `ROLE_LIST` for the
   call sites that genuinely iterate, and `hasRole()` exists in
   `lib/auth/roles.ts`.
4. A role-list drift between `lib/auth/role-labels.ts`,
   `web/src/app/core/models/role.model.ts` and `scripts/create-user.mjs` fails
   `npm run check:role-parity`.
5. `scripts/check-story-status.mjs` throws rather than falling back to a stale
   list when it cannot parse `ROLES`.
6. `npm run web:build`, `npm run web:lint`, `npm run web:test` and
   `npm run web:gate` all work from the repo root.
7. `tsc --noEmit -p tsconfig.json` exits 0.

## Dev notes

The parity check earned its place on first run: it immediately caught that
`scripts/create-user.mjs` was missing six roles, which meant that CLI could not
create an admin, a CS Director, or any setter. That is the exact class of drift
the August audit's `tag_admin` / `admin` finding came from.

The root `npm run lint` is still red at 47 errors after excluding `_archive` and
`web` (45 `no-explicit-any`, spread across `app/` 22, `lib/` 13, `test/` 3,
`functions/` 3). Those are pre-existing and predate this story — verified
identical against HEAD. CLAUDE.md forbids `any`, so they are a real contract
violation, but most of the `app/` ones live in pages that get deleted as their
Angular feature ships. The `lib/` ones will outlive the migration and need their
own story.

`eslint-plugin-import` cannot be used for the `web/` boundary zones: `web/` runs
ESLint 10.8.1, the plugin's peer range tops out at `^9`, and npm 11 resolves
peers strictly, so the install fails. `@typescript-eslint/no-restricted-imports`
is already available via typescript-eslint 8.62.1 and does the same job.

When the zones are written, they must not bar `shared/` from `core/services/`:
`web/src/app/shared/directives/has-permission.directive.ts` imports
`PermissionService`, a pairing CLAUDE.md mandates on both sides. Scope the
prohibition to `features/` and `layout/`.

## Dev notes, batch 2

`POST /api/auth/refresh` had to be built rather than deferred, because leaving
the interceptor pointed at a route that does not exist would have kept the
refresh path dead in a different way. Firebase has no "refresh a session cookie"
primitive — `createSessionCookie` takes an ID token — and the migration decision
is that the browser never holds a Firebase SDK, so the round trip is server-side:
verify the current cookie, mint a custom token for that uid, exchange it for an
ID token through the Identity Toolkit REST API, mint a fresh session cookie.
It extends a live session and cannot resurrect a dead one; `checkRevoked` stays
on.

The interceptor spec is written against the real composed order from
`app.config.ts` rather than a hand-built array, so reordering that array fails
the suite. Verified: swapping back to `[authInterceptor, errorInterceptor]`
fails 4 of the 7 tests.

The boundary zones needed a second pass. The obvious pattern (`**/features/ghl/**`)
matches the specifier string, so it caught `../../features/ghl/x` but missed
`../ghl/x` — which is exactly how a sibling import is written from one level
inside `features/`. The zones are now depth-independent (`**/ghl/**`), with one
block per integration naming the other three. Verified against four planted
violations and two legitimate imports that must keep passing: GHL importing its
own service, and `shared/` importing `core/services/`.

`lib/auth/session.ts` compared role strings inline at five sites. It passed the
pre-commit role check only because the file imports from `./roles`, which is the
satisfied-by-import escape hatch the audit flagged. Now uses `ROLES.*`.

Two findings deferred to their own stories, not absorbed here:

- **`lib/config.ts` does not exist.** CLAUDE.md states it is the only place that
  reads `process.env` and that it validates every key at import time. 26 files
  under `app/` and `lib/` read `process.env` directly. Nothing validates anything
  at startup, so the audit's "silent fallback to the production project id"
  scenario is still live.
- **The pre-commit hook is still not version-controlled.** `core.hooksPath`
  points at the main repo's hooks directory, shared by every worktree, and
  `git ls-files` shows nothing under `.git/`. Still outstanding below.

## Dev notes, batch 3

`MockRbacService` is now confined to `isDevMode()`. Production gets
`SignedOutRbacService`, which reports "signed out" forever, so every guard
denies. Leaving `RBAC_SERVICE` unprovided was the alternative, but that turns a
missing session into an injector crash at first render, which reads as a build
problem rather than an auth one. The real `HttpRbacService` lands in 10.2.

Three tests failed on first run and all three were worth having:

- The config validator accepted `//api.example.com`. Protocol-relative, so still
  cross-origin and still fatal to a SameSite=lax cookie, but it satisfies a naive
  "starts with /" check. Fixed the validator.
- The guard spec asserted against `console.error` calls from an earlier test,
  because `vi.spyOn` on an already-spied method returns the existing mock. Fixed
  the spec.
- The widget registry spec asserted every role has at least one widget. Six do
  not (see below). Fixed the assertion to pin reality.

**Six roles resolve to an empty dashboard**, identically in
`web/src/app/shared/widgets/widget-registry.service.ts` and
`lib/dashboard/widget-definitions.ts`: `admin`, `tag_sales`,
`tag_setter_manager`, `tag_setter`, `client_setter_manager`, `client_setter`.
`admin` is defensible, since that role works out of `/admin`. The four setter
roles nominally have `/setter`, which polls `POST /api/setter/metrics` — a route
that does not exist on disk. `tag_sales` is the least defensible: the role exists
for TAG's own pipeline, `pipeline_board` is exactly that widget, and its
`availableFor` omits them. The spec now lists all six explicitly, so any *other*
role going empty fails, and any of these six gaining a widget also fails.
Resolving them belongs to 10.6.

The 11 widget `availableFor` lists inlined bare role strings. They passed the
pre-commit check through the satisfied-by-import escape hatch, same as
`lib/auth/session.ts` did. Now `ROLES.*`.

**The hook still needs installing.** `scripts/hooks/pre-commit` is tracked and
`npm run hooks:install` points `core.hooksPath` at it, but that command has not
been run: `core.hooksPath` is repo-wide, so it changes behaviour for the main
checkout and every worktree at once, which is not a change to make silently. Until
it is run, the existing local hook keeps running `check-story-status` only — not
role parity, and not the Angular gate. `.github/workflows/ci.yml` covers the gap
for anything that reaches a branch or PR.

`npm run lint` is deliberately not in CI. It carries 47 pre-existing errors in
real source (45 `no-explicit-any`), so adding it now would make CI red on day one
and train everyone to ignore it. It goes in once those are cleared.

## Closed

All acceptance criteria met and verified green: `npx vitest run`, `npm run web:gate`,
`npm run check:story-status`, `npm run check:role-parity` and
`tsc --noEmit -p tsconfig.json` all exit 0. Angular suite went from 2 tests to 57.

Two items deliberately left open and carried into their own work rather than
absorbed here: `lib/config.ts` (now forced by story 10.2, see below) and the 47
pre-existing `no-explicit-any` errors in real source.

One defect in this story's own output, found by 10.2's design pass and fixed
there: `app/api/auth/refresh/route.ts` reads
`process.env.NEXT_PUBLIC_FIREBASE_API_KEY`. That is a `NEXT_PUBLIC_` variable, so
Next inlines it at build time, and `cloudbuild.yaml:24` defaults the
`_FIREBASE_API_KEY` substitution to an empty string while `--set-env-vars` on line
121 never passes it. Unless the Cloud Build trigger sets that substitution, the
refresh endpoint throws in production. Nothing validated it at startup, which is
precisely the failure `lib/config.ts` exists to prevent. Fixed in 10.2 step 2.
