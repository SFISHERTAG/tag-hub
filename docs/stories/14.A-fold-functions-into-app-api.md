# Story 14.A — Fold `functions/` into `app/api`

**Epic:** 14 — Off Firestore
**Status:** Draft
**Blocks:** 14.10 (delete `lib/firestore.ts` and drop the SDK)

## Story

As the architect finishing the Firestore exit, I need the three Cloud Function
webhooks to run as `app/api` route handlers, so that there is one Firestore
client, one webhook door, and one place each integration is implemented.

## Why this is not a tidy-up

**Phases 2 and 3 can be called by anyone.** All three functions deploy with
`--allow-unauthenticated` (`functions/package.json`). Phase 1 compensates:
`phase1-provisioning.ts:32` calls `requireWebhookSecret`, which returns 401 on a
bad token and 500 when the secret is unset.

Phases 2 and 3 do not. `phase2-intake-submit.ts:29` and
`phase3-meta-setup.ts:26` call `checkWebhookSecret`, which returns `void` and
**never blocks**. Its own comment says so, and gives a real reason: Phase 3's
callers did not send a token at all and Phase 2's had only just started, so a
hard 401 would have broken callers this repo does not control.

Meanwhile `app/api/onboarding/intake-submit/route.ts` and
`app/api/onboarding/phase3-meta-setup/route.ts` already exist and **do** enforce,
via `authorizeOnboardingTrigger` (`lib/api/webhook-auth.ts:31`): a staff session
or a valid bearer token, otherwise 401.

So the shape today is an authenticated front door that forwards to an
unauthenticated back door, and the back door's URL is public. A caller who skips
the proxy reaches Phase 2 — which provisions against a `locationId` named in the
body — with a warning logged and the work done.

**Folding fixes this by construction.** One door, and it is the one that already
enforces. That is the reason to do this story, and it is worth more than the
duplication it also removes.

## What else it collapses

`functions/` is 15 non-test files, 2,631 lines, for three endpoints. Against
`lib/` it re-implements:

| `functions/src/` | `lib/` counterpart |
| --- | --- |
| `ghl.ts` (158) | `lib/ghl/` (13 files) |
| `slack.ts` (98) | `lib/slack.ts` (272) |
| `google.ts` (231) | `lib/google/drive.ts` |
| `postgres.ts` (135) | `lib/postgres.ts` (56) |
| `auth.ts` (142) | `lib/auth/` |
| `firestore.ts` (161) | `lib/data/` (story 14.1) |
| `lib/webhooks/idempotency.ts` | was mirrored in `lib/`; mirror deleted in 14.1 |

CLAUDE.md names the first of these — `functions/src/ghl.ts` versus `lib/ghl/` —
as the duplicate the architecture boundary exists to prevent. It is still there.

## Why it blocks 14.10

`functions/` constructs its own Firestore client and pins
`@google-cloud/firestore` `^7.11.0` against root's `^8.7.1`. The SDK cannot be
dropped from the repo while a separate workspace on a different major is using
it. 14.1 put every `lib/` and `app/` call site behind the seam; `functions/` is
the remainder.

Its four paths, none of which any app-side module reads:
`auth/otpWhitelist`, `locations/{locationId}`,
`locations/{locationId}/provisioningLog`,
`locations/{locationId}/intakeData/latest`.

## The real risk, and it is not technical

Story 1.8 recorded it when `firebase-admin` was approved for `functions/`:
routing provisioning through `app/api` makes the one step a client cannot
onboard without depend on the app being reachable. A Cloud Function has its own
uptime; a Next route handler shares the app's.

That objection was correct then and is weaker now, for reasons to state rather
than assume:

- Phases 2 and 3 **already** route through `app/api` in the live path. Their
  proxies are the authenticated entry point. The app is already on the critical
  path for two of the three.
- The app deploys to Cloud Run, so the availability question is Cloud Run versus
  Cloud Functions gen2, which both run on the same infrastructure.
- The webhook-auth design that was open in 1.8 has since landed as
  `lib/api/webhook-auth.ts`.

**Phase 1 is the one where the objection still has force**, because it is the
only one whose function enforces its own secret and the only one not already
proxied. Sequence it last and decide it separately.

## Scope

**In:** the three webhook handlers, their shared modules, the deploy path, and
the `functions/`-only Firestore paths behind the 14.1 seam.

**Out:** `functions/sql/**`. Those are migrations, not runtime code; the runner
added by 14.2 already reads them from `functions/sql`. Moving them is a separate
decision and migration `010` is unapplied, so nothing should disturb that
directory while the ledger is mid-gap.

## Acceptance criteria

1. Phase 2 and Phase 3 run as `app/api` route handlers, and their existing
   proxy routes become the handlers rather than forwarders.
2. **Every surviving entry point enforces its secret.** No path answers 200 to
   an unauthenticated caller. The `checkWebhookSecret` warn-only function is
   deleted, not left available.
3. The old Cloud Function endpoints are decommissioned, not merely orphaned. A
   deployed function whose replacement exists but which still accepts traffic is
   the same hole with an extra step.
4. `functions/src/firestore.ts` is gone; its four paths are reachable through
   `lib/data`, with types declared from the **writers** per `docs/repository.md`.
5. The duplicated modules are gone: one GHL client, one Slack client, one Drive
   client, one Postgres pool, one idempotency module.
6. Phase 1 is either folded or **explicitly deferred with the 1.8 availability
   reason restated and a decision recorded**. Silence is not a decision.
7. `@google-cloud/firestore` appears in exactly one `package.json`.
8. Gate green: `npm run build`, `npm run test`, `npm run lint`, and
   `npm run check:functions` if `functions/` still exists.

## Dev notes

**Do not do this as one change.** Each moved module is its own commit with its
own gate run. The `functions/` workspace has its own `tsc` and `eslint` that the
root gate does not run — `npm run check:functions` — and CLAUDE.md calls that
out because Story 1.8 landed auth code that way.

**Migrate the paths behind the seam, not around it.** `functions/src/firestore.ts`
writes five fields on `locations/{id}` that `Tenant` never declared; 14.1 found
them by reading the writer. The same method applies to its other three paths, and
they have no app-side reader at all, so nothing has ever modelled them.

**`create()` semantics are load-bearing in the module being moved.**
`idempotency.ts` relies on the write failing when the document exists. That is
the exactly-once webhook claim. `docs/repository.md` says what a `false` means
and why every caller must decide explicitly.

**The deploy path changes and that is most of the risk.** Three `gcloud functions
deploy` commands with per-phase secrets disappear. Whoever does this needs the
Cloud Run deploy to carry `PHASE2_WEBHOOK_SECRET`, `PHASE3_WEBHOOK_SECRET`,
`GHL_PIT`, `SLACK_BOT_TOKEN`, `GOOGLE_GEMINI_API_KEY` and
`META_SYSTEM_USER_TOKEN` before anything is decommissioned.
