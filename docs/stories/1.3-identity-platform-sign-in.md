# Story 1.3 — OTP sign-in via Postgres

**Epic:** 1 — Foundation and access
**Status:** Ready

## Story

As a TAG staff member or client user, I want to sign in to the Hub with a 6-digit OTP sent to my email, so that the app knows who I am before it shows me anything.

## Context

Nothing in the Hub is currently authenticated. Every route reads
`GHL_LOCATION_ID` from the environment and serves the same single tenant to
anyone who opens it. That is fine for development against TAG's own
sub-account and unacceptable the moment a client user or a second tenant
exists.

OTP via email is simpler than password management and works for both TAG staff and client users.

## Acceptance criteria

1. An unauthenticated request to any route other than the sign-in page
   redirects to sign-in.
2. Email entry generates a 6-digit OTP (valid for 10 minutes) stored in Postgres.
3. User enters email + OTP; server verifies against Postgres and creates session.
4. The session is verified server-side on every request. A forged or expired
   token is rejected, not trusted from the client.
5. Sign-out clears the session and returns to sign-in.
6. `GHL_LOCATION_ID` no longer determines what a signed-in user sees. It may
   remain as a development fallback only.

## Tasks

- [ ] Create `otp_sessions` table in Postgres (email, code, created_at, expires_at)
- [ ] Email send integration (sendgrid or similar)
- [ ] POST `/api/auth/request-otp` — generate and send OTP
- [ ] POST `/api/auth/verify-otp` — verify code and create session
- [ ] Session cookie, httpOnly and secure in production
- [ ] Sign-in page with email + OTP entry
- [ ] `middleware.ts` gating all routes except sign-in and `/api/oauth/*`
- [ ] Sign-out
- [ ] Seed initial users (email → location/role claims populated via 1.4 and 1.6)

## Dev notes

`/api/oauth/*` must stay unauthenticated — it is the GHL install callback and
GHL will not carry a Hub session. It has its own CSRF protection via the
`state` parameter and cookie comparison.

Verify the session server-side on every request. The whole tenant-isolation model rests on the role and location list
being trustworthy.

OTP cleanup: expired codes can be deleted via a scheduled job or vacuum on request.
