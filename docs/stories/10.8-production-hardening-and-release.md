# Story 10.8 — Production hardening and release

**Epic:** 10 — Angular migration
**Status:** Draft

## Story

As the team, we want the migration's accumulated work in production and soaking
before the Angular cutover is called done, so that if something breaks we know
which change did it.

## Renumbered from 10.4 on 2026-08-21

This was 10.4. So was a different story: `docs/epics.md` used that number for
"Shared M3 primitives, portfolio and bug reports", the first story to ship a
real feature end to end. Two stories under one id is how one of them silently
never gets built, so they are split. 10.4 is the feature story, which is also
what Story 11.4 calibrates its estimates against. This one moved to 10.8,
after 10.7's legacy removal, because a release story belongs at the end of the
work it releases.

**Its premise has also moved on.** When written, the body of work was 22
commits sitting unmerged on a branch. Those are merged: `main` is green at
`fe332b2`, and production is roughly 109 commits behind it, running an image
whose commit cannot be identified because manual builds record no SHA. The
numbers below are stale wherever they say 22; re-measure before working this
story. What has not changed is the argument, which is that a release nobody
can attribute is a release nobody can debug.

**One thing that has changed materially.** The Angular cutover happens
pre-launch with nobody being served, so the soak this story describes is a
verification exercise rather than a customer-risk mitigation. Weigh its
ceremony accordingly.

## Context

The branch carries the whole 10.1 and 10.2 body of work: the CSRF check, the
401 JSON path, `lib/config.ts`, the session-cookie extraction, typed API session
guards, the keyed `ROLES`, the boundary lint, and the domain cutover config.
None of it is deployed. `main` is 22 commits behind.

Two claims were checked before this plan was written, because both were
load-bearing and one was wrong.

**Production has working auth today.** `main` carries `app/signin/*` and the full
OTP endpoint set (`request`, `verify`, `session`, `signout`, `test-signin`). An
adversarial review asserted the live revision "has no login at all", which is
false. This release hardens working auth rather than introducing it, and the
risk is correspondingly smaller.

**The Angular bundle is not shipped.** `Dockerfile:31` runs `npm run build` and
`:48-50` copies `.next/standalone`. `web/` is never built and never served. This
is the real blocker: no Angular route can be flipped until something builds and
serves the bundle, and no lane owns that today.

## The rule this story exists to enforce

One variable at a time. Deploying the hardening and the first Angular route
together means a failure has 23 possible causes. Deploying the hardening alone
means it has one.

## Acceptance criteria

1. The 22 commits are on `main` and deployed, with the `run.app` URL and
   `hub.taxadvisorygrowth.com` both verified serving.
2. Sign-in works end to end in production: OTP request, verify, session, hat
   switch, sign-out.
3. The GHL OAuth install completes against the new redirect URI.
4. `/api/**` returns 401 JSON to an unauthenticated caller, not a 307.
5. No Angular route is flipped in this story.

## Tasks

### Preconditions, verified and recorded before anything merges

- [ ] `hub.taxadvisorygrowth.com` certificate issued and serving (confirmed
      2026-08-20, re-confirm at merge time)
- [ ] GHL Marketplace app redirect URI equals `_GHL_REDIRECT_URI` in
      `cloudbuild.yaml`, exactly
- [ ] `_FIREBASE_API_KEY` substitution is actually set on the Cloud Build
      trigger. It defaults to `""` in the file, and `POST /api/auth/refresh`
      plus both sign-in paths now need it server-side
- [ ] A rollback revision is identified by name, not "the previous one"

### The release

- [ ] Merge the branch to `main`
- [ ] Deploy
- [ ] Smoke: `/` redirects to `/signin`, `/signin` renders, OTP round trip
      completes, `/api/auth/session` returns a session for a signed-in caller
- [ ] Smoke the two things that flip with this deploy and are easy to miss:
      an unauthenticated `/api/**` call returns 401 JSON, and the GHL install
      callback lands on the new domain
- [ ] Soak. No Angular work merges until it has run clean.

### Known behaviour changes to watch for

- [ ] `APP_ORIGIN` is now set, so the CSRF check demands that exact origin
      rather than falling back to comparing Origin against Host. Sign-in
      requests arriving at the `run.app` URL will start failing. Intended, but
      it means the two origins stop being interchangeable at deploy time, not
      when the old one falls out of use.
- [ ] `proxy.ts` no longer auth-gates `.js`, `.css`, `.map`, fonts or the
      service worker. Confirm no Next asset relied on that gate.

## Dev notes

**Why this is its own story.** The Angular slice needs three things that do not
exist yet: the Dockerfile building `web/`, Next serving the bundle same-origin
with a route allowlist, and a way for an Angular nav item to link out to a page
still served by Next. Today the shell renders every nav entry as an in-app
`routerLink`, there is no wildcard route, and two entries (`/clients`, `/flow`)
match no Next route at all. That work is story 10.5 and it is the real critical
path, not the feature ports.

**What this story explicitly does not do.** It ships no Angular. `web/` still is
not in the image after it. That is the point: it separates "did the hardening
break anything" from "did the Angular flip break anything".
