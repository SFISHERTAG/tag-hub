# Story 5.1 — Onboarding checklist from Fulfillment stages

**Epic:** 5 — Onboarding and campaign launch
**Status:** Ready

## Story

As a CSM, I want an onboarding checklist that tracks where each new client sits in setup, so that nothing falls through and handoffs are clear.

## Context

Each client has a Fulfillment opportunity tracking their onboarding stage:
- PR1: Funnel built
- PR2: Funnel tested
- AP1: Campaign created (paused)
- AP2: Campaign launched
- AP3–5: Post-launch (up-sell, ascension)

The checklist maps to this pipeline: each stage has a set of tasks, and advancing the stage closes those tasks.

## Acceptance criteria

1. `/onboarding` shows checklist driven by the client's Fulfillment opportunity stage.
2. Stage map: each stage (PR1–AP5) has a list of "before next stage" tasks (e.g., "Fund the account" for PR1). **Before AP1 specifically:** "Connect Meta ad account" — Story 5.4 (create paused campaign) calls the Marketing API against a specific `metaAdAccountId` on the tenant record, so AP1 cannot complete without it. Two-step process, documented in `docs/meta-live-launch-plan.md`: (a) client's business partners their ad account with TAG's Business Manager (Business Settings → Partners, on the client's side), (b) TAG assigns that ad account to the `tag-hub-server` System User (Business Settings → System Users → Add Assets → Ad Accounts, on TAG's side) — partner access alone isn't enough, the System User needs the individual asset assignment too, confirmed the hard way during Story 4.1. Once both are done, the id gets set on the tenant either via intake (if the client already had an account — see `functions/src/webhooks/phase2-intake-submit.ts`) or manually via the admin tenant form (`app/admin/tenants/[locationId]/tenant-form.tsx`, which already has the field).
3. CSM can mark tasks complete via checkbox (optional — not gated by Fulfillment stage).
4. Advancing stage (via Story 5.5) auto-completes tasks for that stage.
5. Checklist is read-only for client users (only CSM can edit).
6. Each client shows **time in current stage**, derived from the Fulfillment
   opportunity's `lastStageChangeAt` — the same field `daysSince()` already
   reads on the pipeline board. Without it the checklist says what is
   outstanding but not what is *stuck*, and a client parked in PR2 for three
   weeks looks identical to one that arrived yesterday.
