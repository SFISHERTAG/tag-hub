# Story 13.5 — Stage SLA timers on the client card

**Epic:** 13 — Lifecycle handoff and churn prevention
**Status:** Draft
**Depends on:** 5.10 (opportunity custom fields), 13.2 (stage model parity)
**Supersedes:** 5.7, 5.8, 5.9 — see `docs/epic-5-13-reconciliation.md`
**Architecture:** `docs/fulfillment-pipeline-architecture.md`

## Story

As a CSM, I want to see how long a client has been stuck, so that I intervene
before they churn rather than after.

## Context

24 of 37 clients sit at `Onboarding Booked`, several for a long time, and
nothing anywhere says so. That is the case for this story, and it is measured
rather than argued.

This is the merge of two parallel drafts. `docs/epic-5-13-reconciliation.md`
records what was kept from each and why. Three things came across from the
retired Epic 5 stories and each changes the design:

**1. `lastStageChangeAt` alone is not enough, and this is load-bearing.** GHL
keeps that field only for the stage an opportunity is in *now*. The moment a
client advances, the duration of the stage they left is gone. Built on that
field alone, this feature can report where clients are stuck today and can never
report where clients get stuck. Stage entry time therefore comes from dated
milestone custom fields (5.10), with `lastStageChangeAt` as the fallback for
opportunities that predate the field folder. Both paths must work: the 37 live
records have no milestone history.

**2. Tracks run parallel to stages and are the point.** A2P registration and the
Meta ad account handoff start early, run alongside build work, and hard-gate
launch. A stage-only timer cannot see them: a client can be moving through build
while A2P has sat untouched for a month, and every stage clock reads green the
whole time. Two kinds of clock, one function.

**3. A sweep that is not idempotent is a pager that cries wolf.** Detection runs
on a schedule, not on read, or nothing surfaces until someone opens the screen.
Once it runs on a schedule it must remember what it has already said.

## Acceptance criteria

### The clocks

1. Per-stage SLA thresholds are defined in one place and are admin-editable
   without a deploy. Baselines below.
2. Per-track SLA thresholds sit on the same footing and are equally editable.
   The A2P numbers are the most likely to need tuning, being guesses about a
   carrier's turnaround.
3. One pure function computes both: `sla(startedAt, thresholdHours, now)`
   returning `{ dueAt, hoursRemaining, state }` where state is
   `on-track | due-soon | breached | unknown`. `due-soon` is the final 25% of
   the window. Stage and track differ only in what is passed in; they must not
   become two implementations of the same arithmetic.
4. Stage entry time resolves from the milestone custom field that completed the
   previous stage (5.10), falling back to `lastStageChangeAt`, falling back to
   `unknown`.
5. Where no start time can be established, the display says **unknown**. Never a
   zero, never the record's creation date. A misleading zero on a churn signal
   is worse than a blank.

### Where it appears

6. Timer on the client card in the portfolio.
7. Timer in the client modal, with the track clocks listed separately from the
   stage clock.
8. A breached track is visible on a client whose stage is on-track. That is the
   exact case a stage-only timer hides, so it is the case worth testing.
9. Portfolio is sortable and filterable by time in stage, so the worst case is
   reachable without reading 37 cards.
10. Breach, approaching, and healthy are distinguishable without relying on
    colour alone. Styling flows from M3 tokens; no raw hex in any component
    `.scss`.

### Detection and escalation

11. A scheduled sweep evaluates every tenant, opens a breach record for any
    newly breached stage or track, and resolves any open record whose completing
    milestone has since been stamped. Resolution is observed by the next sweep,
    not reported by a webhook.
12. The sweep is idempotent. Running it twice produces the same state as running
    it once and sends no second notification.
13. A newly opened breach notifies the assignee and their manager, once. Stamped
    so it cannot re-fire hourly.
14. A newly opened breach raises a 13.6 escalation, origin `system`.
15. Tenants with no milestone history and no `lastStageChangeAt` are counted and
    skipped, not breached. The 37 live records are all in this state on day one,
    and a wall of 37 false breaches on first run would discredit the feature
    permanently.
16. Per-tenant failure is isolated. One tenant's GHL fetch failing does not abort
    the run. The summary reports `{ scanned, skipped, opened, resolved, failed }`
    and a non-empty `failed` is surfaced, never swallowed.

## Baselines

Keyed to the 12 live stages, verified on the board 2026-08-22. Ownership
alternates, which is what makes a breach nameable: it always belongs to someone.

| Stage | Whose move | Baseline | Rationale |
| --- | --- | --- | --- |
| Onboarding Booked | Client | 168h (7d) | Call is booked, not held. A booked call that has not happened in a week is the single largest bucket today, 24 of 37. |
| Onboarding Complete | TAG | 72h (3d) | Provision Slack, GHL, Skool. Entirely TAG-side, no external dependency. |
| Tech Stack Provisioned | Client | 120h (5d) | Waiting on intake. Longest legitimate client wait; chasing sooner reads as nagging. |
| Intake Complete | TAG | 120h (5d) | VSL copy. The largest genuine block of TAG production work. |
| Creative Copy Complete | Client | 168h (7d) | Client or actor produces creative. Filming needs scheduling; a shorter clock breaches on everyone simply booking a shoot. |
| Creatives Compete | TAG | 72h (3d) | Editing. TAG-side production. |
| Editing Complete | TAG | 48h (2d) | Launch. Everything is built and approved, so this is execution. A funnel sitting built-but-dark is pure waste. |
| Campaign Launched | Market | 336h (14d) | To first appointment. Not a task SLA, a performance signal: no appointment in two weeks means the campaign is wrong, not that someone is slow. |
| First Appointment Booked | Client | none | The client's own sales motion. Outside TAG's control. |
| 1st Deal Closed | none | none | Working. Ascension timing is story 3.6's concern. |
| Ascension | none | none | Steady state. Clients legitimately sit here for months. |
| Offboarded | none | none | Terminal. |

Tracks, which run independently of stage:

| Track | Baseline | Rationale |
| --- | --- | --- |
| A2P submitted | 120h (5d) from Onboarding Booked | Get registration details out of the client and filed. The clock that matters most: starts day one, gates launch, and is the one thing that can be a month late while every stage reads green. |
| A2P completed | 336h (14d) from submission | Carrier approval. TAG does not control it, so this measures "chase it", not "do it". |
| Meta partnered | 120h (5d) from Tech Stack Provisioned | Client-side action in their Business Manager. Known long pole, story 5.1 AC2. |
| Meta system user | 24h (1d) from partnered | TAG-side, one setting, immediately after the client's half lands. |

These are reasoned, not measured. There is no history to fit them to, because
the pipeline that would have produced it was replaced. Expect the first revision
to be real work rather than a correction, and see the rollout note below.

## Dev notes

**Roll out with notifications off.** Run the sweep in observe-only mode until it
has produced enough history to re-set the baselines from data. Every current
record lacks milestone history, so the first live run is the least trustworthy
one it will ever do.

**Cadence: hourly.** Onboarding SLAs are measured in days. Hourly detection is
already far finer than the thing being measured, and a tighter loop buys nothing
but GHL rate-limit pressure across 40 tenants.

**No inbound webhook.** GHL webhook authentication is an unsettled design
question, and a poll has everything it needs. A webhook would make detection
faster, not more correct. Add it later as an optimisation on a working loop.

**Do not let the two derivations drift.** Time-in-stage on the card and
`hoursRemaining` in the sweep come from the same start time. One function, one
answer.
