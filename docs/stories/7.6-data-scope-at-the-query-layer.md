# Story 7.6 — Data scope at the query layer

**Epic:** 7 — Command surface and configurability
**Status:** In progress — enforcement layer and metric registry landed, route wiring outstanding

## Story

As a closer who is also the closing manager, I want each hat to show the rows that hat is
entitled to, so that my own numbers and my team's numbers are different views rather than the
same view with different labels.

## Context

"What data am I allowed to see on my dashboard" has three parts. Two already exist:

- **Which widgets** — `WidgetDefinition.availableFor` gates by role.
- **Which tenancy** — `RoleGrant.locations`, enforced by `requireLocationAccess`.

The third did not: **whose rows**. Inside one tenancy a `client_closer` and a `client_manager`
were indistinguishable to the data layer. Nothing expressed "my calls" versus "the team's calls".

This is the row-level counterpart to **Story 7.4** (client-visibility allowlist), and takes the
same position that story does: enforce where the data is fetched, not where it is rendered.
7.4 governs *which columns*; this governs *whose rows*. Both fail the same way if left to a
conditional in a component.

The failure mode is specific: a metric fetcher that ignores its filter shows one person another
person's numbers, fails silently, reviews clean, and is found by a user rather than a test. So
the design goal was not "remember to scope" but "an unscoped fetch does not compile."

## Acceptance criteria

1. A resolver turns a session into a filter describing whose rows it may read.
2. The filter cannot be constructed anywhere but the resolver — no call site can fabricate one.
3. A metric cannot be registered without a fetch that takes the filter.
4. Dashboard code cannot reach the database directly, bypassing the registry.
5. A metric that ignores its filter fails CI without anyone writing a test for it.
6. The resolver fails closed: unknown role, unreadable scope, or an empty team all narrow to
   the caller's own rows — never to everyone.
7. Existing claims, which carry no scope, keep working.

## Dev notes

`METRIC_REGISTRY` is deliberately empty at this commit. The enforcement layer lands first so
that every metric added after it is scoped by construction; migrating the existing eleven
widgets is separate work with its own risk, since saved dashboards reference the bundled ids
and must not reset.

`unsafeScopeForTests` is the one escape hatch, named so it cannot be mistaken for legitimate
application code. The alternative — exporting the internal mint, or letting tests cast — both
read as reasonable at a call site, which is exactly the property the brand exists to remove.

`test/require-location-access.test.ts` proves the tenancy guard behaves correctly when called,
but not that every call site calls it. AC5 exists because that gap is what a registry-driven
test closes, and it is why the test enumerates the registry rather than listing metrics.

### Zone repair, 2026-08-21

The zone above originally targeted `lib/dashboard/**` and `app/dashboard/**`. The Angular
cutover deleted `app/dashboard/` and moved every server-side reader under `app/api/dashboard/**`,
so half the zone matched nothing from that commit onward. Lint stayed green the whole time,
because a target that matches no file reports no violation. The task line now reads `app/api/**`,
which is what it guards.

Two files had been querying from outside the zone with no disable comment needed:
`app/api/clients/_lib/client-record.ts` and `app/api/clients/[clientId]/creatives/route.ts`.
Neither is a leak, since both reads are rooted at a `clientId` that `gateClient` has already
authorised, but nothing was counting them. They now carry the same disable-with-marker as the
six in `lib/dashboard`, so the migration list is one list.

The target is `app/api/**` rather than `app/api/dashboard/**` on purpose: the endpoint surface
is now the only server-side caller, and the narrower path would have missed both of those files.

This repairs a task that was already checked off. It does not advance the story. `METRIC_REGISTRY`
is still empty, `resolveScope` still has no application call site, and the registry-driven test
still generates zero cases, so the three unchecked tasks and the status are unchanged.

### Metric registry migration, 2026-08-21

`METRIC_REGISTRY` is no longer empty. Three metrics are registered
(`pipeline_open_value`, `pipeline_by_stage`, `appointments_booked`) and AC5 is
in force: sabotaging one of them to drop its uid constraint fails
`test/metric-scope.test.ts` on two assertions, with no test written for that
metric by hand.

**AC5's test had to change, and it is why the registry stayed empty.** As
written it asserted that a metric returns different results for two different
uids, then called each metric's real `fetch` to check. Registering any metric at
all failed it immediately, proven with a throwaway entry before any of this
landed. Two things were wrong with it. Uid-variance is false for a legitimately
tenancy-wide metric, where two execs in one tenancy *should* see the same
number. And calling real fetches would drive network I/O from the unit suite the
moment a metric had a live data path.

The property now policed is narrower and provable: a metric must push the scope
it was handed down to the data layer instead of fetching wide and filtering
afterwards. Those two produce an identical number today and diverge the moment a
dataset outgrows one page, because what leaks is the rows that crossed the
boundary, not the rows that survived the reduce. `Metric.fetch` therefore takes
a `MetricSource` port, the test passes a recording fake, and the assertions read
the queries. The file carries a canary: a deliberately leaky metric that returns
the correct number and is caught anyway.

**The uid mapping does not exist, and it bounds what "scoped" means today.**
`ScopeFilter.uids` are Firebase uids; GHL rows carry `assignedTo`, a GHL user
id. `Tenant.ownerGhlUserId` covers only the tenant owner, and `users` holds
sign-in identity alone. So an adapter over GHL can supply `SourceRow.ownerUid`
only as null, and a metric can be location-scoped for real now and uid-scoped
only once that mapping exists. This is a data-model decision, not a fetch bug,
and it belongs to whoever owns the identity model.

**The three unchecked tasks stay unchecked**, and none of them is
half-finished-and-claimed:

- Migrating *eleven* widget ids to `(metric, visual)` pairs is not satisfiable
  as written, and the honest count is zero rather than a partial three.
  `Shape` covers numbers; a deal board, a day's schedule, a client book, a team
  rollup, a department summary and a calendar are screens. The three metrics
  registered here are new capabilities, not replacements: `appointments_booked`
  counts appointments and `day_view` lists today's calls, so mapping one to the
  other would answer a different question while looking like a migration. An
  earlier draft of this commit did exactly that for three ids and it was wrong.
  `BUNDLED_WIDGET_METRICS` therefore names all eleven with `null`, which keeps a
  saved dashboard from referencing an id nobody has ruled on, and a test keeps
  the map in step with `WIDGET_REGISTRY` so a new widget added without a
  decision fails CI. The task is left unchecked rather than reworded, per the
  same rule Story 11.5 followed.
- Threading `resolveScope` into `app/dashboard/widget-grid.tsx` cannot be done:
  the Angular cutover deleted that file. The equivalent is the widget endpoints
  under `app/api/dashboard/widgets/**`, and no metric is wired to a route yet.
- The six legacy disables stay until a real adapter implements `MetricSource`
  over Firestore and GHL. Nothing has moved into the registry's data path, so
  removing one now would be a false signal.

Nothing user-facing changed in this commit: no route reads a metric yet, so the
dashboard behaves exactly as it did.

### The adapter, 2026-08-21

`lib/sources/metric-source.ts` implements `MetricSource` over GHL and Meta, so a
metric now has a real data path. It sits in `lib/sources/` rather than
`lib/dashboard/` deliberately: the `import/no-restricted-paths` zone bars
dashboard code from querying directly, and the point of the zone is that
dashboard code says *what* it wants while something else decides *how*. This is
that something else, outside the zone, needing no disable comment. The six
legacy fetchers are inside it and carry one each precisely because they never
made that separation.

Every dependency is injected, so `test/metric-source.test.ts` proves the
adapter's behaviour with fakes and no GHL token. Eighteen tests, four of which
run a registered metric through the real adapter end to end.

**It fails closed on a per-user scope, and that is the headline.** With no
uid-to-GHL-user mapping, a query naming specific uids cannot be answered. Both
ways of papering over it are bugs: returning every row is the cross-user leak
this story exists to prevent, and returning no rows reads as "you genuinely have
nothing", the error-as-empty confusion the ApiResult contract refuses elsewhere.
So it throws `UnsupportedScopeError`, names the missing mapping in the message,
and does not touch the data layer first.

**The consequence to weigh before wiring a route.** `DEFAULT_SCOPE_BY_ROLE`
gives `self` to `tag_sales`, `tag_setter`, `client_closer` and `client_setter`.
All three registered metrics list `client_closer` in `availableFor`, so with the
real adapter a closer placing one of them gets an error every time, not a
number. Nothing is wired to a route yet, so nobody can hit it today, and that is
the decision this leaves open: either narrow `availableFor` to the roles that
resolve to tenancy scope, or add the uid mapping. Narrowing hides a capability;
the mapping is the real fix. It is a data-model call, not a fetch bug.

Task 3 (removing the six legacy disables) stays unchecked. The adapter does not
replace `csm-clients`, `csm-directory`, `customization`, `location-config`,
`freshness` or `phase3-status` — none of their data paths moved into the
registry — so removing a disable now would be a false signal.

### Split out, 2026-08-21

Two findings from the work above are their own stories rather than notes here:

- **7.7 — Write scope and team to the claim.** `setUserClaims` writes only
  `{ role, locations }`. Nothing has ever written `scope` or `team`, so the read
  path this story built has never seen either and `resolveScope` always falls
  through to `DEFAULT_SCOPE_BY_ROLE`. The per-hat scope is inert until that is
  fixed.
- **7.8 — Map uids to GHL users.** No join exists between Firebase uids and the
  GHL user ids on the rows, which is why the adapter refuses a per-user scope.
  This is what gates wiring a metric to a route.

Neither depends on the other. `team` scope needs both.

### Metric semantics repaired, 2026-08-22

The 2026-08-22 adversarial review (docs/reviews/2026-08-22-branch-review-fix-plan.md,
Stream 1) found that all three registered metrics computed a number that did
not match its name. The scope machinery held; the semantics inside it were
wrong in seven ways, now fixed:

- "Open pipeline value" summed won, lost and abandoned deals (fetch defaulted
  to status "all" and SourceRow dropped status). `SourceQuery` now carries a
  required `statuses` constraint; the pipeline metrics ask for `["open"]`, and
  a single status is pushed down to the GHL query so the pagination budget is
  not spent on dead records. "any" is the explicit opt-in for status-blind
  reads; there is no default.
- The same metric was a point-in-time stock sliced by a creation-date flow
  filter: an open deal older than the period vanished. `SourceQuery` now
  carries `timeframe: "in-period" | "current"`; the pipeline metrics are
  "current" and no dataset gets a bespoke period exemption anymore (the old
  ad_spend special case is gone with it).
- Sums covered at most the first 100 rows per pipeline. `searchAllOpportunities`
  (lib/ghl/opportunities.ts) follows `meta.nextPageUrl` to exhaustion through
  `ghl()` (so `requireLocationAccess` runs on every page), refuses a
  pagination URL that leaves the GHL host, and throws past a 50-page sanity
  cap rather than returning a clipped set as if complete.
- "Appointments booked" counted cancelled, no-show and invalid events. The
  metric now asks for `["new", "confirmed", "showed", "noshow"]` — a no-show
  was still a booked appointment; a cancelled one stopped being one.
- Ad spend for any non-trailing period returned the trailing window from
  today, relabelled. `getAdSpendForRange` (lib/meta/ads.ts) honours the
  period's position; `getAdSpend` keeps its trailing anchor for the cards it
  was built for. The range path also stops making the trailing-7-day trend
  call nothing on it used.
- Two locations sharing one `metaAdAccountId` each contributed the account's
  full spend. The adapter now dedupes by account before fetching.
- A row with an unparseable timestamp silently vanished from every sum
  (`Date.parse` NaN fails every period comparison). `SourceDataError` now
  fails the read loudly instead, per the no-error-as-empty contract.

test/metric-scope.test.ts gained registry-driven pins for the semantics
(statuses and timeframe per metric), so a metric added tomorrow cannot quietly
fetch closed deals; test/opportunities-pagination.test.ts pins the pagination
including the loud-failure cap. 483 tests to 493.

Still open from the same review: availableFor advertises these metrics to
self/team roles the adapter rejects (Stream 3 of the fix plan), and SourceQuery
remains unbranded. Neither is made worse by this change.

### Boundary hardened, 2026-08-22 (review Stream 3)

- **SourceQuery is now unforgeable**, closing the review's cross-tenant
  finding: the adapter trusted a plain exported type, so any server code could
  hand-write `{ dataset: "ad_spend", locations: [victim], uids: "all" }` and
  read another tenant's Meta spend with no session anywhere on the path (the
  GHL datasets had `requireLocationAccess` downstream; ad_spend had nothing).
  The query now carries the same unique-symbol brand as ScopeFilter, with
  `scopedQuery` as the only minter and `unsafeQueryForTests` as the marked
  escape hatch. The test file's canary had to switch to the test constructor,
  which is itself the fix demonstrated: the literal it used to write no longer
  typechecks, pinned by a `@ts-expect-error` that fails the build if forging
  ever compiles again.
- **availableFor is narrowed to tenancy-resolving roles** (tag_exec, tag_csm)
  until Story 7.8 lands the uid mapping. All three metrics were offered to
  client_closer and client_manager, whose default scopes the adapter refuses:
  a closer placing "Open pipeline value" got a permanent error widget. A
  registry-driven test now resolves every availableFor role through
  resolveScope and asserts the adapter can serve it, so the mismatch cannot
  recur silently when roles or datasets change.
- **The two legacy eslint disables are line-scoped.** File-wide
  `eslint-disable import/no-restricted-paths` switched off every zone in
  those files, not just the firestore one the comment described; probed
  before/after, a `lib/postgres` import in them now fires again.
