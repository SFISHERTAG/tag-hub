# Story 1.4 — Role and location claims

**Epic:** 1 — Foundation and access
**Status:** Done
**Depends on:** 1.3

## Story

As the Hub, I want every authenticated user to carry a role and an explicit set
of permitted locations, so that authorisation is a property of the session
rather than a check each feature remembers to make.

## Context

Seven roles across two sides. A client user must never reach another tenant by
any path; a CSM reaches only assigned clients; an executive reaches all.

Getting this wrong is not a bug, it is one client's lead list shown to another.

## Acceptance criteria

1. Custom claims carry `role` and `locations`:
   ```
   { role: 'tag_csm', locations: ['loc_a', 'loc_b'] }
   { role: 'client_closer', locations: ['loc_a'] }
   ```
2. Roles are exactly: `tag_sales`, `tag_sales_manager`, `tag_csm`, `tag_exec`,
   `client_closer`, `client_manager`, `client_owner`.
3. `tag_exec` resolves to all known locations rather than an enumerated list,
   so a new client does not require re-provisioning.
4. A server helper `requireLocationAccess(session, locationId)` throws unless
   the location is permitted, and is called before every GHL request.
5. Attempting a location outside the permitted set returns 403 — not an empty
   page, not a redirect that leaks existence.
6. Claims are set by an admin action, not self-service.

## Dev notes

`lib/ghl/client.ts` already takes `locationId` as the first argument of every
call, with no ambient current location. That is deliberate and it is what makes
this story a guard rather than an audit of every query — the parameter is
already explicit at every call site.

Claims are capped at 1000 bytes. Enumerating 40+ location ids for a `tag_exec`
would approach that, which is why 3 resolves dynamically instead.

Return 403 rather than 404 for a permitted-but-wrong tenant. A 404 leaks
whether the tenant exists; both are refusals, only one is quiet about it.
