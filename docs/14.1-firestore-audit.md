# Story 14.1 Audit — Firestore call sites and data paths

**Date:** 2026-08-23 (rewritten from code)
**Baseline:** `635e14e` (`main`)
**Scope:** app-side Firestore access — `lib/**` and `app/api/**`. `functions/**` is
out of scope; see "Why functions/ is excluded" below.

> This file replaces an earlier version audited at `3b3f65c`. That version was
> derived from filenames rather than from code and was wrong in the file list,
> in nearly every collection name, and in its transaction finding. The
> corrections are itemised at the end under "What the previous audit got wrong",
> because later stories were sequenced off those numbers.

## Summary

- **20 files** call `firestore()`. 18 in `lib/**`, 2 in `app/api/**`.
- **1 implementation file**, `lib/firestore.ts` (30 lines), which is the only
  place the SDK is constructed.
- **21 distinct document paths**, of which **10 are parent-scoped
  subcollections**. There is no flat 14-collection model.
- **6 operations beyond get/set/query**: 2 transactions, 1 batch, 1 collection
  group query, 1 multi-document `getAll`, 1 projection, plus create-if-absent.
- **3 server-side sentinels** (`serverTimestamp`, `delete`, `arrayUnion`), which
  the first pass of this audit missed. See below.
- **2 test files** (`lib/ghl/store.test.ts`, `lib/meta/retry.test.ts`) reach the
  SDK and will need the seam's fake.

## Operations the interface must carry

| Operation | Site | Why it matters for 14.2+ |
| --- | --- | --- |
| `runTransaction` | `lib/auth/otp.ts:140` | Verify-and-consume of an OTP. Read-modify-write under contention; the whole point is that two verifies cannot both win. |
| `runTransaction` | `lib/audit/store.ts:148` | Amend an audit entry. Must stay atomic against the immutability guarantee. |
| `batch` | `lib/knowledge-base/db.ts:91` | Write the version snapshot and the page update together. A partial write loses revert history. |
| `collectionGroup` | `lib/meta/retry.ts:155` | Scans `metaConversionLog` across every location for failed conversions. No per-parent equivalent — the retry job does not know which locations have failures. In Postgres this is the unqualified table scan, which is easier, but the seam must expose it or the retry job cannot be written. |
| `getAll` | `lib/ghl/store.ts:256` | Multi-document read by ref list. Degrades to N round trips if the seam only offers `get(id)`. |
| `select()` | `lib/ghl/tenants.ts:97` | Projection to `locationId` only, over every location. Dropping it turns a key scan into a full document read. |

### Server-side sentinels, missed by the first pass of this audit

Recorded as a correction to this document rather than quietly folded in, since
its whole point is that an unverified inventory is worthless.

The first version of this file said `FieldValue.increment` is unused, which is
true, and stopped there. It should have asked what `FieldValue` is used *for*.
Three sentinels are live:

| Sentinel | Site | Postgres equivalent |
| --- | --- | --- |
| `FieldValue.serverTimestamp()` | `lib/bug-reports.ts:41` | `now()` |
| `FieldValue.delete()` | `lib/onboarding/store.ts:39` | remove a JSON key |
| `FieldValue.arrayUnion()` | `functions/src/firestore.ts:35` | array append (out of 14.1 scope) |

These are not ordinary values and cannot cross the seam as data. `serverTimestamp`
in particular is assigned by the store, not the caller, so replacing it with
`Date.now()` during migration would be a silent behaviour change that only shows
up as clock skew between writers.

The `deleteField` site is nested — `{ completedTasks: { [taskId]: ... } }` — so a
top-level-only scan misses the one live use in the repo.

`lib/auth/otp.ts:110` also writes `issuedAt: Timestamp.now()` alongside
`expiresAt`, which the first pass missed when listing which fields need
normalising.

`FieldValue.increment` is **not** used anywhere. The only occurrence is a comment
at `lib/auth/otp.ts:131` explaining why it was deliberately *not* used: it would
fix the counter and leave the gate racing.

## Two leaks to close

**`lib/ghl/store.ts:33` re-exports the handle.** `export { firestore };` means
any module importing `lib/ghl/store` can obtain a raw Firestore instance without
importing `lib/firestore` at all. A lint rule keyed on the import path will not
catch this. The re-export has to go, and the rule needs a second check for the
symbol.

**`lib/webhooks/idempotency.ts` has no importers.** It is a hand-synced mirror of
`functions/src/lib/webhooks/idempotency.ts`, which is the live one. The two files
disagree about which is authoritative: the `lib/` header says the `functions/`
copy is the duplicate, the `functions/` header says `lib/` is the source of
truth. Nothing in `lib/` or `app/` imports the `lib/` copy. It is dead code kept
alive by a comment, and it should be deleted when the `functions/` fold lands
rather than seamed here.

## Migration 003 already built most of the target schema, and it corroborates this audit

Surfaced by the session doing 14.2 and verified here at `0518b32`.

`functions/sql/003_migrate_firestore_to_postgres.sql` creates **17 tables**. Only
three are ever queried by application code — `csm`, `dashboard_configs`,
`course_progress`. The test is `grep -riE "(from|into|update|join)[[:space:]]+<table>"`
across `lib/`, `app/` and `functions/src`, excluding tests.

The other **14 have zero SQL against them**, including `clients`, which
`docs/data-model.md` describes as a live denormalised Postgres table:

`users`, `tenants`, `auth_codes`, `groups`, `audit_log`, `bug_reports`,
`clients`, `client_alerts`, `client_meta_creatives`, `appointment_outcomes`,
`ghl_agency_token`, `ghl_location_tokens`, `webhook_dead_letter`,
`webhook_events_processed`.

**Two consequences for Epic 14.**

1. **The epic is scoped as create-table, backfill, cut over. For most collections
   the table has existed since 003.** That is story 11.6's exact condition — an
   empty Postgres schema beside a live Firestore collection — already in the tree
   fourteen times. Stories 14.4 through 14.9 assume they are creating these
   tables. They are not.
2. **A stale schema that nearly fits is more dangerous than none**, because it
   invites a cutover onto columns nobody re-examined. Each story has to read its
   table in 003 and decide adopt-or-replace before writing a backfill. Do not
   assume these definitions are usable.

**Why this is also the strongest corroboration of the inventory above.** 003 was
written months ago, from the code, by someone solving a different problem. Set
its table list beside the collection list the three contract docs carried:

## Why `functions/` is excluded

`functions/` is a separate npm workspace with `rootDir: ./src` and no path
mapping to `lib/`. Nothing in `functions/src` imports `lib/` and it cannot,
so a `lib/data/` module is unreachable from there. It also pins
`@google-cloud/firestore` `^7.11.0` against root's `^8.7.1` — different majors,
so a shared module would need those reconciled first.

Decided 2026-08-23: `functions/` folds into `app/api` in its own story. Its three
webhook endpoints become Next route handlers, which collapses the duplicated
Firestore init, idempotency, GHL client, Slack, Drive and Postgres modules at the
same time. Seaming `functions/src/firestore.ts` here would be work thrown away by
that fold.

## What the previous audit got wrong

Recorded because 14.3–14.10 were sequenced off it.

1. **Included two files that do not touch this seam.**
   `functions/src/webhooks/phase1-provisioning.ts` and
   `functions/src/webhooks/phase3-meta-setup.ts` import `../firestore.js`, the
   `functions/` module, not `@/lib/firestore`.
2. **Missed four real call sites.** Both `app/api/**` files,
   `functions/src/webhooks/phase2-intake-submit.ts`, and the `lib/` copy of
   `idempotency.ts`.
3. **Named collections that do not exist:** `tenants`, `ghl_subscriptions`,
   `meta_campaigns`, `deadLetterQueue`, top-level `auditLog`, top-level
   `creatives`, `orgs`, `users`. `lib/ghl/tenants.ts:24` sets
   `TENANTS_COLLECTION = "locations"` — the module is named for a concept that
   has no collection.
4. **Reported "Transaction usage: None found."** There are two `runTransaction`
   sites and one `batch`, which is the same count `docs/epics.md` already
   documented as verified in code.
5. **Attributed `FieldValue.increment` to `lib/bug-reports.ts` and
   `lib/onboarding/store.ts`.** Neither uses it. Nothing does.
6. **Missed the collection group query, the `getAll`, the `select()`
   projection, and the `lib/ghl/store.ts` re-export.**
7. **Modelled the data as 14 flat collections.** Half the real paths are
   parent-scoped.
